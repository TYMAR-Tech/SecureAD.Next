## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-204
  name: "Unexpected Principal with High-Impact Right on Tier-0 Target"
  description: >-
    A principal has a high-impact control right (ResetPassword, AddMember, WriteDACL, WriteOwner, GenericAll, or ownership) on a Tier-0 target — a single-edge privilege spill that enables direct domain compromise.
  severity: Critical
  category: PrivilegeEscalation
  remediation: >-
    Remove the high-impact right unless the delegation is explicitly required and documented.
  mitre: T1098
  tags: ["tier-zero", "spill", "single-edge", "privilege-escalation"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 577–586.

## 2. Intended detection (plain English)

Fire one Critical finding per `(non-privileged source, Tier-0 target)` pair when a `fact_control_edge` exists with `control_type ∈ { ResetPassword, AddMember, WriteDacl, WriteOwner, GenericAll, Owns }` against an object the rule classifies as Tier-0. "Tier-0" is computed at evaluation time as the union of:

- **Broad-SID Tier-0 targets.** `IsBroadSidTargetTierZero` flags well-known Tier-0 SIDs (RID 502/512/516/518/519, Builtin Administrators) **and** structural Tier-0 DNs (`CN=AdminSDHolder,…`, `OU=Domain Controllers,…`, plain `DC=…` heads excluding `DC=DomainDnsZones` / `DC=ForestDnsZones`).
- **Privileged-by-membership targets.** `target_sid` resolves to a SID that is itself in `context.PrivilegedSids` (transitive DA / EA / SA / Builtin Administrators members).

The rule then **deduplicates with SEC-201** by skipping `domainDNS` targets — that class is owned by SEC-201's narrower three-control-type rule. Deny-cancelled edges are excluded by `e.deny_cancelled = 0`. Tombstoned targets must not fire — a deleted object cannot host an actionable spill. Privileged sources must not fire — the rule is about *unexpected* principals.

### 3.1 Effective SQL (copied from code)

```sql
SELECT e.source_sid, e.target_object_guid, o.distinguished_name, e.edge_id,
       e.control_type, o.sid AS target_sid, o.object_class
FROM fact_control_edge e
INNER JOIN dim_object o ON e.target_object_guid = o.object_guid
WHERE e.deny_cancelled = 0
  AND e.control_type IN ('ResetPassword', 'AddMember', 'WriteDacl', 'WriteOwner', 'GenericAll', 'Owns')
  AND o.is_deleted = 0
ORDER BY e.source_sid, e.target_object_guid, e.control_type
```

### 3.2 Post-SQL filters (in C#)

- `IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — drops well-known admin and transitively privileged sources. `IsPrivilegedPrincipal` already delegates to `IsAdminSid`, so a single call covers both well-known admin RIDs/system SIDs and transitively privileged members. (Previously `IsAdminSid(sid) || IsPrivilegedPrincipal(...)` — collapsed under `[IMP-PRIV-MEMB-SRC]`.)
- `targetIsTierZero = IsBroadSidTargetTierZero(targetSid, targetDn) || (targetSid is not null && IsPrivilegedPrincipal(targetSid, context.PrivilegedSids))` — keeps only Tier-0 targets.
- `targetClass.Equals("domainDNS", OrdinalIgnoreCase)` — drops domain-root targets (delegated to SEC-201).

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Edges with non-spill rights | SQL `e.control_type IN ('ResetPassword', 'AddMember', 'WriteDacl', 'WriteOwner', 'GenericAll', 'Owns')` | Lower-impact rights (ReadProperty, GenericRead, etc.) are not single-edge takeover primitives; the catalog scopes the rule to the six rights that are. |
| Deny-cancelled edges | SQL `e.deny_cancelled = 0` | Already neutralised at edge-derivation time; firing would be noise. |
| Tombstoned targets | SQL `o.is_deleted = 0` | A deleted object cannot host an actionable spill. |
| Non-Tier-0 targets | C# `IsBroadSidTargetTierZero` ∪ privileged-by-membership check | Catalog scope is "Tier-0 target"; non-Tier-0 spill is partly covered by SEC-204's broader siblings (SEC-006 / SEC-101 / SEC-204 itself for Tier-0 only). |
| `domainDNS` targets | C# `targetClass.Equals("domainDNS", …)` | Delegated to SEC-201 (which scopes to `WriteDacl` / `WriteOwner` / `Owns` only) to avoid duplication. Pinned by `WhenNonPrivilegedHasWriteDaclOnDomainDNS_ThenSEC204DoesNotFire`. |
| Well-known admin sources | C# `IsAdminSid(sid)` | DA / EA / SA / BA legitimately hold these rights. |
| Transitively privileged sources | C# `IsPrivilegedPrincipal(sid, …)` | DA / EA members inherit the same trust. |

Not excluded (intentionally subject to review):

- Broad SIDs (`Everyone`, `Authenticated Users`, etc.). In scope — they are emphatically *not* privileged. Note SEC-060 also fires for the broad-SID side of these primitives; documented in §13 `[IMP-DUP-RULE]`.

## 12. Defects / deferred items

1. **Tombstone gap (resolved on rule).** SQL did not filter `o.is_deleted = 0`, so a stale spill edge against a tombstoned Tier-0 target surfaced as Critical. Same defect class fixed in SEC-122 / SEC-123 / SEC-124 / SEC-126 / SEC-131 / SEC-201. Fixed inline this session; pinned by `WhenSEC204TargetIsDeleted_ThenSEC204DoesNotFire`. With this fix, every audited rule in `AdvancedRuleEvaluator` is `is_deleted = 0`-clean. Cross-cutting tracked under `[IMP-DEL-OBJ]` (remaining sweep targets `KerberosRuleEvaluator` SEC-020/021/022/023, which have `*_KnownLimitation` pin tests today).

## 13. Improvement suggestions (not blocking)

1. `[IMP-DEL-OBJ]` — Resolved on SEC-204. The `AdvancedRuleEvaluator` family is now fully tombstone-filtered. Cross-cutting sweep narrows to `KerberosRuleEvaluator` (SEC-020 / 021 / 022 / 023) — pinned today by `*_KnownLimitation` tests.
2. `[IMP-COV-MEMB]` — `RuleCoverageRequirements["SEC-204"]` does not declare `GroupMembership` even though `IsPrivilegedPrincipal` is consulted **twice** (once for source filtering, once for target Tier-0 classification). Same gap as SEC-025 / SEC-080 / SEC-081 / SEC-090 / SEC-123 / SEC-124 / SEC-126 / SEC-131 / SEC-201.
3. `[IMP-PRIV-MEMB-SRC]` — Mechanical redundancy resolved: the post-SQL source filter now uses a single `IsPrivilegedPrincipal(sid, …)` call (the historical `IsAdminSid(sid) || IsPrivilegedPrincipal(...)` disjunction was collapsed), in lock-step with the SEC-201 fix. The semantic question — whether transitively privileged sources should be excluded outright vs. severity-tiered — is still open at the cross-cutting level (see `IMPROVEMENTS.md`).
4. `[IMP-DN-ENRICH]` — `Detail` interpolates `dn ?? targetGuid.ToString()`; the trustee SID is surfaced raw with no `sam_account_name` join. Parity with SEC-100 / 101 / 102 / 120 / 121 / 122 / 123 / 124 / 126 / 131 / 201.
5. `[IMP-PARITY-TEST]` — No per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-204. Cross-cutting.
6. `[IMP-DUP-RULE]` — Broad-SID spill against Tier-0 surfaces under both SEC-060 (Critical) and SEC-204 (Critical); `domainDNS` spill via `WriteDacl/WriteOwner/Owns` is delegated to SEC-201 but `GenericAll` / `AddMember` on a `domainDNS` target would fire under SEC-204 alone (potential coverage gap if `GenericAll` on `domainDNS` is currently expected to land in SEC-201). Document the partition. Same gap pattern as SEC-201.
7. `[IMP-CTRL-SCOPE]` — **RESOLVED.** SEC-204's spill list is `IN ('ResetPassword', 'AddMember', 'WriteDacl', 'WriteOwner', 'GenericAll', 'Owns')` (verified `AdvancedRuleEvaluator.EvaluateSpillToTierZero`). `GenericWrite` is intentionally **not** in the set — it grants `WRITE_PROPERTY` but not `WRITE_DAC` / `WRITE_OWNER`, so it cannot rewrite the target's DACL or seize ownership the way the spill rule means (a `GenericWrite` property primitive against a privileged target is covered by SEC-006 / SEC-024 / SEC-025). The exclusion is now pinned by `WhenNonPrivilegedHasGenericWriteOnPrivilegedTarget_ThenSEC204DoesNotFire` so a future "widen to all writes" edit cannot silently fold it in.
8. `[IMP-TGT-CLASS]` — `IsBroadSidTargetTierZero`'s DN-prefix matching is brittle for non-default-naming-context Tier-0 (`Configuration` / `Schema` NCs, multi-domain partitioned forests). Same cross-cutting gap as SEC-201.
9. `[IMP-CTX-RULEID]` — `CreateEdgeFinding` does stamp `rule_id`, so this rule is fine on its own — but the cross-cutting tag still applies until `CreateDelegationFinding` is brought into parity (open under SEC-122 / 126 / 131).

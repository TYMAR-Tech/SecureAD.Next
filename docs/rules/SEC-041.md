## 2. Status summary

SEC-041 is a **catalog stub**: `enabled: false` in `rules.yaml`, with **no evaluator implementation**.
It is intentionally inert — no `FindingV2` is ever produced for `SEC-041`. The catalog entry reserves
the id and describes the intended future detection (certificate **auto-enrollment**, i.e. the
`Certificate-AutoEnrollment` extended right / `CertificateAutoEnroll` control type, distinct from the
plain `Certificate-Enrollment` covered by SEC-040).

The capture / control-edge side already recognizes `ControlType.CertificateAutoEnroll`
(mapped in `ControlEdgeService.DeriveControlTypes` from `a05b8cc2-17bc-4802-a710-e7c15ab866a2`), so a
future implementation has the underlying edge available; only the rule evaluator is absent.

## 5. Deferred implementation notes

If SEC-041 is implemented later, the natural shape mirrors SEC-040:
- Query `fact_control_edge` for `control_type = 'CertificateAutoEnroll'` on `pKICertificateTemplate`
  (and possibly `pKIEnrollmentService`) targets, excluding well-known admins.
- Assign a `mitre` id (T1649 is the SEC-040 analogue) and flip `enabled: true`.
- Constrain to auto-enroll-capable template classes to avoid stray-edge false positives (the
  `[IMP-TGT-CLASS]` pattern already applied to SEC-040).

Until then this card records that the rule is **intentionally not active** so its absence is not
mistaken for missing coverage.

## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-072
  name: "Path to Tier 0 Shadow"
  description: >-
    A non-administrative principal has a privilege escalation path to a Tier 0 Shadow target — a principal that is one action away from Tier 0 (e.g., transitive DA member, DCSync holder, unconstrained delegation).
  severity: High
  category: PrivilegeEscalation
  remediation: >-
    Review and break the escalation path. Consider whether the shadow target itself should be reclassified or hardened.
  mitre: T1078
  tags: ["escalation-path", "tier-zero-shadow"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 335–344.

## 2. Intended detection (plain English)

Fire one finding per row in `fact_escalation_path` where:

- the **target** is classified `Tier0Shadow` — a principal that is one
  action away from Tier 0 (transitive Domain Admins / Enterprise Admins
  / Schema Admins member, DCSync holder, unconstrained delegation
  principal, RBCD on a DC, GPO linked to the DC OU); and
- the **source** is not itself a well-known admin principal
  (`IsAdminSid` exclusion).

Unlike SEC-070 (≤2 hops) and SEC-071 (≥3 hops), SEC-072 has **no
path-length bound** — any path to a Tier 0 Shadow target surfaces.

Tier 0 Shadow classification is intended to come from `dim_asset_tier`,
which is populated by `DerivedAssetTierClassifier` (closure expansion,
dangerous control edges, DCSync, unconstrained delegation, RBCD on DCs,
GPOs linked to DC OU). When `dim_asset_tier` is absent, the evaluator
falls back to a narrower RID-based classifier that only recognises RID
519 (Enterprise Admins) as `Tier0Shadow`; see §12.1 and
`[IMP-FALLBACK-TIER]`.

Severity is fixed at `High`. SEC-076 (Path to Tier 0 Shadow via DCSync)
and SEC-077 (Path to Tier 0 Shadow via unconstrained delegation) are
the narrower siblings that filter the same `Tier0Shadow` target set by
`dim_asset_tier.reason`.

SEC-072 shares the entire `EvaluateByTier` / `EvaluateByFallbackTier`
implementation with SEC-070 and SEC-071. The differences are:

- the tier passed to the helper — `"Tier0Shadow"` instead of `"Tier0"`
  (SEC-070/071) or `"Tier1"` (SEC-073/074) or `"Custom"` (SEC-075); and
- no path-length bound — unlike SEC-070 (`maxPathLength: 2`) and
  SEC-071 (`minPathLength: 3`), SEC-072 passes neither bound; and
- the severity resolved via `SeverityOf("SEC-072")` — `High` on both
  the tier-table and the fallback code paths after this audit's fix
  (see §12.2).

### 3.1 Effective SQL (copied from code)

Primary path (when `dim_asset_tier` exists):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name,
       att.reason AS tier_reason
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
LEFT JOIN dim_asset_tier att ON p.target_sid = att.sid
WHERE COALESCE(att.tier, 'Tier2') = $tier
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $tier = 'Tier0Shadow'; no path-length bounds
```

Fallback path (when `dim_asset_tier` does not exist):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
WHERE 1 = 1
ORDER BY p.source_sid, p.target_sid, p.path_id
-- no path-length bounds; tier classification then applied per row via ClassifyFallbackTier
```

### 3.2 Post-SQL filters (in C#)

- `IsAdminSid(sourceSid) → skip` — exclude rows whose source SID is a
  well-known admin (RID 500, 502, 512, 516, 518, 519, 520, 521, 526,
  527 — `AdminRids` in `RuleEvaluatorHelpers.cs:27`) or a well-known
  privileged system SID (`PrivilegedSystemSids` in `RuleEvaluatorHelpers.cs:46`).
  `BroadSids` are explicitly **not** treated as admins.
- Fallback path only: `ClassifyFallbackTier(targetSid) != "Tier0Shadow" → skip`
  — drops rows whose target RID is not 519. RID 512 routes to
  SEC-070/071 via `Tier0`, RID 516 routes to SEC-073/074 via `Tier1`,
  every other RID lands in SEC-075 (Custom). Same
  `[IMP-FALLBACK-TIER]` gap as SEC-070/071.

The Tier 0 Shadow classification itself depends on group membership

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Paths to non-Tier-0-Shadow targets | `WHERE COALESCE(att.tier, 'Tier2') = 'Tier0Shadow'` (primary) / `ClassifyFallbackTier(target) == "Tier0Shadow"` (fallback) | SEC-072 is the Tier 0 Shadow rule by definition. Tier 0, Tier 1, and unclassified targets belong to SEC-070/071, SEC-073/074, and SEC-075 respectively. |
| Admin sources | Post-SQL `IsAdminSid(sourceSid) → continue` | A path starting from `Domain Admins → ... → Tier 0 Shadow` is normal Tier-0 RBAC reaching its shadow set, not an escalation. Uses RID + well-known SID matching, never group-membership expansion (see E7). |
| Broad SIDs not excluded | `IsAdminSid` explicitly returns `false` for `BroadSids` | An `Authenticated Users → Tier 0 Shadow` path is still a High escalation and must surface. |

Not excluded (intentionally subject to review):

- `coverage_complete = 0` rows — the rule still fires; the per-row flag
  flows through `CreatePathFinding` to `FindingV2.CoverageComplete`.
- Deleted (`is_deleted = 1`) source / target — `dim_object` is **not**
  joined; the path service is expected to drop tombstoned principals
  at capture time. Cross-cutting `[IMP-DEL-OBJ]`.
- Cross-domain paths — surface as-is. A Tier 0 Shadow target in any
  domain of the forest is in scope.
- No path-length bound — paths of length 1, 2, 5, 50 all surface.
  Accepted: by design, since the Tier 0 Shadow classification itself
  represents a one-action gap to Tier 0, so a short path is equally
  dangerous as a long path through Tier 0 Shadow.
- DCSync- and unconstrained-delegation-specific Tier 0 Shadow paths
  are **not** excluded — they fire SEC-072 **in addition to** SEC-076 /
  SEC-077 because the latter rules filter `dim_asset_tier.reason` and
  share the same path rows. Accepted: SEC-076/077 escalate severity
  (Critical / High) for the specific reasons and SEC-072 acts as the
  catch-all signal for any Tier 0 Shadow target.

- `RuleId == "SEC-072"`
- `Severity == High`
- `SubjectSid` = source principal SID
- `TargetKind == "sid"`

- `SourcePathId` populated (from `fact_escalation_path.path_id`)

- `FindingKey == "SEC-072|{source_sid}|{target_sid}|{path_id}"`

  - tier-table path: `"{source_name} has {path_length}-hop escalation path to Tier0Shadow target {target_name}{[ (tier_reason)]}: {truncated path_detail}"`

- `ContextJson` non-null (typed `PathFindingContext`) and contains:
  - `"rule_id": "SEC-072"`
  - `"source_sid"`, `"source_name"`, `"target_sid"`, `"target_name"`
  - `"path_id"`, `"path_length"`, `"coverage_complete"`
  - `"target_tier"` (`"Tier0Shadow"` on the primary code path; the
    fallback classifier value on the fallback code path)
  - `"tier_reason"` when supplied by `dim_asset_tier.reason`
  - `"path_detail"`, `"first_actionable_edge_id"`,
    `"first_actionable_edge_summary"`, `"steps"`

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Fallback classifier narrower than the tier table** `[IMP-FALLBACK-TIER]` —
   **RESOLVED.** `ClassifyFallbackTier` now delegates to
   `StaticAssetTierClassifier`, which **never** emits `Tier0Shadow` — that
   tier is a purely behavioural classification (transitive DA / EA / SA
   membership, DCSync holders, unconstrained delegation, RBCD on DCs, GPOs
   linked to the DC OU) computed only by `DerivedAssetTierClassifier` from
   `dim_asset_tier`. Consequently **SEC-072 does not fire in fallback mode**
   (correct — there is no derived shadow data without the table), and RID 519
   (Enterprise Admins), which the old fallback mis-mapped to `Tier0Shadow`,
   now correctly classifies as `Tier0` and fires SEC-070 / SEC-071. SEC-072's
   real positives are covered by `EscalationPathTierFindingsTests`
   (`WhenPathToTier0Shadow_ThenSEC072HighFinding`); the former fallback pins
   were converted to `WhenFallbackPathTo{EnterpriseAdmins,AnyTarget}_ThenSEC072DoesNotFire`.

2. **Fallback severity mismatch — fixed in this audit.**
   `GetFallbackSeverity` previously hardcoded SEC-072 to
   `Severity.Critical`, contradicting the catalog claim
   (`severity: High`) and the tier-table-backed code path
   (`SeverityOf("SEC-072") == High`, pinned by
   `WhenPathToTier0Shadow_ThenSEC072HighFinding` in
   `EscalationPathTierFindingsTests`). The fix removes the SEC-072
   arm from the switch so the default `SeverityOf(ruleId)` resolves
   it to `High` consistently in both code paths. The stale fallback
   smoke test was updated from `…GeneratesCriticalFinding` to
   `…GeneratesHighFinding`. Resolved — no tag.

## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-126
  name: "Privileged Service Account with Static Password"
  description: >-
    A privileged account has a servicePrincipalName, is Kerberoastable, and has PasswordNeverExpires set — a high-value credential theft target with a static password.
  severity: High
  category: CredentialTheft
  remediation: >-
    Migrate to Group Managed Service Accounts (gMSA) or enforce regular password rotation and remove from privileged groups.
  mitre: T1558.003
  tags: ["service-account", "kerberoasting", "static-password", "privileged"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 544–553.

## 2. Intended detection (plain English)

Fire one High finding per `(privileged subject, target object_guid)` pair when **all** of the following hold for the same principal:

1. The object has at least one `servicePrincipalName` of a recognized Windows service prefix (Kerberoastable in practice).
2. The object has `userAccountControl.DontExpirePassword` (`PasswordNeverExpires`) set, so the Kerberos service-ticket key is materially static and an offline crack of an RC4/AES blob remains valid indefinitely.
3. The principal is privileged — either a well-known admin SID/RID or transitively a member of a Tier-0 group (`PrivilegedSids`).
4. The principal is not `krbtgt` (its SPN/PWNE attributes are inherent and out of scope).
5. The object class is not `computer`, `msDS-GroupManagedServiceAccount`, or `msDS-ManagedServiceAccount`. Computer accounts auto-rotate; gMSA/MSA rotate their managed password — none of them are "static" in the sense that drives this rule.
6. The target object is not tombstoned (`is_deleted = 0`).

This combination is the classic high-value Kerberoasting target: a Tier-0 service account whose hash never changes.

### 3.1 Effective SQL (copied from code)

```sql
SELECT DISTINCT o.object_guid, o.distinguished_name, o.sid,
       GROUP_CONCAT(spn.target, '|') AS spns
FROM dim_delegation spn
INNER JOIN dim_object o ON spn.object_guid = o.object_guid
INNER JOIN dim_delegation pwd ON o.object_guid = pwd.object_guid
                              AND pwd.delegation_type = 'DontExpirePassword'
WHERE spn.delegation_type = 'SPN'
  AND o.object_class NOT IN ('computer',
                             'msDS-GroupManagedServiceAccount',
                             'msDS-ManagedServiceAccount')
  AND o.is_deleted = 0
GROUP BY o.object_guid, o.distinguished_name, o.sid
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

- `IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — drops non-privileged subjects (well-known admin RIDs **or** transitively privileged-by-membership are required to fire).
- `IsKrbtgtSid(sid)` — drops `krbtgt` (RID 502) explicitly, before the SPN check.
- `FindFirstServiceSpn(spns)` — requires at least one SPN to start with a recognized Windows service prefix
  (`HTTP/`, `MSSQLSvc/`, `CIFS/`, `HOST/`, `LDAP/`, `RPCSS/`, `FIMService/`, `TERMSRV/`, `WSMAN/`,
  `exchangeMDB/`, `exchangeRFR/`, `exchangeAB/`, `SMTP/`, `POP3/`, `IMAP/`). Pure non-service SPNs are filtered out
  (the rule wants Kerberoastable surface area, not arbitrary SPN registration).

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Objects without an SPN | SQL `INNER JOIN dim_delegation spn` | No Kerberoasting surface without an SPN. |
| Objects without `DontExpirePassword` | SQL `INNER JOIN dim_delegation pwd … 'DontExpirePassword'` | The rule is specifically the *static-password* variant; rotating accounts are covered by SEC-021 (Kerberoastable Privileged) without the static-password severity bump. |
| Computer accounts | SQL `o.object_class NOT IN ('computer', …)` | Machine accounts auto-rotate the password (default 30 days); they are not "static". |
| gMSA / MSA accounts | SQL `o.object_class NOT IN (…, 'msDS-GroupManagedServiceAccount', 'msDS-ManagedServiceAccount')` | Managed Service Accounts and Group Managed Service Accounts rotate their secrets automatically; the static-password premise does not hold. |
| Tombstoned targets | SQL `o.is_deleted = 0` | Tombstoned accounts cannot be Kerberoasted in their current state; lingering delegation rows are noise. |
| Non-privileged subjects | C# `IsPrivilegedPrincipal(sid, context.PrivilegedSids)` | Catalog explicitly scopes the rule to *privileged* accounts; SEC-020 / SEC-021 cover the broader Kerberoasting cases at a lower severity. |
| `krbtgt` | C# `IsKrbtgtSid(sid)` | krbtgt is structurally privileged with a well-known SPN/key model; surfacing it here would be permanent noise and is handled separately by hygiene workflows. |
| SPNs without a recognized service prefix | C# `FindFirstServiceSpn` | Drops e.g. UPN-style or arbitrary SPN registrations that are not realistically Kerberoastable services; parity with SEC-021. |

## 8. Edge cases considered

| # | Scenario | Resolution |
| --- | --- | --- |
| E1 | Multiple SPNs, only some service-prefix | `FindFirstServiceSpn` returns the first matching prefix; non-matching SPNs are still preserved in `all_spns` context. |
| E2 | gMSA / MSA Tier-0 account with SPN + `DontExpirePassword` | Excluded — managed password is auto-rotated, not "static". |
| E3 | Computer account in DA (e.g., a misadmin'd server) with SPN + `DontExpirePassword` | Excluded by `object_class != 'computer'`. SEC-101 covers privileged computers at a different angle. |
| E4 | krbtgt with SPN | Excluded — `IsKrbtgtSid` runs before the SPN check. |
| E5 | Tombstoned target with stale `SPN` + `DontExpirePassword` rows | Excluded — covered by N2 (`o.is_deleted = 0`). |
| E6 | Privileged subject without service-prefix SPN (e.g., UPN-only) | Excluded — `FindFirstServiceSpn` returns null; parity with SEC-021. |
| E7 | Group-membership coverage missing | Without the closure, only well-known admin SIDs/RIDs are flagged as privileged; transitive members fall out — `[IMP-COV-MEMB]`. |
| E8 | `SPN`/`DontExpirePassword` rows present but the principal is disabled (`Disabled` delegation row) | Not filtered — disabled accounts can still be re-enabled, and SPN/password attributes survive disablement. Pinned by sibling-rule philosophy (SEC-022 also does not filter). `[IMP-DISABLED-FILTER]`. |

## 12. Defects / deferred items

1. **Tombstone gap (resolved on rule).** SQL did not filter `o.is_deleted = 0`, so a stale `SPN` + `DontExpirePassword` row pair on a tombstoned privileged user surfaced as High. Same defect class fixed in SEC-122 / SEC-123 / SEC-124 in earlier sessions. Fixed inline this session; pinned by `WhenSEC126TargetIsDeleted_ThenSEC126DoesNotFire`. Cross-cutting tracked under `[IMP-DEL-OBJ]`.

## 13. Improvement suggestions (not blocking)

1. `[IMP-DEL-OBJ]` — Resolved on SEC-126. Cross-cutting sweep against the remaining sibling rules in `AdvancedRuleEvaluator` (SEC-201, SEC-204) and `KerberosRuleEvaluator` (SEC-020/021/022/023) is still open — pinned by the existing `*_KnownLimitation` tests on those rules.
2. `[IMP-COV-MEMB]` — `RuleCoverageRequirements["SEC-126"]` does not declare `GroupMembership` even though `IsPrivilegedPrincipal` consumes the transitive closure. Same gap as SEC-025 / SEC-080 / SEC-081 / SEC-090 / SEC-123 / SEC-124.
3. `[IMP-DN-ENRICH]` — `Detail` interpolates `dn ?? objectGuid.ToString()` and surfaces the SPN, but the trustee SID is raw with no `sam_account_name` join. Parity with SEC-021 / SEC-100 / SEC-101 / SEC-120 / SEC-121 / SEC-122 / SEC-123 / SEC-124.
4. `[IMP-PARITY-TEST]` — No per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-126. Cross-cutting.
5. `[IMP-CTX-RULEID]` — `CreateDelegationFinding` does not stamp `rule_id` into `ContextJson` (unlike `CreateEdgeFinding`). Same parity gap as SEC-122. Cross-cutting.
6. `[IMP-SPN-PARSE]` — `FindFirstServiceSpn` returns the *first* matching SPN, not necessarily the most security-relevant (e.g., a benign `HOST/…` would mask a more interesting `MSSQLSvc/…`). Catalog wording stays accurate, but operator triage benefits from selecting the highest-signal SPN. Same gap as SEC-012.
7. `[IMP-DISABLED-FILTER]` — Disabled privileged service accounts still fire. Cross-cutting decision: should disabled accounts surface here or be deferred to a hygiene rule? Same gap as SEC-022 / SEC-023 / SEC-077 / SEC-101.
8. `[IMP-PRIV-PROV]` — The catalog claim ties this to "Tier-0 service account" intuitively, but the evaluator simply checks `IsPrivilegedPrincipal`. Provenance of the privileged classification (well-known RID vs. closure membership) is not in `ContextJson`, even though `ClassifyPrincipal` already computes it for edge findings. Parity with SEC-003 / SEC-004 / SEC-005 / SEC-006.
9. `[IMP-CAT-WORDING]` — Catalog says "is Kerberoastable"; the SQL approximates Kerberoastable as "has any SPN" plus the post-filter "has a service-prefix SPN". Cipher / encryption-type filtering (RC4 vs. AES-only) is not considered. Make the catalog phrasing more precise or add cipher filtering. Cross-cutting.

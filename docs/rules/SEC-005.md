## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-005
  name: "Unexpected Principal can Write Owner on Admin"
  description: >-
    A principal can take ownership of privileged accounts.
  severity: Critical
  category: PrivilegeEscalation
  remediation: >-
    Remove WriteOwner permission unless the delegation is explicitly required and documented.
  mitre: T1222.001
  tags: ["ownership-takeover", "tier-zero"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 47–56.

## 2. Intended detection (plain English)

A finding must be raised for every captured `WriteOwner` (WRITE_OWNER) right whose source principal is **not** a well-known admin/system principal **and** whose target is a principal that is **membership-confirmed privileged** (transitively in Domain Admins, Enterprise Admins, Schema Admins, Administrators, Account/Server/Print/Backup Operators, Replicators, Group Policy Creator Owners, or one of the built-in admin groups). A stale `adminCount=1` is not sufficient — the target must actually appear in `fact_group_membership_closure` under a privileged group, or be a well-known admin RID itself. `WriteOwner` is the canonical takeover primitive (an owner can always rewrite the DACL via `WRITE_DAC` implicit grant), so the rule is intentionally aggressive about firing on broad-SID sources as well.

### 3.1 Effective SQL (from `EvaluateControlEdgeOnAdminTarget`)

```sql
SELECT e.source_sid, e.target_object_guid, o.distinguished_name, e.edge_id, o.sid AS target_sid
FROM fact_control_edge e
INNER JOIN dim_object o ON e.target_object_guid = o.object_guid
WHERE e.control_type = $type AND e.deny_cancelled = 0
ORDER BY e.source_sid, e.target_object_guid
```

`$type` is bound to `ControlType.WriteOwner.ToString()` → `"WriteOwner"`.

### 3.2 Post-SQL filters (in C#)

1. **Admin source skip** — `IsAdminSid(source_sid)` true → row skipped (`RuleEvaluatorHelpers.cs:649`).
2. **Target SID required** — rows where `o.sid IS NULL` are skipped (`RuleEvaluatorHelpers.cs:651-652`).
3. **Target must be privileged** — `IsPrivilegedPrincipal(targetSid, context.PrivilegedSids)` must be true. `IsPrivilegedPrincipal` is true when `IsAdminSid(targetSid)` is true **or** when the SID is in the membership-derived set produced by `BuildPrivilegedSidSet`.

### 3.3 Privileged SID set composition

`BuildPrivilegedSidSet` (`FindingsService.cs:357-399`) populates the set from:

- `fact_group_membership_closure` rows whose `group_sid` ends in one of RIDs `{512, 516, 518, 519, 526, 527}` — Domain Admins, Domain Controllers, Schema Admins, Enterprise Admins, Group Policy Creator Owners, Enterprise Read-only DCs.
- Exact built-in admin SIDs `S-1-5-32-544`, `S-1-5-32-548`, `S-1-5-32-549`, `S-1-5-32-550`, `S-1-5-32-551` (Administrators, Account/Server/Print/Backup Operators).
- All of `RuleEvaluatorHelpers.PrivilegedSystemSids` (SYSTEM, Enterprise DCs, Creator Owner, Self, plus the BUILTIN operator groups).

When the closure table is absent the set falls back to the exact built-ins plus system SIDs only.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Deny-cancelled edges | `WHERE e.deny_cancelled = 0` | The right is not effective; flagging it would be a false positive. |
| Well-known admin RIDs as source | `IsAdminSid` via RID check (500, 502, 512, 516, 518, 519, 520, 521, 526, 527) | These principals are expected to hold high-privilege ACEs on admins. |
| Well-known system SIDs as source (`S-1-5-18`, `S-1-5-9`, `S-1-3-0`, `S-1-5-10`, BUILTIN operator groups) | `IsAdminSid` via `PrivilegedSystemSids` | Expected built-ins. |
| Targets with `sid IS NULL` | C# null-check before privileged-principal test | A target without a SID (e.g., container) cannot be a privileged principal. |
| Non-privileged targets | `IsPrivilegedPrincipal(targetSid, context.PrivilegedSids)` must be true | Rule scope is admin-target only; non-admin WriteOwner edges are covered by SEC-060 (broad SIDs) and SEC-201 (domain root). |
| Stale `adminCount=1` only | Target is privileged **only** via group membership closure, not via the `AdminCount` delegation | Avoids false positives from orphaned `adminCount` left after AdminSDHolder propagation. |

Not excluded (intentionally subject to review):

- **Broad principals** (`Everyone`, `Authenticated Users`, `Anonymous`) as the source — `IsAdminSid` returns `false` for these, so they **will** fire SEC-005. SEC-060 also covers broad SIDs; the duplication is acceptable because SEC-005 carries higher signal for an admin target.
- **Privileged-by-membership** principals as the source (non-RID admins who are transitively in DA/EA) — `IsAdminSid` does not consult `PrivilegedSids`, so a custom admin SID transitively in Domain Admins still fires SEC-005 against another DA member. Documented; see §12.
- **Creator Owner of the target** — There is no `WriteOwner`-only exemption for the original creator. If a non-admin somehow holds `WriteOwner` on a privileged target, the rule fires regardless of how the ACE came to exist. Intentional — `WriteOwner` is itself the takeover primitive.

| E6 | Target SID present but not in closure (e.g., manually-elevated principal flagged only by `adminCount`) | Not flagged; SEC-005 trusts closure-derived membership only. By design — N7 covers this. |
| E7 | Broad SID (`Everyone`/`AuthUsers`) source | Fires under SEC-005 and SEC-060. Intentional duplication. P4 covers this. |
| E8 | Privileged-by-membership (transitive DA) non-RID source SID | Fires. Different from a strict tier-zero filter; intentional — see §12 (`[IMP-PRIV-MEMB-SRC]`). |

Since the domain object's SID is the domain SID (which is not in `PrivilegedSids`), SEC-005 typically does not fire here, leaving SEC-201 as the canonical signal. |
| E11 | `WriteOwner` companion of an existing `WriteDacl` edge | Each control type produces its own SEC-00x finding (SEC-004 + SEC-005). Intentional — they describe distinct ACE bits and remediations. |

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-005"`
- `Severity == Severity.Critical`
- `SubjectSid` = source principal SID from `fact_control_edge.source_sid`
- `TargetKind == "object_guid"`
- `TargetId` = target object GUID string (`D` format)
- `SourceEdgeId` = `fact_control_edge.edge_id` (non-null when capture stored it)
- `FindingKey == "SEC-005|{SubjectSid}|{TargetId}"`
- `Detail` contains substring `"WriteOwner"`, the target DN (or GUID fallback), and the phrase `"Review whether this explicit delegation is required."`
- `ContextJson` is non-null and contains:
  - `"rule_id": "SEC-005"`
  - `"control_type": "WriteOwner"`
  - `"evidence_type": "control_edge"`
  - `"source_admin_classification"` ∈ {`NonPrivileged`, `BroadPrincipal`, `PrivilegedByMembership`}
  - `"target_dn"` matches the target object's DN

## 12. Defects / deferred items

> Improvement tags follow the taxonomy in `docs/rules/IMPROVEMENTS.md`.

1. `[IMP-DEL-OBJ]` **`is_deleted` not filtered.** A `WriteOwner` edge on a deleted (tombstoned) admin object would still fire. **Status: accepted-with-known-limitation.** Capture upstream is expected to skip tombstoned objects; if a deleted admin is captured at all, surfacing the finding is preferable to silent suppression. Re-open if real-world false positives appear.
2. `[IMP-DN-ENRICH]` **`Detail` does not include source or target display name.** Only SIDs and the target DN are rendered. **Status: accepted-with-known-limitation.** `ContextJson.source_admin_classification` plus the SIDs are sufficient for downstream UI/reporting to enrich; no change required at the evaluator layer.
3. `[IMP-PRIV-MEMB-SRC]` **Privileged-by-membership not excluded as source** (see E8). Behaviour differs from a strict tier-zero source filter. **Status: accepted-with-known-limitation.** Intentional — a non-RID identity transitively in DA performing `WriteOwner` on another DA member is still suspicious enough to warrant explicit attention; aligning with a stricter filter would suppress real signal. Documented; no change.
4. `[IMP-PRIV-PROV]` **No privileged-group provenance in `ContextJson`.** `Detail` currently says "Principal {sid} has WriteOwner on privileged object {dn}". The "privileged" qualifier is asserted but the *reason* (which admin group the target belongs to) is not surfaced in `Detail` or `ContextJson`. **Status: deferred improvement.** Capturing the matched privileged group SID(s) in `ContextJson` (e.g., `target_privileged_via: ["S-1-5-21-...-512"]`) would make the finding self-explanatory; this requires extending `EvaluateControlEdgeOnAdminTarget` and the `PrivilegedSids` context to carry provenance. Not gating verification. Identical to SEC-003 §12.4 and SEC-004 §12.4.

## 13. Improvement suggestions (not blocking)

> Improvement tags follow the taxonomy in `docs/rules/IMPROVEMENTS.md`.

These are recorded for future iteration and were **not** applied as part of this verification pass:

1. `[IMP-PRIV-PROV]` **Carry privileged-group provenance into `ContextJson`.** See deferred item 4. Would require `RuleEvaluationContext.PrivilegedSidProvenance` (member SID → list of matched group SIDs) and a new `extraContext` payload from `EvaluateControlEdgeOnAdminTarget`. Shared with SEC-003 §13.1 and SEC-004 §13.1; a single change would resolve all three rules at once.
2. `[IMP-CAT-WORDING]` **Tighten catalog wording.** The current description is "A principal can take ownership of privileged accounts." A more specific phrasing — "A non-administrative principal holds WriteOwner (WRITE_OWNER) on an account that is transitively a member of a privileged group (Domain Admins, Enterprise Admins, Administrators, etc.); the principal can rewrite the owner SID and then grant itself any further right via the implicit owner DACL write." — better matches the evaluator and explains why this is the canonical takeover primitive.
3. `[IMP-PARITY-TEST]` **Add a parity test for SEC-005 severity/category.** `RuleCatalogParityTests` should assert that `SEC-005` resolves to `Severity.Critical` and category `PrivilegeEscalation`; if such an assertion already exists generically, no change is required.
4. `[IMP-PRIV-MEMB-SRC]` **Consider classifying the source via `ClassifyPrincipal` and downgrading severity** when the source itself is privileged-by-membership but not a well-known admin RID — surfaces the finding without overstating severity. Requires UX agreement before changing severity semantics.

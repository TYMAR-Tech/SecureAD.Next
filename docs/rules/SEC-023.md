## 2. Intended detection (plain English)

A finding must be raised when an account that has the `DONT_REQUIRE_PREAUTH`
(`0x400000`) bit set in `userAccountControl` is **privileged** in the sense
that `RuleEvaluatorHelpers.IsPrivilegedPrincipal` accepts it. AS-REP
roasting on a privileged account is materially worse than the SEC-022 case
because the recovered hash directly compromises a tier-zero credential.
The catalog claim is the same wording as SEC-022 with the word
"**privileged**" inserted; the evaluator differs from SEC-022 only by the
post-SQL privileged-membership gate. There is no krbtgt exclusion, no
class filter, and no `Disabled` filter — these are
the same deferred items as SEC-022 (Â§12). (`is_deleted = 0` is applied at
SQL level on both rules.)

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid
FROM dim_delegation asrep
INNER JOIN dim_object o ON asrep.object_guid = o.object_guid
WHERE asrep.delegation_type = 'ASREPRoastable'
  AND o.is_deleted = 0
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

- `if (sid is null || !RuleEvaluatorHelpers.IsPrivilegedPrincipal(sid, context.PrivilegedSids)) continue;`
  is the **only** post-SQL filter. Every other implicit exclusion from
  SEC-022 (class, krbtgt, disabled, deleted) is still absent here.
- `IsPrivilegedPrincipal(sid, privilegedSids)` returns true when either
  `IsAdminSid(sid)` matches (RID 500 / 502 / 512 / 519, etc.) or
  `privilegedSids.Contains(sid)` matches the SID set built by
  `BuildPrivilegedSidSet`. The SID set is sourced from
  `fact_group_membership_closure` joined to `PrivilegedGroupExactSids`
  plus the well-known privileged-group SIDs themselves and a small set
  of system SIDs. Stale `adminCount = 1` alone is not sufficient — the
  closure row must exist (parity with SEC-021).
- The catalog wording "**Excludes krbtgt, computer accounts, and
  gMSA/managed service accounts**" present on SEC-021 is **not** present
  on SEC-023, and the evaluator does not enforce any of those exclusions.
  RID 502 (krbtgt) is in `AdminRids`, so `IsAdminSid` returns true and the
  privileged gate **accepts** krbtgt as privileged — `[IMP-KRBTGT-FILTER]`.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Accounts without the `DONT_REQUIRE_PREAUTH` UAC bit | Capture-side gate in `WriteDelegations` | The row is never written, so the join finds nothing. Same gate as SEC-022. |
| Null `sid` | Post-SQL gate: `sid is null \|\| !IsPrivilegedPrincipal(...)` | A null SID cannot be matched against the privileged-SID set; the finding cannot be attributed to a principal. SEC-022 still fires for the null-SID case (with `SubjectSid == ""`); SEC-023 does not. |
| Non-privileged principals | Post-SQL gate: `!IsPrivilegedPrincipal(...)` | The privileged-SID set is built from `fact_group_membership_closure` plus well-known privileged groups, system SIDs, and `IsAdminSid` RID matches. A regular user fails the gate and fires only SEC-022. |
| (Implicit, not enforced by code) krbtgt | _none_ | RID 502 is in `AdminRids`, so the privileged gate **accepts** krbtgt. A tampered capture setting the UAC bit on krbtgt surfaces SEC-023 at Critical. `[IMP-KRBTGT-FILTER]` in Â§12. |
| (Implicit, not enforced by code) Computer / gMSA / MSA / group | _none_ | No `object_class` filter. If a non-user object_class were both privileged-by-membership and had this UAC bit, SEC-023 would fire. `[IMP-TGT-CLASS]` in Â§12. |
| Disabled accounts (`ACCOUNTDISABLE` bit) | `NotDisabledSql("o")` in the SQL | Disabled accounts cannot complete AS-REQ â†’ AS-REP, so the attack vector is non-viable; excluded. `[IMP-DISABLED-FILTER]` (resolved) in Â§12. |
| Tombstoned (`is_deleted = 1`) | SQL `o.is_deleted = 0` | A deleted user cannot be roasted. `[IMP-DEL-OBJ]` resolved on this rule. Verified by `WhenAsrepRoastablePrivilegedUserIsDeleted_ThenSEC023DoesNotFire`. |

Not excluded (intentionally subject to review): everything above except the
single capture-side UAC gate and the privileged-membership gate. SEC-023 is
operationally narrower than SEC-022 because of the privileged gate, but it
inherits all the same deferred exclusions plus a krbtgt-specific concern
that does not affect SEC-022 in practice (a typical capture does not set
the UAC bit on krbtgt, but if it did, SEC-023 would fire at Critical and
SEC-022 would only fire at Medium).

## 12. Defects / deferred items

1. `[IMP-KRBTGT-FILTER]` — **Resolved on rule.** SEC-023 now calls
   `IsKrbtgtSid` immediately after the SID read in
   `EvaluateAsrepRoastablePrivileged`, mirroring the SEC-020 / SEC-021
   pattern and matching the same fix applied to SEC-022. A krbtgt row with
   `DONT_REQUIRE_PREAUTH` no longer surfaces a Critical finding, closing
   what was previously the most dangerous noise path in the SEC-02x family.
   Pinned by the flipped regression
   `WhenAsrepRoastablePrivilegedUserIsKrbtgt_ThenSEC023DoesNotFire`.

2. `[IMP-TGT-CLASS]` — SEC-023 SQL has **no** `object_class` filter. In
   practice the privileged gate filters most non-user classes (computers
   and gMSAs are not in the privileged-SID set under normal AD config),
   but a tampered capture or a misconfigured environment with a computer
   account in DA could fire SEC-023 on a non-user object. Suggested
   resolution: add `AND o.object_class = 'user'` to the SQL. Apply
   identically to SEC-022.

3. `[IMP-DISABLED-FILTER]` - **RESOLVED.** Disabled privileged accounts are
   now excluded via `NotDisabledSql("o")` in the SQL, since the KDC will not
   service their AS-REQs. The former `*_StillFiresKnownLimitation` pin was
   flipped to `WhenAsrepRoastablePrivilegedUserIsDisabled_ThenSEC023DoesNotFire`.
   Same tag as SEC-020 / SEC-021 / SEC-022.



4. `[IMP-DEL-OBJ]` — Resolved. SQL now filters `o.is_deleted = 0`; a
   tombstoned privileged user with a stale `ASREPRoastable` row no longer
   fires. Same fix applied to SEC-020/021/022.

5. `[IMP-DUP-RULE]` — SEC-022 (Medium) and SEC-023 (Critical) fire on the
   same row when the user is privileged. Same partitioning concern as
   SEC-020/SEC-021 (Â§12.4 of those cards). Resolution requires a
   product-level decision to either collapse with severity tiering via
   `ClassifyPrincipal` or scope SEC-022 to non-privileged only.

6. `[IMP-PRIV-MEMB-SRC]` — The privileged-SID set is sourced from
   `fact_group_membership_closure` joined to `PrivilegedGroupExactSids`
   plus `IsAdminSid` RID matches. Cross-domain privileged accounts whose
   closure row was not captured (e.g., enterprise-tier principals in a
   foreign forest) will not satisfy the gate even though they are
   semantically privileged. Same tag as SEC-021.

7. `[IMP-PRIV-PROV]` — `ContextJson` carries `delegation_type` and
   `object_dn` but not the **reason** the principal is considered
   privileged (matched RID, matched group SID, etc.). Without
   provenance, an analyst cannot tell whether the finding came from a
   tier-zero closure or from a stale RID-500 alias.

8. `[IMP-DN-ENRICH]` — `Detail`/`ContextJson` carry `object_dn` but no
   `sam_account_name` or display name; cross-domain SIDs are opaque
   without enrichment. Same tag as SEC-022.

9. `[IMP-PARITY-TEST]` — No per-rule severity / MITRE / tag parity
   assertion exists for SEC-023 in `RuleCatalogParityTests`. Adding one
   (`Severity == Critical`, `mitre == "T1558.004"`, tags `{ "kerberos",
   "asrep-roasting", "tier-zero" }`) would prevent silent catalog edits.

10. `[IMP-CAT-WORDING]` — The catalog claim for SEC-023 says "a
    privileged account" without listing the same explicit exclusions
    SEC-021 carries ("Excludes krbtgt, computer accounts, and
    gMSA/managed service accounts"). Either bring the SEC-023 wording
    into line with SEC-021 **and** add the corresponding filters, or
    explicitly document that SEC-023 is deliberately broader than
    SEC-021. The current wording is technically accurate given the
    looseness of the evaluator, but the asymmetry with SEC-021 is the
    kind of drift `[IMP-CAT-WORDING]` exists to surface.

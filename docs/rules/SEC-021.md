```yaml
- id: SEC-021
  name: "Kerberoastable Privileged Account"
  description: >-
    A privileged account (confirmed via group membership in DA, EA, SA, Administrators, or other protected groups) has a recognized Windows service SPN set. Excludes krbtgt, computer accounts, and gMSA/managed service accounts.
  severity: Critical
  category: CredentialTheft
  remediation: >-
    Remove SPN from privileged accounts or use managed service accounts.
  mitre: T1558.003
  tags: ["kerberos", "kerberoasting", "tier-zero"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 135–144.

## 2. Intended detection (plain English)

A finding must be raised for every captured **user account that is confirmed
privileged** (member of Domain Admins, Enterprise Admins, Schema Admins,
Administrators, or another protected group) **and** has at least one
`servicePrincipalName` value whose prefix matches a recognised Windows service
(e.g., `HTTP/`, `MSSQLSvc/`, `CIFS/`, …). Such accounts are Tier-0 Kerberoasting
targets: anyone with valid domain credentials can request a TGS ticket for the
SPN and offline-crack it to recover a domain-admin password. Excluded:
`krbtgt`, computer accounts, gMSA, and MSA — same rationale as SEC-020,
plus the privileged-membership gate.

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid,
       GROUP_CONCAT(spn.target, '|') AS spns
FROM dim_delegation spn
INNER JOIN dim_object o ON spn.object_guid = o.object_guid
WHERE spn.delegation_type = 'SPN'
  AND o.object_class = 'user'
  AND o.is_deleted = 0
GROUP BY o.object_guid, o.distinguished_name, o.sid
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

- `IsKrbtgtSid(sid)` — drops the row when the SID ends in `-502` (RID-based).
- `sid is null || !IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — drops
  the row when the SID is missing OR the principal is not confirmed
  privileged. `IsPrivilegedPrincipal` short-circuits to `IsAdminSid` (well-known
  admin RIDs 500, 502, 512, 516, 518, 519, 520, 521, 526, 527 plus
  `PrivilegedSystemSids`) and otherwise consults the precomputed
  `PrivilegedSids` set built by `FindingsService.BuildPrivilegedSidSet` from
  the `fact_group_membership_closure` table.
- `FindFirstServiceSpn(spns) is null` — drops the row when **none** of the
  SPNs returned by `GROUP_CONCAT(spn.target, '|')` start with a prefix in
  `RuleEvaluatorHelpers.ServiceSpnPrefixes`.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| RID-502 (`krbtgt`) | `IsKrbtgtSid` post-SQL filter (evaluated **before** `IsPrivilegedPrincipal`) | KDC's own service account; not an attacker-targetable account. The filter is RID-based, not name-based. Although `IsAdminSid(502)` returns true, `IsKrbtgtSid` runs first and shortcuts the row. |
| Non-privileged principals | `IsPrivilegedPrincipal(sid, context.PrivilegedSids)` returning `false` | SEC-021 is the privileged tier of SEC-020. A regular service account still fires SEC-020 (Medium); SEC-021 is reserved for confirmed Tier-0 principals. |
| Null `sid` | `sid is null` short-circuit | Cannot be matched against `PrivilegedSids`; would otherwise be coerced to `""` and never appear in the set. |
| Computer accounts | SQL `o.object_class = 'user'` | Same rationale as SEC-020 Â§5: machine-account passwords are 120-char random and rotated; Kerberoasting is not economical. |
| Group / OU / built-in objects | SQL `o.object_class = 'user'` | Cannot have a usable Kerberos password to crack. |
| gMSA (`msDS-GroupManagedServiceAccount`) | SQL `o.object_class = 'user'` (indirect via `ExtractMostSpecificClass`) | gMSA passwords are 240-byte random; structural class returned by the capture path is `msDS-GroupManagedServiceAccount`, not `user`. Same `[IMP-TGT-CLASS]` caveat as SEC-020. |
| MSA (`msDS-ManagedServiceAccount`) | SQL `o.object_class = 'user'` (indirect) | Same reasoning as gMSA. |
| Non-service-prefix SPNs | `FindFirstServiceSpn` returning `null` | A privileged account with only custom-prefix SPNs (e.g., `MyCustomApp/...`) is filtered out — those SPNs are not Kerberoastable in the operationally meaningful sense the rule targets. Note: this is **stricter** than SEC-020, which fires on any SPN. |

Not excluded (intentionally subject to review):

- **Disabled privileged accounts (UAC bit `0x2`)** — filtered by
  `NotDisabledSql("o")` in the SQL. The KDC refuses to issue a TGS for a
  disabled account, so the vector does not exist; excluded.
  `[IMP-DISABLED-FILTER]` resolved. Verified by
  `WhenKerberoastablePrivilegedUserIsDisabled_ThenSEC021DoesNotFire`.
- **`is_deleted = 1` tombstoned users** — filtered by SQL (`AND o.is_deleted = 0`).
  `[IMP-DEL-OBJ]` resolved on this rule. Verified by `WhenKerberoastablePrivilegedUserIsDeleted_ThenSEC021DoesNotFire`.
- **Privileged-by-membership vs. well-known admin parity** — both pathways
  produce the same Critical finding without telling the operator which gate
  fired (no `provenance` / `privileged_via` field in `ContextJson`).
  `[IMP-PRIV-PROV]`.

## 12. Defects / deferred items

1. `[IMP-TGT-CLASS]` — Inherits SEC-020 Â§12.1 verbatim: gMSA/MSA exclusion is
   **indirect** via `object_class = 'user'` and depends on
   `LdapAttributeHelper.ExtractMostSpecificClass` returning the structural
   class. If the capture pipeline ever surfaces the inherited `user` class,
   every gMSA/MSA will start firing SEC-021 — and at Critical, not Medium.
   Suggested resolution: same as SEC-020 (explicit `NOT IN
   ('msDS-GroupManagedServiceAccount', 'msDS-ManagedServiceAccount')` or a
   `sam_account_type` predicate).

2. `[IMP-DISABLED-FILTER]` — **RESOLVED.** Disabled privileged accounts are
   now excluded via `NotDisabledSql("o")` in the SQL, since the KDC will not
   issue a TGS for them. The former `*_StillFiresKnownLimitation` pin was
   flipped to `WhenKerberoastablePrivilegedUserIsDisabled_ThenSEC021DoesNotFire`.

3. `[IMP-DEL-OBJ]` — Resolved. SQL now filters `o.is_deleted = 0`; a
   tombstoned privileged user with a stale SPN row no longer fires.

4. `[IMP-DUP-RULE]` — SEC-020 (Medium) and SEC-021 (Critical) fire on the same
   row when the user is both privileged AND has a service-prefix SPN. Two
   findings per Tier-0 principal complicates remediation triage. Resolution
   requires a product-level decision: collapse-with-severity-tiering (let
   `ClassifyPrincipal` raise SEC-020 to Critical when the source is
   privileged, retire SEC-021) **or** scope SEC-020 to non-privileged users
   only. Either path is acceptable; the current state is intentional but
   verbose. Same tag also referenced by SEC-010/SEC-011/SEC-013/SEC-020.

5. `[IMP-PRIV-PROV]` — `ContextJson` does not record **why** the account was
   deemed privileged (RID 500 vs. closure-derived DA membership vs. transitive
   BUILTIN\Administrators). Operators cannot triage without a separate query.
   Suggested resolution: thread `PrivilegedSidProvenance` (member SID â†’ list
   of matched group SIDs) into `RuleEvaluationContext` and emit a
   `privileged_via` array in `ContextJson`. Applies equally to SEC-003/004/005
   /006/013/014/021/023.

6. `[IMP-DN-ENRICH]` — `Detail`/`ContextJson` carry the user's `object_dn` but
   no `sam_account_name` or human-readable display name. Cross-domain SIDs
   are particularly opaque without enrichment.

7. `[IMP-PARITY-TEST]` — No per-rule severity / MITRE / tag parity assertion
   exists for SEC-021 in `RuleCatalogParityTests`. Adding one
   (`Severity == Critical`, `mitre == "T1558.003"`, tags `{ "kerberos",
   "kerberoasting", "tier-zero" }`) would prevent silent catalog edits and
   would also catch a future severity collapse in the `[IMP-DUP-RULE]`
   resolution.

8. `[IMP-CAT-WORDING]` — The catalog `description` says "*a privileged
   account … has a recognized Windows service SPN set*" but does **not**
   make explicit that:
   - the privileged-membership gate is closure-based (transitive),
   - well-known admin RIDs (500, 502, 512, 516, 518, 519, 520, 521, 526, 527)
     also satisfy the gate without closure evidence,
   - the SPN must use a prefix in `ServiceSpnPrefixes`,
   - `krbtgt` is excluded by RID, not by name.
   Tightening the wording prevents future drift between the catalog and the
   evaluator and aligns SEC-021 with SEC-020 Â§12.8.

9. `[IMP-PRIV-MEMB-SRC]` — `BuildPrivilegedSidSet` seeds from
   `fact_group_membership_closure` AND from `PrivilegedSystemSids`/exact group
   SIDs. The exact-SID fallback when the closure table is missing only adds
   the **groups**, not their members; in that fallback mode SEC-021 will miss
   every privileged-by-membership principal silently. The behaviour matches
   other privileged-aware rules (SEC-003 / 004 / 005 / 006), so this is
   collected here under the shared tag rather than as a SEC-021-specific
   defect.

## 13. Improvement suggestions (not blocking)

1. `[IMP-DUP-RULE]` — Highest-leverage clean-up for the Kerberos rule family.
   Consolidating SEC-020 + SEC-021 into a single rule whose severity is tuned
   by `ClassifyPrincipal` would eliminate the duplicate-finding problem and
   would let `[IMP-DISABLED-FILTER]` / `[IMP-DEL-OBJ]` be fixed once instead
   of in both evaluators.

2. `[IMP-PRIV-PROV]` — Threading provenance through `RuleEvaluationContext`
   unblocks remediation tooling for SEC-021, SEC-023, and every existing
   privileged-aware ACL rule.

3. `[IMP-PARITY-TEST]` — Worth applying to the full SEC-02x family in a single
   pass (`SEC-020`, `SEC-021`, `SEC-022`, `SEC-023`, `SEC-024`, `SEC-025`,
   `SEC-026`) rather than per rule.

## 2. Intended detection (plain English)

> Written from §1 only. Compared against §3 below.

Fire when an Active Directory account that is privileged (well-known admin RID or transitive membership in a privileged group) is currently disabled (UAC `ACCOUNTDISABLE` bit set). The built-in `krbtgt` account is excluded because it is intentionally disabled by AD design.

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid
FROM dim_delegation dis
INNER JOIN dim_object o ON dis.object_guid = o.object_guid
WHERE dis.delegation_type = 'Disabled'
ORDER BY o.sid, o.object_guid
```

Notes:

- `dim_delegation.delegation_type = 'Disabled'` is the upstream signal that `userAccountControl & 0x2 (ACCOUNTDISABLE) != 0`. `DirectObjectWriter` inserts this row when the UAC bit is set.
- The SQL has no SID-based exclusions (no `LIKE '%-502'` for krbtgt). Both the privilege filter and krbtgt exclusion are post-SQL in C#.
- `o.sid` is **not** explicitly guarded against NULL in the SQL, but the post-SQL `sid is null` check handles it.

### 3.2 Post-SQL filters (in C#)

For every row returned by the SQL:

1. **Subject privilege check** (line 174):  
   `if (sid is null || !RuleEvaluatorHelpers.IsPrivilegedPrincipal(sid, context.PrivilegedSids)) continue;`  
   - `IsPrivilegedPrincipal` returns `true` when the SID is a well-known admin RID (via `IsAdminSid`) **or** when the SID appears in `context.PrivilegedSids` (built from `fact_group_membership_closure` by `FindingsService.BuildPrivilegedSidSet`).
   - Unprivileged disabled accounts are silently skipped.

2. **krbtgt exclusion** (line 175):  
   `if (RuleEvaluatorHelpers.IsKrbtgtSid(sid)) continue;`  
   - `IsKrbtgtSid` matches any SID whose last RID is `502`. The well-known krbtgt account is the only AD object using RID 502, so this is precise.
   - Note: SEC-022/SEC-023 (AS-REP Roastable family) do not call `IsKrbtgtSid` post-SQL — see cross-cutting `[IMP-KRBTGT-FILTER]` in `IMPROVEMENTS.md`.

3. **Always emit** the finding if both checks pass.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Object without a Disabled delegation row | SQL `delegation_type = 'Disabled'` | The Disabled marker is emitted only when UAC `ACCOUNTDISABLE` is set; absence means the account is enabled. |
| NULL `sid` | Post-SQL `sid is null` | An object without a captured SID cannot be classified as privileged. |
| Non-privileged subject | Post-SQL `!IsPrivilegedPrincipal(sid, context.PrivilegedSids)` | The rule's scope is privileged accounts. Disabled regular users are not in scope. |
| krbtgt account (RID 502) | Post-SQL `IsKrbtgtSid(sid)` | krbtgt is intentionally disabled by AD design and would always fire otherwise. |

Not excluded (intentionally subject to review):

- **Deleted objects (`is_deleted = 1`)**. The SQL does not filter tombstones. A privileged tombstoned account with a Disabled delegation row will fire. `[IMP-DEL-OBJ]` in §13.
- **Trust accounts (`InterdomainTrustAccount`, RID range 502-equivalent)**. Inter-domain trust accounts may be disabled by design but are still privileged. SEC-032 does not currently exclude them. Not pinned because it requires a product decision; deferred.
- **Computer accounts**. A disabled computer account that holds a privileged RID would fire. No special handling.

| # | Scenario | Resolution |
| --- | --- | --- |
| E1 | Deny ACE / `deny_cancelled = 1` | N/A — SEC-032 does not consult ACEs. |
| E2 | Inherited ACE | N/A — SEC-032 does not consult ACEs. |
| E3 | Deleted target object (`is_deleted = 1`) | Not filtered. A privileged tombstone with a Disabled delegation row would fire. `[IMP-DEL-OBJ]` in §13. |
| E4 | Multiple matching edges for same (sid, target) | N/A — SEC-032 does not use edges. `dim_delegation` PK is `(object_guid, delegation_type, target)` and the `Disabled` row is inserted with `target=''`, so at most one row per object. |

| E6 | Cross-domain principal | Subject is identified by SID. Cross-domain privileged accounts work the same way (RID-based detection + closure membership). |
| E7 | Broad SID (`Everyone`, `Authenticated Users`, `Anonymous`) | N/A — broad SIDs are never `dim_object` subjects with a `Disabled` delegation. |
| E8 | Privileged-by-membership (transitive DA/EA) non-RID SID | Included via `context.PrivilegedSids`. Pinned by P5 `WhenDisabledAccountIsPrivilegedByClosureMembership_ThenSEC032Fires`. |
| E9 | NULL `sid` on `dim_object` | Excluded by post-SQL `sid is null` guard. Pinned by N3. |

| E11 | `FindingKey` collision risk | `FindingKey = "SEC-032\|{subjectSid}\|{objectGuid}"`. The `dim_delegation` PK guarantees one Disabled row per object, so each object produces exactly one SEC-032 finding. No collisions. |
| E12 | Disabled inter-domain trust account | Not filtered. Trust accounts with `InterdomainTrustAccount` UAC are sometimes disabled by design; SEC-032 will fire if they hold a privileged RID. Documented in §5; not pinned. |
| E13 | `privileged_membership_observed` in `ContextJson` is always `true` | The literal `true` is emitted unconditionally. It does **not** reflect whether evidence came from RID or closure membership. `[IMP-PRIV-PROV]` in §13. |

## 9. Output assertions (`Detail` and `ContextJson`)

For a disabled privileged account (e.g., Domain Admins group with `userAccountControl & ACCOUNTDISABLE` set), the finding must include:

- `RuleId == "SEC-032"`
- `Severity == Low`
- `TargetKind == "object_guid"`
- `TargetId == objectGuid` (D-formatted)
- `SubjectSid == sid` (the privileged account's SID)
- `SourceEdgeId is null` (delegation finding)
- `SourcePathId is null`
- `FindingKey == "SEC-032|{subjectSid}|{objectGuid}"`
- `Detail` contains: `"Disabled privileged account: "` followed by the object DN or GUID.
- `ContextJson` keys:
  - `evidence_type` = `"account_hygiene"`
  - `condition` = `"DisabledPrivilegedAccount"`
  - `object_dn` = the DN (string, may be `null` if DN is `null` in `dim_object`)
  - `object_sid` = the subject SID (string)
  - `disabled` = `true`
  - `privileged_membership_observed` = `true` (literal — see E13)
  - `object_guid` = the GUID (D-formatted string)

`ContextJson` does **not** carry a top-level `"rule_id"` field — same `[IMP-CTX-RULEID]` shape as SEC-026, SEC-030, SEC-031. Captured in §12.

## 12. Defects / deferred items

1. `[IMP-CTX-RULEID]` — **Accepted-with-known-limitation.**  
   `ContextJson` produced by `CreateDelegationFinding` does not embed a top-level `"rule_id"` field. Same shape issue as documented in SEC-026, SEC-030, SEC-031 cards.

2. `[IMP-DEL-OBJ]` — **Accepted-with-known-limitation.**  
   SQL does not filter `is_deleted = 1`. Tombstoned privileged accounts with stale Disabled delegation still fire. Deferred to the cross-cutting `[IMP-DEL-OBJ]` workstream.

3. `[IMP-DN-ENRICH]` — **Accepted-with-known-limitation.**  
   `Detail` and `ContextJson` carry DN and SID but no `sAMAccountName` / `display_name`. Operators identifying which account to remediate typically search by `sAMAccountName`. Deferred to the cross-cutting `[IMP-DN-ENRICH]` workstream.

4. `[IMP-PRIV-PROV]` — **Accepted-with-known-limitation.**  
   `ContextJson["privileged_membership_observed"]` is emitted as literal `true` without distinguishing whether the subject is privileged via well-known RID (no closure required) or via closure-based transitive membership (`context.PrivilegedSids`). Operators have no provenance for which group(s) grant privilege. Deferred to the cross-cutting `[IMP-PRIV-PROV]` workstream.

5. `[IMP-PARITY-TEST]` — **Accepted-with-known-limitation.**  
   No per-rule severity / category / tag parity assertion exists for SEC-032 in `RuleCatalogParityTests`. Deferred to the cross-cutting `[IMP-PARITY-TEST]` workstream.

## 13. Improvement suggestions (not blocking)

1. `[IMP-DEL-OBJ]` — Add `AND o.is_deleted = 0` to the SQL to filter tombstones. See §12.2.

2. `[IMP-DN-ENRICH]` — Include `sam_account_name` in `Detail` and `ContextJson` so operators can identify the account without opening SQLite. See §12.3.

3. `[IMP-PRIV-PROV]` — Replace the literal `privileged_membership_observed = true` with provenance (e.g., a list of privileged group SIDs that the subject belongs to via closure, or a discriminator showing "well-known RID" vs "transitive closure"). See §12.4.

4. `[IMP-CTX-RULEID]` — Add a top-level `"rule_id"` field to `ContextJson` for delegation findings. See §12.1.

5. `[IMP-PARITY-TEST]` — Add explicit severity / category parity assertions for SEC-032. See §12.5.

6. **Disabled trust-account handling** — Inter-domain trust accounts (UAC `InterdomainTrustAccount`) that are disabled may be intentional. A future enhancement could distinguish "Disabled by AD design" (krbtgt, possibly trust accounts) from "Disabled by administrator action." No tag because the resolution is product-level. See §5 not-excluded list.

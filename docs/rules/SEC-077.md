## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-077
  name: "Path to Unconstrained Delegation Host"
  description: >-
    A non-administrative principal has a privilege escalation path to a host with unconstrained Kerberos delegation. Compromising this host allows capturing TGTs from any authenticating service, including Domain Controllers.
  severity: High
  category: PrivilegeEscalation
  remediation: >-
    Remove unconstrained delegation from the target host or break the escalation path. Migrate to constrained or resource-based delegation.
  mitre: T1558.003
  tags: ["escalation-path", "tier-zero-shadow", "unconstrained-delegation"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 390–399.

## 2. Intended detection (plain English)

Fire one finding per escalation-path row in `fact_escalation_path`
whose target principal is classified as `Tier0Shadow` **because**
that principal is a host that holds the `TRUSTED_FOR_DELEGATION`
(`0x80000`) `userAccountControl` bit — i.e., the target is configured
for unconstrained Kerberos delegation. Domain Controllers are out of
scope (the same UAC bit always rides with `SERVER_TRUST_ACCOUNT`,
`0x2000`); the rule is meant for non-DC hosts and service accounts
that have been (mis)configured for unconstrained delegation.

The rule is the unconstrained-delegation-specialised sibling of
SEC-072 (any Tier 0 Shadow target, `High`) — SEC-077 also surfaces at
`High`, distinguishing the finding for triage rather than escalating
severity. SEC-076 (DCSync, `Critical`) is the other reason-routed
sibling.

Source-principal exclusion: well-known admin RIDs and well-known
privileged system SIDs (`IsAdminSid`). Broad SIDs (`Everyone`,
`Authenticated Users`, `Anonymous`) are intentionally not treated as
admins and a path from those to an unconstrained-delegation host must
still surface.

No path-length bound — any `path_length >= 1` qualifies.

### 3.1 Effective SQL (copied from code)

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name,
       att.reason AS tier_reason
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
INNER JOIN dim_asset_tier att ON p.target_sid = att.sid
WHERE att.tier = $tier
  AND att.reason LIKE $reasonPattern
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $tier = 'Tier0Shadow'
-- $reasonPattern = '%unconstrained delegation%'
```

Upstream classifier SQL (`LoadUnconstrainedDelegation`):

```sql
SELECT sid FROM dim_object
WHERE sid IS NOT NULL
  AND object_class IN ('computer', 'user')
  AND user_account_control IS NOT NULL
  AND (CAST(user_account_control AS INTEGER) & 524288) != 0  -- TRUSTED_FOR_DELEGATION
  AND (CAST(user_account_control AS INTEGER) & 8192) = 0     -- NOT SERVER_TRUST_ACCOUNT (excludes DCs)
```

### 3.2 Post-SQL filters (in C#)

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Targets not classified `Tier0Shadow` | `WHERE att.tier = 'Tier0Shadow'` (`INNER JOIN` discards untagged rows) | A path to a Tier 0 / Tier 1 / Custom target is SEC-070..074's territory. |
| Tier 0 Shadow targets without an unconstrained-delegation reason | `AND att.reason LIKE '%unconstrained delegation%'` | SEC-077 is the unconstrained-delegation-specialised sibling of SEC-072; non-unconstrained-delegation shadow targets surface as SEC-072 (or, for DCSync, as SEC-076) only. |
| Domain Controllers as targets | Classifier SQL: `AND (CAST(user_account_control AS INTEGER) & 8192) = 0` | DCs always carry `TRUSTED_FOR_DELEGATION`; without the `SERVER_TRUST_ACCOUNT` carve-out every DC in the forest would generate noise. |
| Objects of class other than `computer` / `user` | Classifier SQL: `AND object_class IN ('computer', 'user')` | The UAC bit is only meaningful for security principals. |
| Targets without a captured `user_account_control` | Classifier SQL: `AND user_account_control IS NOT NULL` (plus try/catch around `SqliteException` for older schemas missing the column) | Pre-capture / pre-schema environments cannot evaluate the bit. |
| Admin sources | Post-SQL `IsAdminSid(sourceSid) → continue` | A path from a well-known admin RID is normal admin lateral movement. |
| Broad SIDs not excluded | `IsAdminSid` explicitly returns `false` for `BroadSids` (line 80) | A broad-SID path to an unconstrained-delegation host is still a `High` SEC-077 finding by design. |

Not excluded (intentionally subject to review):

- `coverage_complete = 0` rows — the per-row flag flows through
  `CreatePathFinding` to `FindingV2.CoverageComplete`.
- Deleted (`is_deleted = 1`) source / target — `dim_object` is not
  joined by the evaluator and `LoadUnconstrainedDelegation` does not
  filter on `is_deleted`. Cross-cutting `[IMP-DEL-OBJ]`.
- Disabled targets (UAC `ACCOUNTDISABLE` = `0x2`) — the classifier
  flags any host with `TRUSTED_FOR_DELEGATION` regardless of whether
  the account is disabled. A disabled unconstrained-delegation host
  is still a misconfiguration, but the live exploitation vector is
  gated by KDC behaviour. Cross-cutting `[IMP-DISABLED-FILTER]`.
- Cross-domain paths — surface as-is.
- SEC-072 + SEC-077 dual firing — by design (SEC-072 is the broad
  shadow bucket, SEC-077 the unconstrained-delegation specialisation;
  both surface at `High`). See §12.1 `[IMP-DUP-RULE]`.
- Read-only Domain Controllers (RODCs) — RODCs carry
  `PARTIAL_SECRETS_ACCOUNT` (`0x4000000`) but they also carry
  `SERVER_TRUST_ACCOUNT` (`0x2000`), so they are excluded as DCs by
  the same carve-out. Pinned by the DC-exclusion test in §10.

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Classifier reason routing — RESOLVED at SEC-076.** Prior to the
   SEC-076 fix, `DerivedAssetTierClassifier` wrote the generic reason
   `"Derived Tier 0 Shadow"` to `dim_asset_tier.reason`, so the SEC-077
   `LIKE '%unconstrained delegation%'` filter never matched and the
   rule was effectively dead in production. The SEC-076 refactor
   replaced the `HashSet<string>` of shadow SIDs with a
   `Dictionary<string, string>` keyed on SID and storing a per-cause
   reason; `LoadUnconstrainedDelegation` now writes
   `ReasonUnconstrainedDelegation = "Unconstrained delegation host"`,
   which contains the SEC-077 trigger substring. No further code
   change is required for SEC-077; this entry is retained for
   historical context.

2. **SEC-072 + SEC-077 dual firing** `[IMP-DUP-RULE]` — a path to an
   unconstrained-delegation Tier 0 Shadow target produces both a
   SEC-072 `High` finding (any Tier 0 Shadow) and a SEC-077 `High`
   finding (unconstrained-delegation specialisation). Both fire
   simultaneously and per path because the two evaluator code paths
   are independent. Unlike SEC-076 (`Critical`) vs SEC-072 (`High`),
   the duplication here is at the same severity, so the second
   finding adds triage cost without surfacing additional severity
   signal. UI / triage must dedupe by (subject, target). Resolution
   requires a product-level decision on whether the
   unconstrained-delegation specialisation should suppress the broad
   SEC-072 row or keep both as separate evidence.

3. **DC exclusion mechanic differs from SEC-010 / SEC-011 / SEC-012**
   `[IMP-DC-DETECT]` — SEC-077's classifier carves out DCs via the
   `SERVER_TRUST_ACCOUNT` UAC bit, which is the *correct*
   implementation. SEC-010 / SEC-011 / SEC-012 carve out DCs via a
   `distinguished_name LIKE '%OU=Domain Controllers%'` heuristic
   instead. A DC moved out of the default OU evades SEC-010 / SEC-011
   but is correctly excluded by SEC-077; a non-DC computer placed
   under that OU is incorrectly excluded by SEC-010 / SEC-011 but
   correctly included by SEC-077. SEC-077 is the reference
   implementation for the cross-cutting fix; this entry is retained
   to document the desired direction of alignment.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-DN-ENRICH]` — `Detail` and `ContextJson` carry SIDs and
   `dim_principal.display_name` only. For an unconstrained-delegation
   host the most actionable identifier is the computer's DNS host
   name or DN, neither of which is joined from `dim_object`. Adding
   `LEFT JOIN dim_object ON p.target_sid = dim_object.sid` and
   surfacing the DN alongside the SID would make the finding
   directly remediation-actionable without opening SQLite.

2. `[IMP-DEL-OBJ]` — neither `EvaluateByTierReason` nor
   `LoadUnconstrainedDelegation` filter `is_deleted = 1`. A
   tombstoned computer object that retained
   `TRUSTED_FOR_DELEGATION` at deletion time still surfaces. The
   capture pipeline should drop deleted objects upstream, but a
   defence-in-depth `AND o.is_deleted = 0` filter in the classifier
   would make the rule robust to capture-time drift.

3. `[IMP-PARITY-TEST]` — `RuleCatalogParityTests` does not assert
   that SEC-077's `Severity`, `Category`, `Mitre`, and `Tags` from
   `rules.yaml` match `BuiltInRules.ById["SEC-077"]` (or vice
   versa). Adding a per-rule parity row for SEC-077 (mirroring the
   SEC-076 row) would pin the catalog claim at build time. Same
   cross-cutting need as SEC-076.

4. `[IMP-CTX-RULEID]` — `PathFindingContext` already embeds
   `rule_id` through `CreatePathFinding`, so SEC-077 itself satisfies
   the cross-cutting goal. Retained on the rolling backlog only
   because the same cross-cutting fix is still pending for the
   delegation-finding family (SEC-026, SEC-030, SEC-031, SEC-032,
   SEC-061, SEC-062). No SEC-077-local action.

5. `[IMP-REASON-DRIFT]` — SEC-077 routing depends on the substring
   `"unconstrained delegation"` matching between
   `DerivedAssetTierClassifier.ReasonUnconstrainedDelegation` and
   the evaluator's `LIKE` pattern. The two sides are kept in sync by
   convention only — a future reword of the classifier reason
   constant silently breaks SEC-077 in production. Resolution: see
   the `[IMP-REASON-DRIFT]` row in `IMPROVEMENTS.md` (either
   structured `classification_cause` column or shared constants).
   Same cross-cutting need as SEC-076.

6. `[IMP-DISABLED-FILTER]` — `LoadUnconstrainedDelegation` does not
   exclude accounts carrying `ACCOUNTDISABLE` (UAC `0x2`). A
   disabled service account configured for unconstrained delegation
   is a misconfiguration worth surfacing but is not a live
   exploitation path. Resolution would tier severity (or add a
   `coverage_reason` carve-out) per the cross-cutting
   `[IMP-DISABLED-FILTER]` fix.

7. `[IMP-DC-DETECT]` — SEC-077 is the reference implementation for
   the cross-cutting "use UAC bit, not OU DN" fix. Already covered
   in §12.3; retained here for completeness against the rolling
   backlog.

8. `[IMP-DELEGATION-SOURCE]` — **new tag.** Unconstrained-delegation
   evidence is captured twice: `DirectObjectWriter.WriteDelegations`
   writes a `dim_delegation` row with
   `delegation_type = 'Unconstrained'` (consumed by SEC-010 /
   SEC-011), while the escalation-path classifier
   `DerivedAssetTierClassifier.LoadUnconstrainedDelegation` reads
   `dim_object.user_account_control` directly (consumed by SEC-077).
   Both ultimately derive from the same UAC bit
   (`TRUSTED_FOR_DELEGATION` = `0x80000`), but a partial capture or a
   future writer change that touches one path silently desyncs the
   other. Concrete example: gMSAs (`object_class =
   'msDS-GroupManagedServiceAccount'`) carrying
   `TRUSTED_FOR_DELEGATION` are captured into `dim_delegation`
   (SEC-010 / SEC-011 fire) but **not** classified into
   `dim_asset_tier` (SEC-077 silently misses). Resolution: pick a
   single source of truth — either route SEC-077 through
   `dim_delegation` so the family agrees, or have all three rules
   read UAC directly. The first option keeps capture-time
   normalisation; the second simplifies storage.

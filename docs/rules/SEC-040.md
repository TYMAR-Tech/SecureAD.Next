## 2. Intended detection (plain English)

> Written from §1 only. Compared against §3 below.

Fire when an unexpected (non-admin) principal holds the `Certificate-Enrollment` extended right on an Active Directory Certificate Services (AD CS) object. The catalog description says *"on a CA"*, but the remediation says *"Review certificate template enrollment permissions"* — so the rule conceptually covers both `pKIEnrollmentService` (CA) and `pKICertificateTemplate` objects. See §3 for the actual code-level scope, which does **not** restrict the target object class.

### 3.1 Effective SQL (copied from generic `EvaluateControlEdgeRule`)

```sql
SELECT e.source_sid, e.target_object_guid, o.distinguished_name, e.edge_id, e.control_type
FROM fact_control_edge e
INNER JOIN dim_object o ON e.target_object_guid = o.object_guid
WHERE e.control_type IN ($type0) AND e.deny_cancelled = 0
ORDER BY e.source_sid, e.target_object_guid, e.control_type
```

with `$type0 = 'CertificateEnroll'`.

Notes:

- The SQL has **no** target-class filter. Any object (CA, template, OU, container, user, etc.) holding a `CertificateEnroll` edge can match.
- `deny_cancelled = 0` excludes edges that an allow-then-deny ACL sequence cancelled.
- `o.sid` is not referenced; the join is used only to surface the DN.

### 3.2 Post-SQL filters (in C#)

For every row returned by the SQL:

1. **Admin exclusion** (line 640):  
   `if (excludeAdmins && IsAdminSid(sid)) continue;` — SEC-040 is dispatched with `excludeAdmins: true`.  
   - `IsAdminSid` returns `true` for SIDs in `PrivilegedSystemSids` (SYSTEM, Enterprise DCs, BUILTIN\Administrators, Account Ops, etc.) and for SIDs whose last RID is in `AdminRids` `{500, 502, 512, 516, 518, 519, 520, 521, 526, 527}`. **`IsAdminSid` does not consult `context.PrivilegedSids` (closure membership).** Transitive privilege via group membership is not enough to be excluded by `IsAdminSid`.
   - Broad SIDs (`Everyone S-1-1-0`, `Authenticated Users S-1-5-11`, `Anonymous S-1-5-7`) are explicitly **not** admins and therefore **not** excluded — they will still produce SEC-040 findings.

2. **Always emit** the finding if the admin check passes. `IsAdminSid` is the only post-SQL filter.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Edge with `deny_cancelled = 1` | SQL `deny_cancelled = 0` | Allow ACE was cancelled by an effective deny; the trustee no longer has the right. |
| Edge whose `control_type` is not `CertificateEnroll` | SQL `control_type IN ('CertificateEnroll')` | The rule scope is enrollment, not auto-enrollment (`CertificateAutoEnroll` is SEC-041 territory) or generic control. |
| Subject is a well-known admin RID | Post-SQL `IsAdminSid(sid)` | Admins are expected to be able to enroll; the rule targets "unexpected" principals. |
| Subject is a well-known privileged system SID | Post-SQL `IsAdminSid(sid)` via `PrivilegedSystemSids` | SYSTEM, Enterprise DCs, BUILTIN\Administrators, BUILTIN\Account/Server/Print/Backup Operators are expected to hold this right. |

Not excluded (intentionally subject to review):

- **Broad principals** (`Everyone`, `Authenticated Users`, `Anonymous`). `IsAdminSid` returns `false` for `BroadSids`. These are usually the highest-value SEC-040 hits.
- **Target object class**. The SQL fires on **any** object holding `CertificateEnroll`, including objects that are neither CAs nor templates. AD typically only sets this right on `pKIEnrollmentService` (CA) and `pKICertificateTemplate`, but a misclassified or test-only object could fire. `[IMP-TGT-CLASS]` in §13.
- **Deleted objects (`is_deleted = 1`)**. SQL does not filter tombstones. `[IMP-DEL-OBJ]` in §13.
- **Privileged-by-membership subjects** (transitive Domain Admin via nested groups). These are excluded by `IsAdminSid` only if the SID *itself* has an admin RID; transitive privilege via `context.PrivilegedSids` is **not** consulted. `[IMP-PRIV-MEMB-SRC]` in §13.

## 9. Output assertions (`Detail` and `ContextJson`)

For a non-admin subject with a `CertificateEnroll` edge to a CA or template, the finding must include:

- `RuleId == "SEC-040"`
- `Severity == Medium`
- `TargetKind == "object_guid"`
- `TargetId == targetGuid` (D-formatted)
- `SubjectSid == sid`
- `SourceEdgeId != null` (matches `fact_control_edge.edge_id`)
- `SourcePathId is null`
- `FindingKey == "SEC-040|{subjectSid}|{targetGuid}"`
- `Detail == "Principal {sid} has CertificateEnroll on {targetDn ?? targetGuid}"` (literal format from `EvaluateControlEdgeRule`).
- `ContextJson` keys (from `EdgeFindingContext` + snake_case naming):
  - `rule_id` = `"SEC-040"`
  - `source_sid` = the subject SID
  - `target_guid` = the GUID
  - `target_dn` = the DN (string, may be `null`)
  - `control_type` = `"CertificateEnroll"`
  - `edge_id` = the integer edge id (or `null`)
  - `evidence_type` = `"control_edge"`
  - `source_admin_classification` = `"NonPrivileged"` / `"BroadPrincipal"` / `"PrivilegedByMembership"` / etc.
  - `source_is_well_known_admin` = `false` (otherwise the finding would not have been emitted)
  - `source_is_privileged_by_membership` = `true` if subject is in `context.PrivilegedSids`
  - `source_is_broad_principal` = `true` for `S-1-1-0` / `S-1-5-11` / `S-1-5-7` / `S-1-5-32-545` / RID `513`

## 12. Defects / deferred items

1. `[IMP-TGT-CLASS]` — **RESOLVED.**  
   The SQL now constrains `o.object_class IN ('pKIEnrollmentService', 'pKICertificateTemplate')` (passed as `targetFilter` to `EvaluateControlEdgeRule`), so a stray `CertificateEnroll` edge against any other class no longer fires. Pinned by `WhenCertificateEnrollEdgeTargetsNonCaObject_ThenSEC040DoesNotFire`; the positives `WhenNonAdminPrincipalHasCertificateEnrollEdge_ThenSEC040Fires` (CA) and `WhenCertificateEnrollEdgeTargetsCertTemplate_ThenSEC040Fires` (template) remain green.

2. `[IMP-DEL-OBJ]` — **Accepted-with-known-limitation.**  
   SQL does not filter `o.is_deleted = 0`. Tombstoned CAs/templates with leftover `CertificateEnroll` edges would fire. Deferred.

3. `[IMP-PRIV-MEMB-SRC]` — **Accepted-with-known-limitation.**  
   `excludeAdmins` uses `IsAdminSid`, which does not consult `context.PrivilegedSids`. A subject privileged only via transitive group membership (closure) is treated as a non-admin and will produce SEC-040 findings. Same cross-cutting issue documented in earlier rules. Deferred.

4. `[IMP-KEY-COLLAPSE]` — **Accepted-with-known-limitation.**  
   Multiple `CertificateEnroll` edges for the same `(subjectSid, targetGuid)` (e.g., direct + inherited, or from different ACE sources) collapse to one finding by `FindingKey`. Provenance for the non-winning edges is lost. Deferred.

5. `[IMP-DN-ENRICH]` — **Accepted-with-known-limitation.**  
   `Detail` and `ContextJson` carry the subject SID and target DN but not the subject's `sAMAccountName` or the target's friendly name. Deferred.

6. `[IMP-PARITY-TEST]` — **Accepted-with-known-limitation.**  
   No per-rule severity / category / tag parity assertion exists for SEC-040 in `RuleCatalogParityTests`. Deferred.

## 13. Improvement suggestions (not blocking)

1. `[IMP-TGT-CLASS]` — Restrict the SQL (or add a post-filter) so SEC-040 only fires on `pKIEnrollmentService` and `pKICertificateTemplate` objects. The current behavior could surface false positives on misclassified objects. See §12.1.

2. `[IMP-DEL-OBJ]` — Add `AND o.is_deleted = 0` to the SQL. See §12.2.

3. `[IMP-PRIV-MEMB-SRC]` — Extend `excludeAdmins` to use a richer privilege predicate (e.g., `IsAdminSid(sid) || privilegedSids.Contains(sid)`). This will also fix similar gaps in SEC-014, SEC-021, SEC-023, SEC-024, SEC-025, etc. See §12.3.

4. `[IMP-KEY-COLLAPSE]` — Either widen `FindingKey` to include `controlType + sourceKind`, or emit one finding per `(subject, target, source)` with a `provenance` list in `ContextJson`. See §12.4.

5. `[IMP-DN-ENRICH]` — Add `sam_account_name` and a short target description (e.g., the CN or template-display-name) to `Detail`. See §12.5.

6. `[IMP-PARITY-TEST]` — Add explicit severity / category parity assertions for SEC-040 in `RuleCatalogParityTests`. See §12.6.

7. **Catalog wording** — The description says *"on a CA"* but the rule also fires on certificate templates (which is the typical AD CS attack surface). Consider revising to *"on a CA or certificate template"* to match the actual scope. No tag because it's a documentation-only nit; resolved by `[IMP-TGT-CLASS]` if the code is tightened to CA-only, or by a YAML edit otherwise.

## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-131
  name: "Privileged Account with Delegation Enabled"
  description: >-
    A privileged account (confirmed via group membership) has TrustedForDelegation (unconstrained delegation) enabled, allowing credential theft via Kerberos ticket forwarding.
  severity: High
  category: Delegation
  remediation: >-
    Disable unconstrained delegation on privileged accounts. Use constrained delegation or RBCD instead.
  mitre: T1558.001
  tags: ["delegation", "unconstrained", "privileged", "credential-theft"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 555–564.

## 2. Intended detection (plain English)

Fire one High finding per `(privileged subject, target object_guid)` pair when a non-computer account is **privileged** (well-known admin SID/RID **or** transitively a member of a Tier-0 group) **and** has `userAccountControl.TrustedForDelegation` (unconstrained delegation) enabled. Such accounts cache forwarded TGTs at any service they receive, which lets a compromise of the service host extract DA tickets — the classic unconstrained-delegation credential-theft vector.

Computer accounts are excluded because Domain Controllers always carry `TrustedForDelegation` by design and member-server unconstrained delegation is a separate workflow (covered, when shipped, under SEC-014 / future computer-side rules). Tombstoned accounts are excluded because lingering attribute rows on a deleted object cannot be exploited in the current state.

### 3.1 Effective SQL (copied from code)

```sql
SELECT DISTINCT o.object_guid, o.distinguished_name, o.sid, o.object_class
FROM dim_delegation ud
INNER JOIN dim_object o ON ud.object_guid = o.object_guid
WHERE ud.delegation_type = 'Unconstrained'
  AND o.object_class != 'computer'
  AND o.is_deleted = 0
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

- `sid is null || !IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — drops non-privileged subjects (only well-known admin RIDs **or** transitively privileged-by-membership subjects fire). The SID-null fail-closed guard mirrors SEC-126.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Objects without `Unconstrained` | SQL `ud.delegation_type = 'Unconstrained'` | The rule's whole premise is the unconstrained-delegation flag; constrained / RBCD are scoped to other rules. |
| Computer accounts | SQL `o.object_class != 'computer'` | DCs carry `TrustedForDelegation` by design; member-server unconstrained delegation is the SEC-014 family's domain. The catalog scopes SEC-131 to user-shaped privileged identities. |
| Tombstoned targets | SQL `o.is_deleted = 0` | Deleted accounts cannot accept forwarded TGTs; lingering rows are noise. |
| Non-privileged subjects | C# `IsPrivilegedPrincipal(sid, context.PrivilegedSids)` | The catalog explicitly scopes the rule to privileged accounts; non-privileged unconstrained delegation surfaces under SEC-014. |
| Subjects with no recorded SID | C# `sid is null` guard | Fail-closed — without a SID we cannot evaluate privileged membership, and a finding without `SubjectSid` would violate `FindingV2` invariants. |

Not excluded (intentionally subject to review):

- gMSA / MSA accounts. Unlike SEC-126 (where the static-password premise specifically excludes managed accounts), SEC-131 keys on the `TrustedForDelegation` flag itself, which is just as dangerous on a gMSA Tier-0 identity. Class filter omitted by design.
- `krbtgt`. Theoretically `krbtgt` could carry the flag in a misconfigured forest; left in scope so the rule fires on this anomaly. Same posture as SEC-022 / SEC-023 reviewed earlier (see `[IMP-KRBTGT-FILTER]` for the cross-cutting decision).

## 8. Edge cases considered

| # | Scenario | Resolution |
| --- | --- | --- |
| E1 | Subject is a `group` class object (e.g. DA group itself) carrying `Unconstrained` | Allowed — class filter only blocks `computer`. Pinned by P2. |
| E2 | Subject is `inetOrgPerson` rather than `user` | Allowed — only `computer` is excluded. |
| E3 | Tombstoned target with stale `Unconstrained` row | Excluded — pinned by N2. |
| E4 | Subject has both `Unconstrained` *and* `Disabled` rows | Currently fires. `[IMP-DISABLED-FILTER]` cross-cutting question. |
| E5 | Subject has `Unconstrained` but no SID at all (highly unusual) | Excluded by `sid is null` guard; prevents an invalid `FindingV2` shape. |
| E6 | Same `(sid, object_guid)` produced by multiple `dim_delegation` `Unconstrained` rows | `SELECT DISTINCT` collapses duplicates pre-filter; `FindingKey = SEC-131|{sid}|{guid}` collapses again at `INSERT OR IGNORE`. |
| E7 | Coverage incomplete for `GroupMembership` | `IsPrivilegedPrincipal` falls back to `IsAdminSid` for well-known RIDs; transitive members fall out — `[IMP-COV-MEMB]`. |
| E8 | Subject is a managed service account (gMSA / MSA) with `Unconstrained` and DA membership | Fires — by design, the `TrustedForDelegation` risk is independent of password rotation. |

## 12. Defects / deferred items

1. **Tombstone gap (resolved on rule).** SQL did not filter `o.is_deleted = 0`, so a stale `Unconstrained` row on a tombstoned privileged user surfaced as a High finding. Same defect class fixed in SEC-122 / SEC-123 / SEC-124 / SEC-126. Fixed inline this session; pinned by `WhenSEC131TargetIsDeleted_ThenSEC131DoesNotFire`. Cross-cutting tracked under `[IMP-DEL-OBJ]`.

## 13. Improvement suggestions (not blocking)

1. `[IMP-DEL-OBJ]` — Resolved on SEC-131. Cross-cutting sweep against the remaining sibling rules in `AdvancedRuleEvaluator` (SEC-201, SEC-204) and `KerberosRuleEvaluator` (SEC-020 / 021 / 022 / 023) is still open — pinned by the existing `*_KnownLimitation` tests on those rules.
2. `[IMP-COV-MEMB]` — `RuleCoverageRequirements["SEC-131"]` does not declare `GroupMembership` even though `IsPrivilegedPrincipal` consumes the closure. Same gap as SEC-025 / SEC-080 / SEC-081 / SEC-090 / SEC-123 / SEC-124 / SEC-126.
3. `[IMP-DN-ENRICH]` — `Detail` interpolates `dn ?? objectGuid.ToString()`. The trustee SID is not surfaced raw in `Detail` (good), but `ContextJson` lacks any `sam_account_name` / display-name enrichment, forcing operators back to LDAP. Parity with SEC-100 / 101 / 102 / 120 / 121 / 122 / 123 / 124 / 126.
4. `[IMP-PARITY-TEST]` — No per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-131. Cross-cutting.
5. `[IMP-CTX-RULEID]` — `CreateDelegationFinding` does not stamp `rule_id` into `ContextJson` (unlike `CreateEdgeFinding`). Same parity gap as SEC-122 / 126. Cross-cutting.
6. `[IMP-PRIV-PROV]` — Provenance of the privileged classification (well-known RID vs. closure membership) is not in `ContextJson`, even though `ClassifyPrincipal` already computes it for edge findings. Parity with SEC-003 / 004 / 005 / 006 / 126.
7. `[IMP-DISABLED-FILTER]` — Disabled privileged accounts with `Unconstrained` still fire. Cross-cutting decision: should disabled accounts surface here or be deferred to a hygiene rule? Same gap as SEC-022 / 023 / 077 / 101 / 126.
8. `[IMP-KRBTGT-FILTER]` — Unlike SEC-126 (which explicitly excludes `krbtgt`), SEC-131 does not. A misconfigured `krbtgt` with `TrustedForDelegation` is genuinely interesting, so leaving it in scope is defensible — but the asymmetry across sibling rules deserves a documented decision. Same gap as SEC-022 / 023.
9. `[IMP-DELEGATION-SOURCE]` _(re-tagged from `[IMP-CTRL-SCOPE]` — this is about delegation-attribute source paths, not control-type ACE equivalence)._ The catalog says "TrustedForDelegation (unconstrained delegation)" but the body of the rule keys only on the resulting `Unconstrained` projection. If a future capture adds finer-grained sources (e.g. `msDS-AllowedToDelegateTo` interpreted as unconstrained when target is `*`), the rule would silently miss them. Consider documenting which UAC bits / attribute paths are considered authoritative. Aligns with the SEC-010 / SEC-011 / SEC-077 delegation-source single-source-of-truth work.

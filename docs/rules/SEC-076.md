## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-076
  name: "Path to DCSync Shadow"
  description: >-
    A non-administrative principal has a privilege escalation path to a principal that holds DCSync rights (GetChanges + GetChangesAll). Compromising this target grants the ability to replicate all domain credentials.
  severity: Critical
  category: PrivilegeEscalation
  remediation: >-
    Remove DCSync rights from the target or break the escalation path.
  mitre: T1003.006
  tags: ["escalation-path", "tier-zero-shadow", "dcsync"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 379–388.

## 2. Intended detection (plain English)

Fire one finding per escalation-path row in `fact_escalation_path`
whose target is a principal classified as `Tier0Shadow` **because**
that principal holds the DCSync replication right pair on the domain
root (`DCSyncGetChanges` + `DCSyncGetChangesAll` against an
`object_class = 'domainDNS'` target). The rule is the
DCSync-specialised sibling of SEC-072 (any Tier 0 Shadow target,
`High`) — it lifts severity to `Critical` to reflect that the
attacker's destination is a credential-replication primitive, not a
generic shadow admin.

The source principal must not itself be a well-known admin
(`IsAdminSid` exclusion: RID 500 / 502 / 512 / 516 / 518 / 519 / 520
/ 521 / 526 / 527 plus the well-known privileged system SIDs).
Broad SIDs (`Everyone`, `Authenticated Users`, `Anonymous`) are
**not** treated as admins and a path from those to a DCSync holder
must still surface.

No path-length bound — any path with `path_length >= 1` qualifies.

### 3.1 Effective SQL (copied from code)

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name,
       att.reason AS tier_reason
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
INNER JOIN dim_asset_tier att ON p.target_sid = att.sid
WHERE att.tier = $tier
  AND att.reason LIKE $reasonPattern
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $tier = 'Tier0Shadow'
-- $reasonPattern = '%DCSync%'
```

### 3.2 Post-SQL filters (in C#)

- `IsAdminSid(sourceSid) → continue` — exclude rows whose source SID is a
  well-known admin (`AdminRids` in `RuleEvaluatorHelpers.cs:27`) or a
  well-known privileged system SID. `BroadSids` are explicitly **not**
  treated as admins.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Targets not classified `Tier0Shadow` | `WHERE att.tier = 'Tier0Shadow'` (`INNER JOIN` discards untagged rows) | A path to a Tier 0 / Tier 1 / Custom target is SEC-070..074's territory. |

| Broad SIDs not excluded | `IsAdminSid` explicitly returns `false` for `BroadSids` (line 80) | A broad-SID path to a DCSync holder is still a `Critical` SEC-076 finding by design. |

Not excluded (intentionally subject to review):

- `coverage_complete = 0` rows — the per-row flag flows through
  `CreatePathFinding` to `FindingV2.CoverageComplete`.
- Deleted (`is_deleted = 1`) source / target — `dim_object` is not
  joined; the path service drops tombstoned principals at capture
  time. Cross-cutting `[IMP-DEL-OBJ]`.
- Cross-domain paths — surface as-is.
- SEC-072 + SEC-076 dual firing — by design (SEC-072 is the broad
  shadow bucket, SEC-076 the DCSync escalation). See §12.1
  `[IMP-DUP-RULE]`.

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **`DerivedAssetTierClassifier` collapsed all per-cause reasons into a
   single hardcoded string** — _resolved this session._ Before this
   audit, every Tier 0 Shadow classification (DCSync, unconstrained
   delegation, RBCD, transitive Tier 0 membership, GPO linked to
   Domain Controllers OU, dangerous control on Tier 0) wrote the
   literal reason `"Derived Tier 0 Shadow"` into
   `dim_asset_tier.reason`. The SEC-076 SQL filter
   (`att.reason LIKE '%DCSync%'`) and the SEC-077 SQL filter
   (`att.reason LIKE '%unconstrained delegation%'`) therefore
   **never matched in production** — both rules were silently dead.
   The defect was masked by the existing tests in
   `EscalationPathTierFindingsTests` which `INSERT INTO
   dim_asset_tier` directly with synthetic reason strings, bypassing
   the classifier. **Fix:** switched the shadow-SID set to
   `Dictionary<string, string>`; each `Load*` method writes the cause-
   specific `ReasonDCSync` / `ReasonUnconstrainedDelegation` /
   etc. constants; `Build()` calls DCSync first and the
   non-DCSync methods use `TryAdd` so the highest-severity routing
   reason wins when a SID is flagged by multiple causes. The DCSync
   loader uses unconditional assignment so it always overrides a
   prior (weaker) reason. Pinned end-to-end by
   `WhenClassifierFlagsDCSyncHolder_ThenSEC076FiresWithCriticalSeverity`
   and at the classifier layer by
   `WhenSidHasDCSyncAndTransitiveDA_ThenDCSyncReasonWins`.

2. **SEC-076 + SEC-072 dual firing** `[IMP-DUP-RULE]` — a path to a
   DCSync holder fires SEC-072 (`High`, every Tier 0 Shadow target)
   **and** SEC-076 (`Critical`, DCSync-specialised). Both findings
   carry the same `(subject, target, path_id)` triple but distinct
   rule ids and severities. The catalog is intentionally tiered this
   way; downstream UI and remediation workflows must dedupe by
   `(subject, target)` and surface the highest severity.
   `Accepted-with-known-limitation`: not a defect, but worth a
   product-level decision. Resolution candidates:
   (a) keep both rules (current), (b) suppress SEC-072 when SEC-076
   covers the same path, (c) demote SEC-076 to a coverage signal and
   tier SEC-072 via the reason field. No code change here.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-DN-ENRICH]` — `Detail` and `ContextJson` carry SIDs and
   `display_name`s for source and target but no `sam_account_name`
   or `domain_fqdn`. Cross-cutting with every rule that joins
   `dim_principal` only on `display_name`.

2. `[IMP-DEL-OBJ]` — `EvaluateByTierReason` does not join `dim_object`
   to filter `is_deleted = 1` sources or targets. Capture-time
   expectation; cross-cutting sweep.

3. `[IMP-PARITY-TEST]` — `RuleCatalogParityTests` does not assert
   per-rule that SEC-076's emitted severity matches the catalog
   default (`Critical`), category is `PrivilegeEscalation`, MITRE id
   is `T1003.006`, or that tags are
   `["escalation-path", "tier-zero-shadow", "dcsync"]`. Generic
   across most rules.

4. `[IMP-CTX-RULEID]` — `PathFindingContext` already embeds
   `rule_id`; verified locally for SEC-076. Tag included for
   cross-cutting completeness with the delegation-finding sweep.

5. `[IMP-REASON-DRIFT]` — **new tag.** SEC-076 / SEC-077 routing
   depends on the SQL `LIKE` filter matching a substring of the
   classifier's reason constant
   (`DerivedAssetTierClassifier.ReasonDCSync` →
   `EvaluateByTierReason("Tier0Shadow", "DCSync")`). The two strings
   are intentionally coupled but not enforced by a shared symbol.
   Resolution: extract the trigger substrings as `internal const`
   on `DerivedAssetTierClassifier` and consume them from both the
   classifier and `EscalationPathRuleEvaluator`, removing the magic
   strings from the evaluator dispatch table.

6. `[IMP-DCSYNC-FILTERED-SET]` — **new tag.** SEC-002 fires on any
   pair from `{GetChanges} × {GetChangesAll, GetChangesInFilteredSet}`,
   but `DerivedAssetTierClassifier.LoadDCSyncHolders` requires the
   `GetChanges + GetChangesAll` pair only. A principal with
   `GetChanges + GetChangesInFilteredSet` (sufficient to replicate a
   filtered attribute set including key material in modern AD) fires
   SEC-002 but is **not** flagged as Tier 0 Shadow, so SEC-076 misses
   it. Resolution: extend the classifier query to match SEC-002's
   `e2.control_type IN ('DCSyncGetChangesAll', 'DCSyncGetChangesInFilteredSet')`.
   Requires a product-level decision on whether the filtered-set
   variant should route through the same `Critical` severity.

7. `[IMP-DC-DETECT]` — `LoadGPOLinkedToDCOU` and `LoadDCSyncHolders`
   indirectly identify DC-adjacent objects via DN substring patterns
   (`OU=Domain Controllers,%`) and `object_class = 'domainDNS'`.
   Cross-cutting with the broader `[IMP-DC-DETECT]` improvement —
   should consume a shared `IsDomainController` / `IsDomainRoot`
   helper if one is introduced.

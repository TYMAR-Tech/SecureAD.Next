## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-070
  name: "Short Path to Tier 0 Target"
  description: >-
    A non-administrative principal has a short (1-2 hop) privilege escalation path to a Tier 0 target (Domain Admins, Enterprise Admins, Schema Admins, krbtgt, Domain Controllers, etc.).
  severity: Critical
  category: PrivilegeEscalation
  remediation: >-
    Break the escalation path by removing one or more control edges. Prioritize the shortest paths first.
  mitre: T1078
  tags: ["escalation-path", "tier-zero", "short-path"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 313–322.

## 2. Intended detection (plain English)

Fire one finding per row in `fact_escalation_path` where:

- the **target** is classified `Tier0` (Domain Admins, Enterprise Admins,
  Schema Admins, krbtgt, Domain Controllers, etc.); and
- the **path length** is short — 1 or 2 hops (`path_length <= 2`); and
- the **source** is not itself a well-known admin principal
  (`IsAdminSid` exclusion).

Tier-0 classification is intended to come from `dim_asset_tier`. When
that table is absent, the evaluator falls back to a RID-based classifier
that recognises a narrower Tier 0 set (RID 512 only); see §12.1 and
`[IMP-FALLBACK-TIER]`.

Severity is fixed at `Critical`; SEC-071 (long path to Tier 0, ≥3 hops)
is the High-severity sibling.

### 3.1 Effective SQL (copied from code)

Primary path (when `dim_asset_tier` exists):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name,
       att.reason AS tier_reason
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
LEFT JOIN dim_asset_tier att ON p.target_sid = att.sid
WHERE COALESCE(att.tier, 'Tier2') = $tier
   AND p.path_length <= $maxLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $tier = 'Tier0', $maxLen = 2
```

Fallback path (when `dim_asset_tier` does not exist):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
WHERE 1 = 1
   AND p.path_length <= $maxLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $maxLen = 2; tier classification then applied per row via ClassifyFallbackTier
```

### 3.2 Post-SQL filters (in C#)

- `IsAdminSid(sourceSid) → skip` — exclude rows whose source SID is a
  well-known admin (RID 500, 502, 512, 516, 518, 519, 520, 521, 526,
  527 — `AdminRids` in `RuleEvaluatorHelpers.cs:27`) or a well-known
  privileged system SID (SYSTEM, Enterprise DCs, BUILTIN\\Administrators
  family — `PrivilegedSystemSids` in `RuleEvaluatorHelpers.cs:46`).
  `BroadSids` are explicitly **not** treated as admins (an
  `Authenticated Users → Tier 0` path correctly surfaces as Critical).
- Fallback path only: `ClassifyFallbackTier(targetSid) != "Tier0" → skip` —
  drops rows whose target RID is not 512 (Domain Admins). RIDs 519, 516
  are routed to other rules; everything else falls to "Custom" (SEC-075).

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Paths to non-Tier-0 targets | `WHERE COALESCE(att.tier, 'Tier2') = 'Tier0'` (primary) / `ClassifyFallbackTier(target) == "Tier0"` (fallback) | SEC-070 is the Tier-0 short-path rule by definition. Tier-1 and "Custom" / unclassified targets are SEC-073 / SEC-075 territory. |
| Long paths (≥3 hops) | `WHERE p.path_length <= 2` | The catalog says "short (1-2 hop)". SEC-071 (long path to Tier 0) handles `path_length >= 3` with `High` severity. |
| Admin sources | Post-SQL `IsAdminSid(sourceSid) → continue` | A path starting from `Domain Admins → Domain Admins` is normal Tier-0 RBAC, not an escalation. The exclusion uses RID + well-known SID matching, never group-membership expansion (see E7). |
| Broad SIDs not excluded | `IsAdminSid` explicitly returns `false` for `BroadSids` (line 80) | An `Authenticated Users → Tier 0` path is a Critical escalation, not noise — must surface. |

Not excluded (intentionally subject to review):

- `coverage_complete = 0` rows — the rule still fires; the
  per-row `coverage_complete` flows through `CreatePathFinding`
  to `FindingV2.CoverageComplete`, and the stamper attaches a
  reason. This is by design: an incomplete-coverage path is still
  actionable evidence of a Tier-0 short path.
- Deleted (`is_deleted = 1`) source / target — `dim_object` is **not**
  joined; the path service is expected to have already filtered
  tombstoned principals at capture time. Not pinned by SEC-070's own
  tests. Tracked cross-cutting under `[IMP-DEL-OBJ]`.
- `path_length = 0` (self-loop / identity path) — possible in theory
  but the path service never emits such rows; not tested explicitly.
- Cross-domain paths — surface as-is. Tier 0 of any domain in the
  forest is in scope; this is the correct cross-cutting behaviour.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-070"`
- `Severity == Critical`
- `SubjectSid` = source principal SID (path source)
- `TargetKind == "sid"`
- `TargetId` = target principal SID (path target — note: SID, not GUID, unlike control-edge rules)
- `SourcePathId` populated (from `fact_escalation_path.path_id`)
- `SourceEdgeId == null`
- `CoverageComplete` = the path's per-row `coverage_complete`
- `FindingKey == "SEC-070|{source_sid}|{target_sid}|{path_id}"`
- `Detail` matches one of:
  - tier-table path: `"{source_name} has {path_length}-hop escalation path to Tier0 target {target_name}{[ (tier_reason)]}: {truncated path_detail}"`
  - fallback path: `"{source_name} has {path_length}-hop escalation path to {fallbackTier} target {target_name}: {truncated path_detail}"`
- `ContextJson` non-null (typed `PathFindingContext`) and contains:
  - `"rule_id": "SEC-070"`
  - `"source_sid"`, `"source_name"`, `"target_sid"`, `"target_name"`
  - `"path_id"`, `"path_length"`, `"coverage_complete"`
  - `"target_tier"` (`"Tier0"` on the primary code path; the fallback
    classifier value on the fallback code path)
  - `"tier_reason"` when supplied by `dim_asset_tier.reason`
  - `"path_detail"`, `"first_actionable_edge_id"`,
    `"first_actionable_edge_summary"`, `"steps"`

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Fallback classifier narrower than the tier table** `[IMP-FALLBACK-TIER]` —
   **RESOLVED.** `EvaluateByFallbackTier` previously called a bespoke
   `ClassifyFallbackTier` that mapped only RID 512 → `Tier0`, 519 →
   `Tier0Shadow`, 516 → `Tier1`, everything else → `Custom` — diverging
   from both the sibling `IsTierZeroFallbackSid` helper and the
   authoritative `StaticAssetTierClassifier`. `ClassifyFallbackTier` now
   delegates to `StaticAssetTierClassifier.Instance.ClassifySid(sid).Tier`,
   so the fallback agrees with the tier-table path: RIDs 500 / 502 / 512 /
   516 / 518 / 519 (and the other well-known Tier-0 groups) classify as
   `Tier0` (fire SEC-070 / SEC-071), and the operator RIDs (548 / 549 / 550 /
   551 / ...) as `Tier1` (fire SEC-073 / SEC-074). The bespoke
   `GetFallbackSeverity` / `IsTierZeroFallbackSid` boost helpers were
   removed — fallback severity now equals the catalog severity, identical
   to the tier-table path. `Tier0Shadow` is intentionally never produced in
   fallback (it is a purely behavioural classification needing
   `dim_asset_tier`), so SEC-072 / SEC-076 / SEC-077 do not fire in fallback;
   likewise SEC-075's `Custom` (policy) targets require the table. The four
   `*_KnownLimitation` pins were flipped to positive
   `WhenFallbackPathTo{Krbtgt,EnterpriseAdmins,SchemaAdmins,BuiltinAdministratorAccount}_ThenSEC070Fires`.

2. **`pathLengthFilter` was overwritten** — `EvaluateByTier` and
   `EvaluateByFallbackTier` originally assigned `pathLengthFilter = …`
   for both bounds, so a future rule supplying both `minPathLength` and
   `maxPathLength` would silently lose the first bound. Fixed in this
   audit to `pathLengthFilter += …` in both methods. No current rule
   passes both bounds, so no behavioural change today; the fix is
   pre-emptive. Resolved — no tag.

   Generic across most rules.

## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-122
  name: "RBCD Configured on Domain Controller"
  description: >-
    A Domain Controller has msDS-AllowedToActOnBehalfOfOtherIdentity configured, enabling resource-based constrained delegation attacks against the DC.
  severity: Critical
  category: Delegation
  remediation: >-
    Remove the msDS-AllowedToActOnBehalfOfOtherIdentity attribute from the Domain Controller.
  mitre: T1558.001
  tags: ["rbcd", "domain-controller", "tier-zero", "delegation"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 511–520.

## 2. Intended detection (plain English)

Fire one Critical finding per Domain Controller computer object that has any `RBCD` row in `dim_delegation`. RBCD on a DC is a documented Tier-0 takeover primitive: any principal listed in `msDS-AllowedToActOnBehalfOfOtherIdentity` can request Kerberos service tickets to the DC as any non-protected user (S4U2Self + S4U2Proxy), enabling DCSync-equivalent compromise. Tombstoned DC computer rows with lingering delegation rows must not fire. Non-DC computers (workstations, member servers, jump boxes) with RBCD are out of scope here — they are covered by SEC-013 (`WriteRBCD`) and SEC-014 patterns. User / managed-service-account objects are out of scope: `msDS-AllowedToActOnBehalfOfOtherIdentity` on a non-computer is malformed data, not the intended target.

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid, d.details
FROM dim_delegation d
INNER JOIN dim_object o ON d.object_guid = o.object_guid
WHERE d.delegation_type = 'RBCD'
  AND o.object_class = 'computer'
  AND o.is_deleted = 0
  AND o.distinguished_name LIKE '%OU=Domain Controllers,%'
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

None. The evaluator emits one finding per row read.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Non-RBCD delegation rows | SQL `d.delegation_type = 'RBCD'` | Constrained (S4U2Proxy on a service principal) and Unconstrained delegation on a DC are tracked by other rules; RBCD is the only delegation type that grants any caller in the trustee set the full S4U primitive. |
| Non-computer objects | SQL `o.object_class = 'computer'` | RBCD only applies to computer accounts; the attribute on any other class is malformed data, not the intended attack surface. |
| Non-DC computers | SQL `LIKE '%OU=Domain Controllers,%'` | Workstation / member-server RBCD is covered by SEC-013 (`WriteRBCD` ACL exposure) and SEC-014 (RBCD-takeover prerequisites). SEC-122 is the Tier-0-specific finding. |
| Deleted target objects | SQL `o.is_deleted = 0` | Tombstoned DC rows can't host an attack. |

Not excluded (intentionally subject to review):

- Multiple `dim_delegation` rows for the same DC. The dedup PK is `(object_guid, delegation_type, target)`, so the same DC can produce multiple rows when `target` differs (one per trustee SID rendered as the row's `target`). The evaluator does not collapse those into a single finding; `FindingKey = SEC-122|{sid}|{guid}` will collapse them at persistence time via the `fact_finding(run_id, finding_key)` dedup. Acceptable — the Detail still names the DC and a representative `details` payload.
- Multi-domain forests. Each domain's `OU=Domain Controllers,DC=…` matches independently; correct, because each DC's RBCD attribute is independently sensitive.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-DC-DETECT]` _(re-tagged from `[IMP-CTRL-SCOPE]` — this is a DC-identification issue, not control-type equivalence)._ DC OU detection keys on the English DN `'%OU=Domain Controllers,%'`. AD does not localize this OU but admins can rename it. Resilient detection would key on the well-known DC OU `object_guid` / a `systemFlags` predicate (`FLAG_DOMAIN_DISALLOW_RENAME` on the default DC OU) or on `userAccountControl & SERVER_TRUST_ACCOUNT`. Parity with SEC-120/SEC-121.
2. `[IMP-DN-ENRICH]` — `Detail` interpolates `dn ?? objectGuid.ToString()`. When `dn` is `NULL`, the operator sees only a GUID, which is unactionable. Parity with SEC-100/101/102/120/121.
3. `[IMP-PARITY-TEST]` — No per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-122. Same gap is open across the audited backlog.
4. `[IMP-CTX-RULEID]` — `CreateDelegationFinding` writes evidence into `ContextJson` but does not stamp `rule_id` inside the JSON body (unlike `CreateEdgeFinding`). Operators reading raw context payloads have to look at the row's `RuleId` separately. Cheap consistency win.
5. `[IMP-MITRE-FIT]` — Catalog maps SEC-122 to `T1558.001` ("Steal or Forge Kerberos Tickets: Golden Ticket"). RBCD-on-DC is closer to `T1558.003` (Kerberoasting variant via S4U) or `T1134.001` (Token Impersonation/Theft via S4U2Self+S4U2Proxy). Same cross-cutting tag as SEC-091/092/100/101/102/120/121.
6. `[IMP-TGT-CLASS]` — `object_class = 'computer'` is correct for DC accounts, but a more defensive predicate would AND with `(userAccountControl & SERVER_TRUST_ACCOUNT) != 0` (UAC 0x2000), which is the actual signal that the computer object is a DC. Today the rule trusts the DN convention alone; the UAC check would be independent of OU naming and would catch DCs moved out of the canonical OU (also a finding worth surfacing — SEC-122-or-sibling decision deferred).

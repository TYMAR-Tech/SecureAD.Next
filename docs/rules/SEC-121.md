## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-121
  name: "Domain Controllers OU Write Access"
  description: >-
    A principal has dangerous rights (GenericAll, GenericWrite, WriteDACL, WriteOwner, ownership control, or CreateChild) on the Domain Controllers OU, enabling computer object injection or permission takeover.
  severity: Critical
  category: PrivilegeEscalation
  remediation: >-
    Remove unnecessary write permissions from the Domain Controllers OU.
  mitre: T1484
  tags: ["domain-controllers", "tier-zero", "ou-control"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 500–509.

## 2. Intended detection (plain English)

Fire one Critical finding per `(non-privileged principal, Domain Controllers OU)` pair when that principal holds `GenericAll`, `GenericWrite`, `WriteDacl`, `WriteOwner`, ownership (`Owns`), or `CreateChild` on the OU itself (`OU=Domain Controllers,DC=…`). These rights enable rogue DC injection (`CreateChild` on `computer` class) or DC OU delegation takeover. Well-known admins and principals that are already privileged-by-membership in tier-0 groups should not fire (they're expected to control DCs by design). Deleted (tombstoned) DC OU rows must not fire even if lingering control-edge rows still join. Computer objects *inside* the DC OU are out of scope for SEC-121 — they're covered by SEC-122 (RBCD on DC) and SEC-204 (spill to Tier-0).

### 3.1 Effective SQL (copied from code)

```sql
SELECT e.source_sid, e.target_object_guid, e.control_type, o.distinguished_name, e.edge_id
FROM fact_control_edge e
INNER JOIN dim_object o ON e.target_object_guid = o.object_guid
WHERE e.deny_cancelled = 0
  AND e.control_type IN ('GenericAll', 'GenericWrite', 'WriteDacl', 'WriteOwner', 'Owns', 'CreateChild')
  AND o.is_deleted = 0
  AND o.distinguished_name LIKE 'OU=Domain Controllers,%'
ORDER BY e.source_sid, e.target_object_guid, e.control_type
```

### 3.2 Post-SQL filters (in C#)

- `RuleEvaluatorHelpers.IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — skips well-known admins (built-in SIDs + admin RIDs from `AdminRids`) **and** principals that are transitive members of the precomputed privileged closure. Broad SIDs (Everyone, Authenticated Users, Anonymous) are *not* skipped — they are the worst-case offenders here.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| `deny_cancelled = 1` edges | SQL `WHERE e.deny_cancelled = 0` | The allow ACE was negated by a stronger deny ACE during edge derivation, so the trustee cannot actually exercise the right. |
| Out-of-scope control types | SQL `IN (...)` filter | Only ownership / full-write / DACL-rewrite primitives — plus `CreateChild` for computer-injection — can compromise the DC OU. Reads, ResetPassword, etc. don't grant the rule's intended attack primitives. |
| Non-DC-OU targets | SQL `LIKE 'OU=Domain Controllers,%'` | The rule is scoped to the DC OU container. Other Tier-0 ACL backdoors are covered by SEC-060/SEC-120/SEC-201/SEC-204. |
| Children of the DC OU | SQL `LIKE 'OU=Domain Controllers,%'` (anchored, no leading `%`) | A computer object at `CN=DC01,OU=Domain Controllers,…` is not the OU itself; rights on the computer are covered by SEC-122/SEC-204. |
| Deleted target objects | SQL `o.is_deleted = 0` | Tombstoned DC OU rows can't be the target of an active attack. |
| Well-known admins | C# `IsPrivilegedPrincipal` (admin RIDs + built-ins) | These principals already control the DC OU by design (RID 500, RID 512, BUILTIN\Administrators, …). |
| Privileged-by-membership | C# `IsPrivilegedPrincipal` (closure-derived) | Custom accounts that are transitive members of tier-0 groups are equivalent to admins; surfacing them as SEC-121 would be a tautology and noise. |

Not excluded (intentionally subject to review):

- Broad SIDs (`Everyone`, `Authenticated Users`, `Anonymous`). These are the canonical worst-case offenders for DC OU takeover and must fire.
- Inherited vs. explicit edges — `fact_control_edge` does not distinguish; if the right reaches the DC OU, it can be exercised.
- Object class — the rule keys on DN alone. See §13 `[IMP-TGT-CLASS]`.
- Multi-domain forests — the SQL matches every `OU=Domain Controllers,DC=…` regardless of domain, which is intentional. Each domain's DC OU is independently sensitive.

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Tombstone gap (resolved on rule).** The SQL did not filter `o.is_deleted = 0`, so lingering control-edge rows against tombstoned DC OU objects would surface as Critical findings. Fixed inline this session by adding `AND o.is_deleted = 0` to the `WHERE` clause; regression pinned by `WhenDeletedDcOuHasWriteDacl_ThenSEC121DoesNotFire`. Cross-cutting sweep against the other sibling rules in `AdvancedRuleEvaluator` (SEC-123, SEC-124, SEC-201) is still open — tracked under `[IMP-DEL-OBJ]`.
2. **Privileged-by-membership exclusion gap (resolved on rule).** The post-SQL filter used `IsAdminSid(sid)`, which only matches well-known admin RIDs and built-in SIDs. A custom account that was a transitive member of Domain Admins via `fact_group_membership_closure` would still fire — a tautological false positive. Fixed inline this session by swapping to `IsPrivilegedPrincipal(sid, context.PrivilegedSids)`; regression pinned by `WhenPrivilegedByMembershipHoldsGenericAllOnDcOu_ThenSEC121DoesNotFire`. Cross-cutting sweep against `AdvancedRuleEvaluator` siblings still open — tracked under `[IMP-PRIV-MEMB-SRC]`.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-TGT-CLASS]` — The rule does not assert `o.object_class = 'organizationalUnit'`. A synthetic / corrupt row whose DN matches but whose class is different would still match. Adding the class predicate makes the rule's intent explicit at the SQL layer.
2. `[IMP-DN-ENRICH]` — `Detail` interpolates `targetDn ?? targetGuid.ToString()`. When `dn` is `NULL`, the operator sees only a GUID, which is unactionable. SEC-100/SEC-101/SEC-102/SEC-120 carry the same `[IMP-DN-ENRICH]` tag; the underlying fix (dim_object enrichment or a derived `dim_object_label` table) would resolve them all together.
3. `[IMP-PARITY-TEST]` — There is no per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-121. Same gap is open across the audited backlog.
4. `[IMP-CTX-RULEID]` — `EdgeFindingContext.RuleId` is duplicated as both the embedded `rule_id` JSON key and as a separate column (`FindingV2.RuleId`). Cheap consistency win across all evaluators emitting `CreateEdgeFinding` — tracked centrally.
5. `[IMP-DC-DETECT]` _(re-tagged from `[IMP-CTRL-SCOPE]` — this is a DC-identification issue, not control-type equivalence; SEC-121 already fires on the full takeover set `GenericAll/GenericWrite/WriteDacl/WriteOwner/Owns/CreateChild`)._ **Status: Accepted-with-known-limitation — robust fix blocked on capture-side work.** The rule keys the DC-OU container on the conventional English DN (`o.distinguished_name LIKE 'OU=Domain Controllers,%'`, anchored at the head). Unlike SEC-122 — which targets the DC *computer account* and already uses the robust `RuleEvaluatorHelpers.IsDomainControllerSql` (UAC `SERVER_TRUST_ACCOUNT` / `primaryGroupID IN (516,521)` / anchored DN) — SEC-121 targets the *OU container*, which has no `userAccountControl` or `primaryGroupID`, so that helper cannot apply. The card's proposed resilient signals (`systemFlags` `FLAG_DOMAIN_DISALLOW_RENAME`, or the well-known DC-OU `object_guid` / `wellKnownObjects`) are **not captured today** — neither `systemFlags` nor `wellKnownObjects` exists in `CapturedAttributeCatalog` / `DerivedStoreSchema`, so the robust fix requires a capture-side attribute addition + re-capture (belongs with the `[IMP-GPO-SYSVOL]`-class infrastructure, not an evaluator tweak). Residual risk is low: AD does not localize the default DC OU (Microsoft documents `OU=Domain Controllers` as fixed), the DN is already head-anchored (no substring leakage), and the only miss is an admin who **renames** the default DC OU — rare and self-inflicted. Accepted until `systemFlags` capture lands.
6. `[IMP-MITRE-FIT]` — Catalog maps SEC-121 to `T1484` (broad "Domain Policy Modification"). A more specific MITRE pin would be `T1484.001` (Group Policy Modification) for `GenericAll` / `WriteDacl` patterns, or `T1078.002` (Domain Accounts) for `CreateChild` enabling rogue DC injection. Same cross-cutting tag as SEC-091/SEC-092/SEC-100/SEC-101/SEC-102/SEC-120.

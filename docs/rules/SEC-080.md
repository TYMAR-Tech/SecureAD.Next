## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-080
  name: "Unexpected Principal can Modify GPO"
  description: >-
    A principal has write, ownership, DACL, or full-control rights over a Group Policy Object. This allows modification of GPO settings affecting any linked scope.
  severity: Critical
  category: ConfigurationHygiene
  remediation: >-
    Remove write permissions on the GPO unless the delegation is explicitly required and documented.
  mitre: T1484.001
  tags: ["gpo", "tier-zero", "configuration"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 401–410.

## 2. Intended detection (plain English)

Surface any principal (other than expected GPO administrators) that holds a control-edge right capable of modifying a Group Policy Object — i.e. `GenericAll`, `GenericWrite`, `WriteDacl`, `WriteOwner`, `Owns`, or `WriteAllProperties` — on an object whose class is `groupPolicyContainer`. Such a principal can rewrite GPO settings (security baselines, scheduled tasks, startup scripts, etc.) and propagate code/configuration to every account or computer that processes a link to that GPO. Severity is `Critical` because GPO modification is a documented Tier 0 escalation vector (MITRE T1484.001 — _Domain or Tenant Policy Modification_).

### 3.1 Effective SQL (copied from code)

```sql
SELECT DISTINCT e.source_sid, e.target_object_guid, gpo.distinguished_name, e.edge_id, e.control_type
FROM fact_control_edge e
INNER JOIN dim_object gpo ON e.target_object_guid = gpo.object_guid
WHERE e.control_type IN ('GenericAll', 'GenericWrite', 'WriteDacl', 'WriteOwner', 'Owns', 'WriteAllProperties')
  AND gpo.object_class = 'groupPolicyContainer'
  AND e.deny_cancelled = 0
ORDER BY e.source_sid, e.target_object_guid
```

### 3.2 Post-SQL filters (in C#)

- `if (RuleEvaluatorHelpers.IsAdminSid(sourceSid)) continue;` — drops well-known admin SIDs (`Domain Admins` RID 512, `Enterprise Admins` RID 519, `SYSTEM` `S-1-5-18`, `Enterprise DCs` `S-1-5-9`, `BUILTIN\Administrators` `S-1-5-32-544`, etc.). Broad principals (`Everyone`, `Authenticated Users`, `Anonymous`) intentionally pass through — see §5.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Non-modify control types | SQL `control_type IN (...)` whitelist | Read / list / extended-right edges do not let a principal rewrite GPO content. Limiting to `GenericAll`, `GenericWrite`, `WriteDacl`, `WriteOwner`, `Owns`, `WriteAllProperties` keeps the rule on actual modify capability. |
| Non-GPO targets | SQL `gpo.object_class = 'groupPolicyContainer'` | SEC-080 is the GPO-specific Critical rule. Modify rights on other classes are handled by the per-class rules (SEC-001..SEC-006 for admin/Tier 0 principals, SEC-024..SEC-026 for class-specific writes, SEC-060 for broad-SID drift, SEC-081 for `LinkGPO`). |
| Cancelled deny ACEs | SQL `e.deny_cancelled = 0` | Edges marked `deny_cancelled = 1` mean an effective-access pass found a deny ACE that neutralises the allow; the principal does not actually hold the right. |
| Well-known admin sources | C# `IsAdminSid(sourceSid)` | Expected GPO administrators (Domain Admins, Enterprise Admins, SYSTEM, Enterprise DCs, BUILTIN\Administrators, Schema Admins, Group Policy Creator Owners RID 520, etc.) writing on a GPO is normal operation, not a misconfiguration. |

Not excluded (intentionally subject to review):

- **Broad principals.** `Everyone` / `Authenticated Users` / `Anonymous` fall through `IsAdminSid` (it returns `false` for `BroadSids`) and surface as SEC-080 findings. This is intentional: broad-SID GPO write access is the canonical "anyone can modify a GPO" misconfiguration, and SEC-060 only covers the generic broad-write case at `High`, not the GPO-specific `Critical` semantic. Pinned in §7 / §8.
- **Privileged-by-membership sources.** A user who transitively reaches Domain Admins (via nested group membership) is **not** excluded — the rule still fires, but `ContextJson.source_admin_classification = "PrivilegedByMembership"` flags the case for downstream tiering. Aligned with SEC-024 / SEC-025; cross-cutting `[IMP-PRIV-MEMB-SRC]`.
- **Deleted GPOs (`is_deleted = 1`).** The SQL does not filter `dim_object.is_deleted`. Same gap as the broader control-edge family — cross-cutting `[IMP-DEL-OBJ]`.
- **GPOs in non-default containers.** The `object_class` filter is the only target predicate; the rule does not require the GPO to live under `CN=Policies,CN=System,DC=…`. Correct — `groupPolicyContainer` instances outside the default container are still legitimate targets.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-080"`
- `Severity == Critical`
- `SubjectSid` = source principal SID
- `TargetKind == "object_guid"`
- `TargetId` = GPO object GUID string (`D` format)
- `SourceEdgeId` populated (control edge provenance)
- `FindingKey == "SEC-080|{SubjectSid}|{TargetId}"`
- `Detail` contains: principal SID, control type, GPO DN (or GUID fallback)
- `ContextJson` non-null and contains:
  - `"rule_id": "SEC-080"`
  - `"source_sid"`, `"target_guid"`, `"target_dn"`, `"control_type"`
  - `"evidence_type": "control_edge"`
  - `"edge_id"` (long)
  - `"source_admin_classification"` ∈ {`"NonPrivileged"`, `"PrivilegedByMembership"`, `"BroadPrincipal"`, `"SystemOrExpectedBuiltIn"`} (the `"WellKnownAdmin"` classification is unreachable here because `IsAdminSid` skipped them upstream)
  - `"source_is_well_known_admin": false`
  - `"source_is_privileged_by_membership"`, `"source_is_broad_principal"` booleans

Pinned by `WhenPrincipalHasWriteDaclOnGpo_ThenSEC080EmitsFullShape`.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`).

1. `[IMP-DEL-OBJ]` — Add `AND gpo.is_deleted = 0` to the evaluator SQL. Without it, a non-admin who held GPO write rights on a tombstoned GPO still surfaces a finding even though the GPO no longer applies. Same family-wide gap tracked from SEC-001 onward.
2. `[IMP-DN-ENRICH]` — `Detail` and `ContextJson` carry the source SID but no display name / SAM account name. A reviewer triaging the finding has to round-trip through `dim_principal` to identify the actor. Join `dim_principal` (or `dim_object` on `sid`) and surface `source_name` next to `source_sid`.
3. `[IMP-PRIV-MEMB-SRC]` — A principal transitively a Domain Admin still fires SEC-080 as `Critical` even though the same write is already covered by SEC-070..SEC-077 escalation-path rules. Decide whether SEC-080 should exclude `source_is_privileged_by_membership = true` (consistent with the admin-source skip) or keep them but tier severity differently. Requires a product-level call; mirrors the SEC-024 / SEC-025 family.
4. `[IMP-PRIV-PROV]` — `ContextJson` exposes `source_is_privileged_by_membership` but no provenance — which privileged group(s) the source reaches. Extend `RuleEvaluationContext.PrivilegedSidProvenance` (per the existing IMP entry) and surface it.
5. `[IMP-KEY-COLLAPSE]` — `FindingKey = "SEC-080|{sourceSid}|{gpoGuid}"` collapses every distinct modify right against the same GPO into one finding. A principal granted both `GenericWrite` **and** `WriteDacl` on the same GPO persists only one row; the `Detail` keeps the first control type the reader saw, the rest is lost. For remediation that wants to enumerate "every right this principal holds on this GPO", consider keying on `(sourceSid, gpoGuid, controlType)` or aggregating control types into a `control_types` array in `ContextJson` before persistence.
6. `[IMP-PARITY-TEST]` — `RuleCatalogParityTests` does not assert SEC-080 severity / category / MITRE / tags. Add an explicit per-rule parity test mirroring the pattern used for SEC-070..SEC-077.
7. `[IMP-CAT-WORDING]` — Catalog `description` says "write, ownership, DACL, or full-control rights". The SQL also includes `WriteAllProperties` (broad write extending beyond DACL/owner) and `Owns` (current owner via security descriptor owner field rather than an `Owns`-named explicit right). Tighten the catalog wording to enumerate all six control types explicitly so the user-facing description matches the evaluator.
8. `[IMP-CTX-RULEID]` — Already satisfied: `CreateEdgeFinding` emits `"rule_id"` in `ContextJson`. No-op for SEC-080; logged so cross-cutting sweep can mark control-edge rules complete.
9. **GPO-specific: `gPCMachineExtensionNames` / `gPCUserExtensionNames` write coverage.** A principal granted write only on the GPO's container is detected; one granted write on the GPO's referenced SYSVOL path (`gPCFileSysPath`) is **not** — SYSVOL ACLs flow through file-system DACLs, which `fact_control_edge` does not model. **Status:** `[IMP-GPO-SYSVOL]` **Resolved (union enrichment).** SYSVOL folder DACLs are now captured into `fact_sysvol_ace` (Phase A) and surfaced as their own Critical finding **SEC-082**. SEC-080 additionally consumes `fact_sysvol_ace` (see §14) to flag, on the directory-object finding, when the same GPO also has a non-admin SYSVOL writer — so a reviewer sees both modify paths in one place. The SYSVOL half is therefore no longer silently missed.

## 14. SYSVOL-DACL union enrichment (`[IMP-GPO-SYSVOL]`)

A GPO can be modified through **two independent paths**: the directory-object ACL on the
`groupPolicyContainer` (this rule's primary vector, via `fact_control_edge`) **or** filesystem
write on the GPO's SYSVOL policy folder (`\\<domain>\SYSVOL\<domain>\Policies\{GUID}`, captured
into `fact_sysvol_ace` and reported in full by **SEC-082**). The two ACLs are managed separately,
so a GPO can have a backdoor on one path while the other looks clean.

To give a complete "who can modify this GPO" picture without duplicating SEC-082, `EvaluateGpoModify`
loads the non-admin SYSVOL writers per GPO (`LoadSysvolWritersByGpo`) and enriches each SEC-080
finding's `ContextJson` when the same GPO has a second modify path:

- `"also_writable_via_sysvol": true`
- `"sysvol_writer_sids": [ ...sorted non-admin trustee SIDs... ]`

Design notes:
- **Additive only.** The fields appear *only* when a non-admin SYSVOL writer exists; the base
  finding shape (§9) is unchanged otherwise (pinned by `WhenGpoHasNoSysvolWriter_ThenSEC080OmitsUnionFields`).
- **Same admin exclusion and write-mask as SEC-082.** Admin trustees (e.g. RID 512) are filtered
  from the writer list (`WhenOnlyAdminHasSysvolWrite_ThenSEC080OmitsUnionFields`); the write mask is
  the shared `SysvolWriteMask` (FILE_WRITE_DATA / WRITE_DAC / WRITE_OWNER / GENERIC_WRITE / GENERIC_ALL),
  AccessAllowed ACE types only.
- **SEC-082 untouched.** It still fires independently for every non-admin SYSVOL writer; the union is
  an enrichment of SEC-080, not a merge. The SYSVOL writer need not be the same principal as the
  directory-object writer (`WhenSysvolWriterIsDifferentPrincipal_ThenSEC080StillFlagsUnion`).
- **Backward compatible.** `LoadSysvolWritersByGpo` is guarded by `TableExists("fact_sysvol_ace")`,
  so SEC-080 still evaluates on Security-mode DBs captured before SYSVOL support.

`LoadSysvolWritersByGpo`, `BuildSysvolUnionContext`.

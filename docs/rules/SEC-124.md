## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-124
  name: "Replication Topology Control Permission"
  description: >-
    A principal has DS-Replication-Manage-Topology, which can enable DCShadow-style attacks by allowing rogue DC registration.
  severity: High
  category: PrivilegeEscalation
  remediation: >-
    Remove unnecessary DS-Replication-Manage-Topology permissions.
  mitre: T1207
  tags: ["dcshadow", "replication", "tier-zero"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 533–542.

## 2. Intended detection (plain English)

Fire one High finding per `(non-privileged trustee, target NC head)` pair when an explicit allow ACE on the target grants the `DS-Replication-Manage-Topology` extended right (control-access bit, `access_mask & 256`). The right is what an attacker needs to manipulate the replication topology — registering a rogue inbound replication partner is the operational primitive of DCShadow. Well-known admin trustees and trustees that are already privileged-by-membership in tier-0 groups must not fire (they manage replication by design — the finding would be noise). Inherited ACEs are out of scope (the rule reports explicit grants). Tombstoned (`is_deleted = 1`) targets must not fire even if a stale `fact_ace` row joins. Deny ACEs (`ace_type` 1 / 6) must not fire.

### 3.1 Effective SQL (copied from code)

```sql
SELECT a.trustee_sid, a.object_guid, o.distinguished_name
FROM fact_ace a
INNER JOIN dim_object o ON a.object_guid = o.object_guid
WHERE a.object_type_guid = $guid          -- DS-Replication-Manage-Topology Rights-GUID
  AND (a.access_mask & 256) != 0          -- ADS_RIGHT_DS_CONTROL_ACCESS
  AND a.ace_type IN (0, 5)                -- AccessAllowed / AccessAllowedObject
  AND a.is_inherited = 0
  AND o.is_deleted = 0
ORDER BY a.trustee_sid, a.object_guid
```

Bound parameter `$guid` = `1131f6ac-9c07-11d1-f79f-00c04fc2dcd2` (DS-Replication-Manage-Topology Rights-GUID per Microsoft adschema `r-ds-replication-manage-topology`).

### 3.2 Post-SQL filters (in C#)

- `IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — drops well-known admin RIDs (RID 500, 502, 512, 516, 518, 519, 521, …) **and** trustees whose SID appears in the precomputed transitive privileged set (DA / EA / Schema Admins / Builtin Administrators members).

Note the rule reads `fact_ace` directly rather than the derived `fact_control_edge`, so it does not need `ControlEdges` coverage — but it also does not benefit from `deny_cancelled` resolution (see §13 `[IMP-ACE-VS-EDGE]`). `GroupMembership` is **not** declared even though `IsPrivilegedPrincipal` consumes the transitive set; same gap that `[IMP-COV-MEMB]` tracks for SEC-025 / SEC-080 / SEC-081 / SEC-090 / SEC-123.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Non-Manage-Topology object types | SQL `a.object_type_guid = $guid` | Rule scope is the DS-Replication-Manage-Topology extended right; other replication rights (`DS-Replication-Get-Changes` family, `DS-Replication-Synchronize`, `DS-Replication-Monitor-Topology`) are covered by SEC-002 / dedicated rules. |
| Non-control-access rights | SQL `(a.access_mask & 256) != 0` | The right is realised only via the control-access bit; ReadProperty / WriteProperty against the same GUID does not actually invoke the extended right. |
| Deny / audit ACEs | SQL `a.ace_type IN (0, 5)` | Deny ACEs (1/6) and audit (2/7) cannot grant the extended right. |
| Inherited ACEs | SQL `a.is_inherited = 0` | Rule reports explicit, source-of-action grants; inheritance is propagation of an upstream finding and would produce derivative noise. |
| Deleted targets | SQL `o.is_deleted = 0` | Tombstoned targets cannot host an attack; lingering ACE rows would be noise. |
| Well-known admin trustees | C# `IsAdminSid(sid)` (inside `IsPrivilegedPrincipal`) | DA / EA / SA / BA already manage replication by design; not actionable. |
| Privileged-by-membership trustees | C# `context.PrivilegedSids.Contains(sid)` (inside `IsPrivilegedPrincipal`) | Transitive DA / EA members inherit the same trust; surfacing topology rights from these principals is noise. |

Not excluded (intentionally subject to review):

- Cross-domain trustees. Considered in scope: rogue-DC / DCShadow-style abuse is the canonical attack here.
- Generic-class targets. The SQL constrains `object_class IN ('domainDNS', 'configuration', 'dMD')` (the Rights-GUID's `Applies-To` per adschema; `[IMP-TGT-CLASS]` resolved).
- `deny_cancelled` semantics are not applied because the rule reads `fact_ace` directly. A deny ACE that neutralises an upstream allow via DACL ordering is currently surfaced. See §13 `[IMP-ACE-VS-EDGE]`.

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Wrong Rights-GUID hardcoded (resolved on rule).** `EvaluateReplicationTopologyControl` previously hardcoded `1131f6ab-9c07-11d1-f79f-00c04fc2dcd2` as the DS-Replication-Manage-Topology GUID. Per Microsoft Learn (`adschema/r-ds-replication-synchronize` and `adschema/r-ds-replication-manage-topology`), `1131f6ab-…` is `DS-Replication-Synchronize`; the correct DS-Replication-Manage-Topology Rights-GUID is `1131f6ac-9c07-11d1-f79f-00c04fc2dcd2`. The bug produced a complete miss on the intended attack (no real Manage-Topology grants ever fired) plus surfaced benign DS-Replication-Synchronize grants as DCShadow findings — the inverse of the catalog claim. Fixed inline this session; pinned by `WhenManageTopologyRight_ThenSEC124Fires` (uses the correct GUID and now fires) and `WhenReplicationSynchronizeRight_ThenSEC124DoesNotFire` (regression for the historic value). Cross-cutting tracked under `[IMP-WK-GUID]`.
2. **`GuidCatalog` had the same two GUIDs swapped (resolved cross-cutting, scoped to this card).** `src/SecureAD.Core/Catalogs/GuidCatalog.cs:86–87` declared `1131f6ab-…` as `DS-Replication-Manage-Topology` and `1131f6ac-…` as `DS-Replication-Synchronize` — the same swap as in the evaluator, propagated into UI labels (`StoredAclCompareViewModel`, `StoredEffectiveAccessViewModel`, `StoredInheritanceViewModel`, `ObjectDetailPanelViewModel`). `src/SecureAD.Core/Schema/WellKnownGuids.cs:36–37` had the correct mapping, so the two catalogs disagreed. Fixed inline; the swap is now consistent with `WellKnownGuids.cs` and Microsoft adschema. Cross-cutting tracked under `[IMP-WK-GUID]`.
3. **Tombstone gap (resolved on rule).** SQL did not filter `o.is_deleted = 0`, so lingering `fact_ace` rows against tombstoned NCs would surface as High findings. Same defect class fixed for SEC-122 / SEC-123 in earlier sessions. Fixed inline; pinned by `WhenManageTopologyAceOnDeletedTarget_ThenSEC124DoesNotFire`. Cross-cutting sweep against the remaining sibling rules in `AdvancedRuleEvaluator` (SEC-201, SEC-204) is still open — tracked under `[IMP-DEL-OBJ]`.
4. **Privileged-by-membership trustees previously surfaced (resolved on rule).** Evaluator filter was `IsAdminSid(sid)` only, ignoring `context.PrivilegedSids`. Sibling rules SEC-120 / SEC-121 / SEC-123 in the same evaluator already use `IsPrivilegedPrincipal(sid, context.PrivilegedSids)`. Brought into parity inline this session; pinned by `WhenPrivilegedByMembershipTrusteeHasManageTopology_ThenSEC124DoesNotFire`. Cross-cutting sweep tracked under `[IMP-PRIV-MEMB-SRC]`.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-DEL-OBJ]` — Resolved on SEC-124. Cross-cutting sweep for the remaining `AdvancedRuleEvaluator` rules (SEC-201, SEC-204) is still open.
2. `[IMP-PRIV-MEMB-SRC]` — Resolved on SEC-124. Cross-cutting sweep against the other audited rules listed under this tag remains open.
3. `[IMP-WK-GUID]` — Centralize every schemaIDGUID and control-access-right GUID literal in a single typed catalog and reference it by symbolic name from every evaluator and UI surface. The SEC-124 audit found the same `DS-Replication-Manage-Topology` / `DS-Replication-Synchronize` swap in **two** catalogs (`AdvancedRuleEvaluator.cs` and `GuidCatalog.cs`) while a third (`WellKnownGuids.cs`) was correct — the duplication enables silent disagreement. Pin each entry with a test that asserts the value matches the Microsoft adschema authoritative value.
4. `[IMP-DN-ENRICH]` — `Detail` interpolates `dn ?? objectGuid.ToString()`. When `dn` is null, the operator sees only a GUID, which is unactionable. The trustee SID is also surfaced raw with no `sam_account_name` join. Parity with SEC-100/101/102/120/121/122/123.
5. `[IMP-PARITY-TEST]` — No per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-124. Same gap is open across the audited backlog.
6. `[IMP-CTX-RULEID]` — `CreateEdgeFinding` already stamps `rule_id` into `ContextJson`, so this rule is fine on its own — but the sibling delegation-style rules in `AdvancedRuleEvaluator` (SEC-122) do not, and the cross-cutting tag still applies until `CreateDelegationFinding` is brought into parity.
7. `[IMP-MITRE-FIT]` — Catalog maps SEC-124 to `T1207` (Rogue Domain Controller). DCShadow itself is the canonical T1207 sub-technique, but Manage-Topology is the *precondition* (the right that lets an attacker register a rogue replication source), not the act of being a rogue DC. A finer mapping (`T1098` Account Manipulation as precondition) might be more accurate, or T1207 could be retained with the understanding that the rule fires on the configuration that enables the technique rather than on the technique's execution. Same cross-cutting tag.
8. `[IMP-CTRL-SCOPE]` — **RESOLVED by documented partition.** SEC-124 keys on `fact_ace` where `object_type_guid = DS-Replication-Manage-Topology` (the extended-right primitive). `GenericAll` / `WriteDacl` / `WriteOwner` on the same NC head confer the capability transitively, but those broad takeover primitives are caught by SEC-001 (GenericAll on domain root), SEC-201 (WriteDacl/WriteOwner/Owns on domain root), and SEC-204 (spill to Tier-0). SEC-124 is the *extended-right-specific evidence* layer; widening it would duplicate those findings. Note this is an **extended right**, not a property write, so the `PropertyWriteEquivalents` helper does not apply (extended rights are conferred by `GenericAll` only, never `GenericWrite` / `WriteAllProperties`). Partition documented; no code change.
9. `[IMP-TGT-CLASS]` — **RESOLVED.** The SQL now constrains `o.object_class IN ('domainDNS', 'configuration', 'dMD')` (the Rights-GUID's `Applies-To` per adschema), so an ACE granting the right on any other class no longer fires. Pinned by `WhenManageTopologyAceTargetsUser_ThenSEC124DoesNotFire`.
10. `[IMP-ACE-VS-EDGE]` — Rule reads `fact_ace` directly so `deny_cancelled` semantics are not applied (a deny ACE that neutralises an earlier allow via DACL ordering still surfaces) and the finding carries `SourceEdgeId == null` (no control-edge provenance). Either model `DS-Replication-Manage-Topology` as a typed `ControlType` and migrate to `fact_control_edge`, or LEFT JOIN `fact_control_edge` for `deny_cancelled` semantics while keeping the `fact_ace` lineage. Same cross-cutting tag as SEC-090 / SEC-123.
11. `[IMP-COV-MEMB]` — `RuleCoverageRequirements["SEC-124"]` does not declare `GroupMembership`, but the post-SQL filter consumes `context.PrivilegedSids` (built from `fact_group_membership_closure`). Without the dependency declared, an incomplete-membership run silently degrades transitively-privileged trustees to NonPrivileged and the stamper does not attach a `coverage_reason`. Same cross-cutting tag as SEC-025 / SEC-080 / SEC-081 / SEC-090 / SEC-123.

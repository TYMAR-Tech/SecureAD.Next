## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-090
  name: "Unexpected Principal can Read LAPS Passwords"
  description: >-
    A principal has read access to LAPS password attributes (ms-Mcs-AdmPwd or msLAPS-Password).
  severity: High
  category: CredentialTheft
  remediation: >-
    Restrict LAPS password attribute read access to authorized workstation administrators.
  mitre: T1003.003
  tags: ["laps", "credential-theft", "lateral-movement"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 423–432.

## 2. Intended detection (plain English)

Surface any principal (other than expected administrators) that holds the right to read a LAPS password attribute on a computer object — either the legacy `ms-Mcs-AdmPwd` attribute (Microsoft LAPS v1) or the modern `msLAPS-Password` attribute (Windows LAPS). Read access to these attributes lets the principal recover the per-machine local administrator password in clear text, enabling credential-theft and lateral movement (MITRE T1003.003 — _OS Credential Dumping: DCSync_ family). Severity is `High` because the impact is limited to the specific computer's local administrator (vs. the domain-wide impact of a Tier 0 control rule), but the credential is plaintext and immediately reusable.

### 3.1 Effective SQL (copied from code)

```sql
SELECT a.trustee_sid, a.object_guid, o.distinguished_name, MIN(e.edge_id) AS edge_id,
       MAX(CASE WHEN a.object_type_guid = '2e0e4a88-...' THEN 1 ELSE 0 END) AS has_legacy,
       MAX(CASE WHEN a.object_type_guid = '53c5be7e-...' THEN 1 ELSE 0 END) AS has_windows,
       MAX(CASE WHEN a.object_type_guid IS NULL THEN 1 ELSE 0 END) AS has_all_extended_rights
FROM fact_ace a
INNER JOIN dim_object o ON a.object_guid = o.object_guid
LEFT JOIN fact_control_edge e ON ... AND e.deny_cancelled = 0
WHERE o.object_class = 'computer'
  AND a.ace_type IN (0, 5)
  AND (a.object_type_guid = '2e0e4a88-f5fa-11df-b3af-001fc000a000'
       OR a.object_type_guid = '53c5be7e-5403-4013-a04b-b22e05d0e3c1'
       OR a.object_type_guid IS NULL)
  AND (a.access_mask & 256) != 0
  AND NOT EXISTS (... deny_cancelled = 1 ...)
GROUP BY a.trustee_sid, a.object_guid, o.distinguished_name, o.domain_fqdn
ORDER BY a.trustee_sid, a.object_guid
```

(GUIDs are inlined in the `EvaluateLapsReadAccess` SQL as the constants `legacyLapsGuid` and `windowsLapsGuid`. Access mask bit `0x100` is `ADS_RIGHT_DS_CONTROL_ACCESS` — required because the LAPS attributes are confidential; see §13 `[IMP-CTRL-SCOPE]`. The `object_type_guid IS NULL` branch matches a generic "all extended rights" ACE / GenericAll.)

### 3.2 Post-SQL filters (in C#)

- `if (RuleEvaluatorHelpers.IsAdminSid(sid) || RuleEvaluatorHelpers.PrivilegedSystemSids.Contains(sid)) continue;` — drops well-known admin SIDs (RID 500, 502, 512, 516, 518, 519, 520, 521, 526, 527) and the built-in privileged system identities (SYSTEM `S-1-5-18`, Enterprise DCs `S-1-5-9`, Creator Owner `S-1-3-0`, Self `S-1-5-10`, BUILTIN\Administrators `S-1-5-32-544`, BUILTIN\Account Operators `S-1-5-32-548`, BUILTIN\Server Operators `S-1-5-32-549`, BUILTIN\Print Operators `S-1-5-32-550`, BUILTIN\Backup Operators `S-1-5-32-551`, BUILTIN\Replicators `S-1-5-32-552`). The `PrivilegedSystemSids` half of the OR is redundant (every SID in that set is already classified as an admin by `IsAdminSid`) — see §13 (`[IMP-DEAD-CHECK]`). Broad principals (`Everyone`, `Authenticated Users`, `Anonymous`) intentionally pass through — see §5.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Non-computer targets | SQL `o.object_class = 'computer'` | LAPS attributes are only meaningful on computer objects (per-machine local administrator password). A read ACE on the same attribute against another class would not produce a credential and is therefore filtered. |
| Audit / Deny ACEs | SQL `a.ace_type IN (0, 5)` | Only `ACCESS_ALLOWED` (0) and `ACCESS_ALLOWED_OBJECT` (5) grant read access. `ACCESS_DENIED` (1, 6) and `SYSTEM_AUDIT` (2, 7) ACEs do not confer the right. |
| Non-LAPS attributes | SQL `object_type_guid IN ('2e0e4a88-...', '53c5be7e-...')` (or NULL for a generic all-extended-rights ACE) | Restricts to the two LAPS attribute GUIDs plus the object-wide CONTROL_ACCESS case. A `CONTROL_ACCESS` ACE scoped to a different attribute does not expose the LAPS password. |
| Insufficient access masks (confidential gate) | SQL `(access_mask & 256) != 0` | The `ADS_RIGHT_DS_CONTROL_ACCESS` bit must be set: LAPS attributes are confidential, so READ_PROPERTY alone is not enough to read them (KB922836). A write-only ACE, or a plain READ_PROPERTY / ReadAllProperties grant (e.g. the default `Authenticated Users` mask `0x00020094`), does not let the principal recover the password. See §13 (`[IMP-CTRL-SCOPE]`). |
| Well-known admin sources | C# `IsAdminSid(sid)` | Expected workstation administrators (Domain Admins RID 512, BUILTIN\Administrators, SYSTEM, etc.) reading LAPS is normal operation, not a misconfiguration. |
| Built-in privileged system identities | C# `PrivilegedSystemSids.Contains(sid)` (redundant) | Same set as the second leg of `IsAdminSid`. See §13 (`[IMP-DEAD-CHECK]`) — the OR clause is dead code; SEC-090 is the only rule in the family that still spells it out. |

Not excluded (intentionally subject to review):

- **Broad principals.** `Everyone` / `Authenticated Users` / `Anonymous` fall through `IsAdminSid` (`BroadSids` are not admins). A broad-SID LAPS read ACE is the canonical "anyone can pull local admin passwords" misconfiguration; the rule must fire. Pinned in §7 / §8. Cross-cutting `[IMP-PRIV-MEMB-SRC]` mirror does not apply because broad principals are not privileged-by-membership.
- **Privileged-by-membership sources.** A user transitively reaching Domain Admins (via nested group membership) still fires SEC-090; `ContextJson.source_admin_classification = "PrivilegedByMembership"` flags the case downstream. Aligned with SEC-080 / SEC-081; cross-cutting `[IMP-PRIV-MEMB-SRC]`.
- **Inherited ACEs.** The SQL does not filter `is_inherited`. Correct: an inherited LAPS-read ACE granted at an OU and propagating to the computer still confers the read right.
- **Deleted targets (`is_deleted = 1`).** The SQL does not filter `dim_object.is_deleted`. Same family-wide gap as SEC-080 / SEC-081 — cross-cutting `[IMP-DEL-OBJ]`.
- **`deny_cancelled` semantics.** SEC-090 reads `fact_ace` directly, not `fact_control_edge`. There is no `deny_cancelled` column on `fact_ace`, so a deny ACE that effectively neutralises an allow at the SD-evaluation layer is **not** filtered here — a row showing `(allow LAPS-read for SID X) + (deny LAPS-read for SID X via DACL ordering)` still fires SEC-090. See §13 (`[IMP-ACE-VS-EDGE]`).

## 9. Output assertions (`Detail` and `ContextJson`)

- `RuleId == "SEC-090"`
- `Severity == High`
- `SubjectSid` = source principal SID
- `TargetKind == "object_guid"`

- `ContextJson` non-null and contains:
  - `"rule_id": "SEC-090"`
  - `"source_sid"`, `"target_guid"`, `"target_dn"`, `"control_type": "ReadProperty:LAPS"`

  - `"source_is_privileged_by_membership"`, `"source_is_broad_principal"` booleans

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`).

1. `[IMP-ACE-VS-EDGE]` — SEC-090 is the only rule in the control-edge family (SEC-001..SEC-006, SEC-014, SEC-024..SEC-026, SEC-040, SEC-060..SEC-062, SEC-080, SEC-081) that reads `fact_ace` directly instead of `fact_control_edge`. Consequences: (a) `deny_cancelled` is not applied — a deny ACE that neutralises an allow via DACL ordering still surfaces a finding; (b) `SourceEdgeId` is always null in the finding (no control-edge provenance); (c) the rule does not benefit from any future capture-pipeline normalization (e.g. ACE deduplication, inherited-vs-explicit resolution) applied at the `fact_control_edge` layer. Either (a) add a `ControlType.ReadLapsPassword` variant to `ControlEdgeService.DeriveControlTypes` and migrate SEC-090 onto `fact_control_edge`, or (b) extend the helper SQL to LEFT JOIN `fact_control_edge` for `deny_cancelled` semantics so the rule keeps its `fact_ace` lineage but gains effective-access correctness.
2. `[IMP-DEAD-CHECK]` — **Resolved on rule.** The post-SQL filter previously read `IsAdminSid(sid) || PrivilegedSystemSids.Contains(sid)`. Every SID in `PrivilegedSystemSids` is already returned `true` by `IsAdminSid` (the helper checks the set on `RuleEvaluatorHelpers.cs:83` before the RID-suffix test), so the second leg of the OR was dead code. Collapsed to a single `IsAdminSid(sid)` call, in line with every other rule in the family. Pinned by `WhenSystemPrincipalCanReadLaps_ThenSEC090DoesNotFire` (S-1-5-18 owner, the canonical previously-redundant case).
3. `[IMP-CTRL-SCOPE]` — **RESOLVED (corrected).** The LAPS password attributes are schema-**confidential** (`searchFlags` fCONFIDENTIAL). Per AD's confidential-attribute rule (KB922836) and the Windows LAPS AD guidance, reading a confidential attribute requires **CONTROL_ACCESS (`0x100`)** in *addition* to READ_PROPERTY — a plain READ_PROPERTY / ReadAllProperties grant cannot read it. The real read delegation (`Set-LapsADReadPasswordPermission`) grants CONTROL_ACCESS ("all extended rights"). SEC-090's gate is therefore `access_mask & 0x100` (not `& 0x10`), satisfied two ways: an object-specific CONTROL_ACCESS ACE on a LAPS attribute GUID, or a generic "all extended rights" ACE (`object_type_guid IS NULL`, also the expansion of GenericAll). **History:** an earlier pass keyed the broad branch on READ_PROPERTY (`0x10`), which produced a false positive on the default `Authenticated Users` GENERIC_READ ACE (mask `0x00020094`, Evidence 59017 — would have flagged nearly every computer) **and** risked a false negative on a CONTROL_ACCESS-only delegation. Corrected to CONTROL_ACCESS; provenance flag renamed `broad_read` → `all_extended_rights`. Pinned by `WhenNonAdminHasAllExtendedRightsOnComputer_ThenSEC090FiresWithFlag`, `WhenNonAdminHasGenericAllOnComputer_ThenSEC090Fires`, `WhenNonAdminHasReadAllPropertiesOnComputer_ThenSEC090DoesNotFire`, `WhenAceGrantsReadPropertyOnlyOnLapsAttribute_ThenSEC090DoesNotFire`, and `WhenNonAdminHasBroadWriteOnlyOnComputer_ThenSEC090DoesNotFire`.
4. `[IMP-DEL-OBJ]` — Add `AND o.is_deleted = 0` to the evaluator SQL. Without it, a non-admin who held LAPS-read on a tombstoned computer still surfaces a finding even though the computer no longer exists. Same family-wide gap as SEC-080 / SEC-081.
5. `[IMP-DN-ENRICH]` — `Detail` and `ContextJson` carry the source SID but no display name / SAM account name. Join `dim_principal` (or `dim_object` on `sid`) and surface `source_name` next to `source_sid`.
6. `[IMP-PRIV-MEMB-SRC]` — A principal transitively a Domain Admin still fires SEC-090 even though they are admin-equivalent. Decide whether SEC-090 should exclude `source_is_privileged_by_membership = true` (consistent with the admin-source skip) or keep them but tier severity differently. Mirrors the SEC-080 / SEC-081 family.
7. `[IMP-PRIV-PROV]` — `ContextJson` exposes `source_is_privileged_by_membership` but no provenance — which privileged group(s) the source reaches. Extend `RuleEvaluationContext.PrivilegedSidProvenance` (per the existing IMP entry) and surface it.

Tighten to clarify the scope: "on a computer object" (target restriction) and "via a non-admin principal" (subject restriction); otherwise the description reads like a coverage gate rather than a misconfiguration assertion.
10. **Modern LAPS encryption.** Windows LAPS supports DPAPI-NG encryption of `msLAPS-Password`; an encrypted password is readable as a SID-bound ciphertext that only the configured admin group(s) can decrypt. SEC-090 cannot distinguish between an encrypted and a plaintext stored password — it surfaces the read-access ACE either way. The encrypted case is significantly lower severity (the attacker still needs the configured decryptor identity). Out of scope of the rule today (would require parsing `msLAPS-EncryptedPassword` configuration or reading `msLAPS-Password` content at capture time); logged here for product-level awareness. If/when added to the taxonomy, tag as `[IMP-LAPS-ENCRYPTION]`.

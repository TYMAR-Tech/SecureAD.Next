### 3.1 SQL

```sql
SELECT o.object_guid, o.distinguished_name, o.sid, g.group_sid
FROM fact_group_membership_direct g
INNER JOIN dim_object o ON g.member_sid = o.sid
WHERE (g.group_sid LIKE '%-512')
  AND o.object_class = 'group'
ORDER BY o.sid, o.object_guid
```

### 3.2 Notes on the SQL

- The `INNER JOIN dim_object o ON g.member_sid = o.sid` filters out members that have no `dim_object` row â€” a nested group missing object metadata is silently dropped. See E5 / `[IMP-OBJ-JOIN]` in Â§13.
- `o.object_class = 'group'` is the explicit nested-vs-user filter. Users / computers / etc. directly in DA are not in scope.
- `g.group_sid LIKE '%-512'` scopes to Domain Admins across all domains. RID-512 is unique to Domain Admins among well-known group RIDs in `AdminRids`. Built-in `BUILTIN\Administrators` (exact `S-1-5-32-544`) does not match this pattern and is therefore out of scope.
- The SQL does not filter `o.is_deleted`. A tombstoned nested group would still fire. `[IMP-DEL-OBJ]` in Â§13.
- The SQL does not consult `fact_group_membership_closure`. The rule is intentionally **direct-only**; transitive nesting (group â†’ group â†’ DA) is left to SEC-100 / SEC-052 / closure-aware rules.
- `Detail` is hardcoded with `"Domain Admins"` â€” the actual `sAMAccountName` of the parent group from `dim_object` is not read. Localized / renamed DA still says "Domain Admins". `[IMP-NAME-DERIVE]` in Â§13.

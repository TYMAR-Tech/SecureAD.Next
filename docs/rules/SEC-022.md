
Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 146–155.

## 2. Intended detection (plain English)

A finding must be raised for every captured account that has the
`DONT_REQUIRE_PREAUTH` (`0x400000`) bit set in `userAccountControl`. AS-REP
roasting lets any unauthenticated attacker send an AS-REQ for such an account
and receive an AS-REP containing material encrypted with the account's password
hash, which can be cracked offline. The catalog claim is intentionally broader
than SEC-020: it says "**an account**", not "**a user account**", and lists
**no** exclusions in the description. This phrasing is consistent with the
evaluator (no class filter, no krbtgt exclusion) but the lack of practical
exclusions is itself a deferred concern (Â§12).

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid
FROM dim_delegation d
INNER JOIN dim_object o ON d.object_guid = o.object_guid
WHERE d.delegation_type = 'ASREPRoastable'
  AND o.is_deleted = 0
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

- **None.** The evaluator fires unconditionally for every joined row. No
  class filter, no `IsKrbtgtSid`, no UAC re-check. (`is_deleted = 0` is
  applied at SQL level.)
  This is the loosest evaluator we have audited so far in the SEC-02x family.
- The only *practical* filtering happens upstream at capture time:
  `DirectObjectWriter.WriteDelegations` only writes the row when the
  `DontRequirePreauth` (`0x400000`) UAC bit is set. Any object whose
  `userAccountControl` attribute can be parsed will be checked, including
  computers (`computer`), gMSA (`msDS-GroupManagedServiceAccount`), and MSA
  (`msDS-ManagedServiceAccount`). Whether the row appears is therefore an
  upstream invariant, not a SEC-022 invariant.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Accounts without the `DONT_REQUIRE_PREAUTH` UAC bit | Capture-side gate in `WriteDelegations` | The row is never written, so the join finds nothing. This is the **only** exclusion in the entire SEC-022 pipeline. |
| (Implicit, not enforced by code) krbtgt | _none_ | The evaluator does not call `IsKrbtgtSid`. krbtgt cannot in practice have this bit set on a real DC, but the rule does not defend against tampered captures. `[IMP-KRBTGT-FILTER]` in Â§12. |
| (Implicit, not enforced by code) Computer / gMSA / MSA / group | _none_ | SEC-022 has no `object_class` filter. The capture path will write the row for any object_class that exposes `userAccountControl` with the bit set, including computers. `[IMP-TGT-CLASS]` in Â§12. |
| Disabled accounts (`ACCOUNTDISABLE` bit) | `NotDisabledSql("o")` in the SQL | Disabled accounts cannot complete AS-REQ â†’ AS-REP, so the attack vector is non-viable; excluded. `[IMP-DISABLED-FILTER]` (resolved) in Â§12. |
| Tombstoned (`is_deleted = 1`) | SQL `o.is_deleted = 0` | A deleted user cannot be roasted. `[IMP-DEL-OBJ]` resolved on this rule. Verified by `WhenAsrepRoastableUserIsDeleted_ThenSEC022DoesNotFire`. |

Not excluded (intentionally subject to review): everything above except the
single capture-side UAC gate. SEC-022 is the most permissive Kerberos rule in
the catalog; this is intentional given the catalog wording ("**an account**")
but is documented in Â§12 so the deferred items can be tightened together
across SEC-020 / SEC-021 / SEC-022 / SEC-023.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-022"`
- `Severity == Medium`
- `SubjectSid` = the user's SID (or `""` when null)
- `TargetKind == "object_guid"`
- `TargetId` = object GUID (`D` format)
- `SourceEdgeId == null` (delegation findings carry no edge id)
- `FindingKey == "SEC-022|{SubjectSid}|{TargetId}"`
- `Detail` matches `Account {dn ?? guid} does not require pre-authentication`
- `ContextJson` non-null and contains:
  - `"rule_id": "SEC-022"`
  - `"evidence_type": "delegation"`
  - `"delegation_type": "ASREPRoastable"`
  - `"object_dn": "<DN or null>"`
  - `"object_guid": "<GUID in D format>"`

## 12. Defects / deferred items

1. `[IMP-TGT-CLASS]` — SEC-022 SQL has **no** `object_class` filter. A
   computer / gMSA / MSA / group with `DONT_REQUIRE_PREAUTH` set will fire
   the rule. This is operationally unusual but possible via tampering, and
   the rule offers no defence. Suggested resolution (same shape as SEC-020
   Â§12.1, applied here too): add `AND o.object_class = 'user'` to the SQL or
   explicitly enumerate the user-account-only structural classes. Pin
   regression tests P3, P4 will need to be flipped from "still fires
   known limitation" to "does not fire" when this is resolved.

2. `[IMP-KRBTGT-FILTER]` — **Resolved on rule.** SEC-022 now calls
   `IsKrbtgtSid` immediately after the SID read in `EvaluateAsrepRoastable`,
   matching the SEC-020 / SEC-021 pattern. A krbtgt row with
   `DONT_REQUIRE_PREAUTH` no longer surfaces a finding. Pinned by the flipped
   regression `WhenAsrepRoastableUserIsKrbtgt_ThenSEC022DoesNotFire`.

3. `[IMP-DISABLED-FILTER]` — **RESOLVED.** Disabled accounts are now
   excluded via `NotDisabledSql("o")` in the SQL (the capture pipeline
   writes a `delegation_type = 'Disabled'` row alongside `ASREPRoastable`
   when the `ACCOUNTDISABLE` bit is set, and the helper filters on it). The
   former `*_StillFiresKnownLimitation` pin was flipped to
   `WhenAsrepRoastableUserIsDisabled_ThenSEC022DoesNotFire`.
   Same tag as SEC-020 / SEC-021 / SEC-023.

4. `[IMP-DEL-OBJ]` — Resolved. SQL now filters `o.is_deleted = 0`; a
   tombstoned user with a stale `ASREPRoastable` row no longer fires.

5. `[IMP-DUP-RULE]` — SEC-022 (Medium) and SEC-023 (Critical) fire on the same
   row when the user is privileged. Same partitioning concern as
   SEC-020/SEC-021 (Â§12.4) — resolution requires a product-level decision
   to either collapse with severity tiering via `ClassifyPrincipal` or
   scope SEC-022 to non-privileged only.

6. `[IMP-DN-ENRICH]` — `Detail`/`ContextJson` carry `object_dn` but no
   `sam_account_name` or display name; cross-domain SIDs are opaque without
   enrichment.

7. `[IMP-PARITY-TEST]` — No per-rule severity / MITRE / tag parity
   assertion exists for SEC-022 in `RuleCatalogParityTests`. Adding one
   (`Severity == Medium`, `mitre == "T1558.004"`, tags `{ "kerberos",
   "asrep-roasting" }`) would prevent silent catalog edits.

8. `[IMP-CAT-WORDING]` — The catalog says "*an account has 'Do not require
   Kerberos pre-authentication' enabled*". This is technically accurate
   given the evaluator's loose behaviour, but a reader following the
   SEC-020 pattern may reasonably expect gMSA/MSA/computer exclusions.
   Tightening the wording — either to "**a user account**" (and adding the
   class filter under `[IMP-TGT-CLASS]`) or "**any object with this UAC
   bit**" (and explicitly documenting that computers can also surface) —
   would prevent future drift.

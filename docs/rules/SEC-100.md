## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-100
  name: "Service Account with Admin Privileges"
  description: >-
    A service account (identified by naming convention, gMSA, or managed service account class)
    is a direct or transitive member of a privileged group.
  severity: High
  category: AccountSecurity
  remediation: >-
    Remove the service account from privileged groups and grant only the minimum permissions required.
  mitre: T1078.002
  tags: ["service-account", "privilege", "least-privilege"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 456–465.

## 2. Intended detection (plain English)

Identify every "service account" (by class — gMSA / MSA — or by location — under `OU=Service Accounts` or `CN=Service Accounts`) that is a direct or transitive member of any privileged group. The catalog says "a privileged group" without enumerating which — so the authoritative privileged-set must come from the same source `FindingsService` uses to build `context.PrivilegedSids` (RIDs 512, 516, 518, 519, 526, 527 plus the five well-known `BUILTIN\*` SIDs S-1-5-32-544 / 548 / 549 / 550 / 551). One finding per `(service_account, privileged_group)` pair — the privileged group SID is part of `FindingKey` (`[IMP-KEY-COLLAPSE]` resolved).

## 4. Effective SQL executed (after defect fixes)

```sql
WITH membership AS (
    SELECT member_sid, group_sid FROM fact_group_membership_direct
    UNION
    SELECT member_sid, group_sid FROM fact_group_membership_closure
)
SELECT DISTINCT o.object_guid, o.distinguished_name, o.sid, g.group_sid
FROM membership g
INNER JOIN dim_object o ON g.member_sid = o.sid
WHERE o.is_deleted = 0
  AND (o.object_class = 'msDS-GroupManagedServiceAccount'
    OR o.object_class = 'msDS-ManagedServiceAccount'
    OR o.distinguished_name LIKE '%OU=Service Accounts%'
    OR o.distinguished_name LIKE '%CN=Service Accounts%')
  AND (g.group_sid LIKE '%-512' OR g.group_sid LIKE '%-518'
    OR g.group_sid LIKE '%-519' OR g.group_sid LIKE '%-516'
    OR g.group_sid LIKE '%-526' OR g.group_sid LIKE '%-527'
    OR g.group_sid IN ('S-1-5-32-544', 'S-1-5-32-548',
                       'S-1-5-32-549', 'S-1-5-32-550',
                       'S-1-5-32-551'))
ORDER BY o.sid, o.object_guid
```

## 5. Defects discovered and fixed this session

| # | Description | Defect risk | Fix |
| --- | --- | --- | --- |
| 1 | `WHERE` clause omitted `o.is_deleted = 0`. Tombstoned service accounts whose membership rows were still present in `fact_group_membership_direct` / `fact_group_membership_closure` surfaced as live findings. | False positive on tombstones. | Added `o.is_deleted = 0` as the first clause in the `WHERE` predicate. |
| 2 | The embedded privileged-group list was a **strict subset** of the canonical `FindingsService.PrivilegedGroupRids` + `PrivilegedGroupExactSids`: SEC-100 only fired on RIDs 512 / 518 / 519 and `S-1-5-32-544`. It silently excluded RID 516 (Domain Controllers), RID 526 (Key Admins), RID 527 (Enterprise Key Admins), and `BUILTIN\Account Operators` / `Server Operators` / `Print Operators` / `Backup Operators` (S-1-5-32-548 / 549 / 550 / 551). These principals are part of `context.PrivilegedSids` and are treated as privileged everywhere else in the rule pipeline, so SEC-100 produced a contradictory account of "in a privileged group". | False negative — multiple privileged groups silently ignored. | Widened the embedded list to mirror the canonical set: added `%-516`, `%-526`, `%-527`, and the four `BUILTIN\*Operators` exact SIDs. The duplication itself is captured for the cross-cutting `[IMP-PRIV-GROUPSET]` improvement. |

Both fixes are pinned by dedicated regression tests in §7.

## 10. Severity rationale

`High` matches `rules.yaml` and is loaded via `BuiltInRules.ById["SEC-100"].DefaultSeverity`. A service account in a privileged group is a least-privilege violation that grants persistent elevated access to an automated identity — typically with a static credential or a long-lived gMSA password. The combination of "service account = often forgotten" and "privileged = full domain compromise primitive" justifies `High` over a hygiene-level severity.

## 11. MITRE mapping

`T1078.002` — _Valid Accounts: Domain Accounts_. Reasonable fit for the persistence/abuse angle. Same `[IMP-MITRE-FIT]` caveat as SEC-091 / SEC-092 (the technique describes the outcome rather than the configuration).

## 13. New cross-cutting items captured this session

- `[IMP-PRIV-GROUPSET]` — The "what counts as a privileged group" set is duplicated in two places: `FindingsService.PrivilegedGroupRids` + `PrivilegedGroupExactSids` (used to compute `context.PrivilegedSids`) and the embedded SQL whitelist in `EvaluateServiceAccountInAdminGroup` (used to decide firing). The two lists drifted (SEC-100 missed RIDs 516 / 526 / 527 and four `BUILTIN\*Operators` SIDs) and the SQL has no compile-time link to the C# constants. Affects SEC-100 today; any future rule that consults a privileged-group set in SQL inherits the trap. **Resolution**: introduce a shared `PrivilegedGroupCatalog` that exposes (a) `IsPrivilegedGroupSid(sid)` for C# use and (b) a SQL-friendly enumeration (exact SIDs + RID-suffix patterns) consumable by evaluator SQL via parameter binding. Have both `BuildPrivilegedSids` and SEC-100 read from the same catalog.
- `[IMP-SA-DETECT]` — Service-account detection in SEC-100 / SEC-101 uses an English-substring DN heuristic (`%OU=Service Accounts%`, `%CN=Service Accounts%`) that misses `OU=Service_Accounts`, `OU=SvcAccts`, localized OU names, and any organization that uses a different naming convention. It also has no comma-boundary anchoring, so `OU=Service Accounts Reserve,...` and `OU=No Service Accounts,...` both match. **Resolution**: replace with a typed `ServiceAccountClassifier` that consults (a) `object_class IN ('msDS-GroupManagedServiceAccount', 'msDS-ManagedServiceAccount')`, (b) `userAccountControl & 0x2000` for `SERVER_TRUST_ACCOUNT` / `INTERDOMAIN_TRUST_ACCOUNT` distinction, (c) `servicePrincipalName IS NOT NULL` for plain user accounts running services, and (d) an explicit policy-provided OU list. Centralize so SEC-100 / SEC-101 share the same source.
- `[IMP-MEMB-UNION]` — SEC-100 `UNION`s `fact_group_membership_direct` + `fact_group_membership_closure` because the closure-expansion pipeline may be partial. Other rules consult only one of the two. The asymmetry is undocumented and the correct intent (transitive via closure if available, otherwise fall back to direct) is implemented as `UNION` in some rules and as plain closure-only in others. **Resolution**: standardize on the `UNION` pattern for any rule whose semantics include transitive membership, or push the union into a derived view (`fact_group_membership_effective`) materialized at expansion time. Document in each rule card which source is intended.

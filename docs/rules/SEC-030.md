## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-030
  name: "AdminCount Without Protection"
  description: >-
    An account has adminCount=1 but lacks observed protected-group membership evidence after excluding expected protected identities (Administrator, krbtgt, Domain Admins, Domain Controllers, Schema Admins, Enterprise Admins, Group Policy Creator Owners, Read-only Domain Controllers, Key Admins, Enterprise Key Admins, and BUILTIN Administrators). BUILTIN Account/Server/Print/Backup Operators and Replicators remain in scope because they are risky and only empty groups are filtered out.
  severity: Medium
  category: AccountSecurity
  remediation: >-
    Review whether adminCount is stale, whether the principal should still be protected, and whether risky operator groups are intentionally populated. The rule also suppresses results when membership evidence shows the principal is already protected through Domain Admins, Domain Controllers, Schema Admins, Enterprise Admins, Group Policy Creator Owners, Read-only Domain Controllers, Key Admins, Enterprise Key Admins, or BUILTIN Administrators.
  tags: ["admincount", "orphaned"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 202–211.

No `mitre` field is present on this rule in the catalog.

## 2. Intended detection (plain English)

> Written from §1 only. Compared against §3 below.

Fire when an AD object carries `adminCount=1` but is **not** one of the
well-known protected identities and **not** a transitive member of one of
those identities. The catalog enumerates eleven excluded identities. It
additionally states that the BUILTIN Account / Server / Print / Backup
Operators and Replicators groups stay in scope *and* that "only empty
groups are filtered out" — i.e. the catalog text implies that operator
groups with **no** members should be suppressed.

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid
FROM dim_delegation d
INNER JOIN dim_object o ON d.object_guid = o.object_guid
WHERE d.delegation_type = 'AdminCount'
  AND o.sid IS NOT NULL
  AND NOT (
    o.sid = 'S-1-5-32-544'
    OR o.sid LIKE '%-500'
    OR o.sid LIKE '%-502'
    OR o.sid LIKE '%-512'
    OR o.sid LIKE '%-516'
    OR o.sid LIKE '%-518'
    OR o.sid LIKE '%-519'
    OR o.sid LIKE '%-520'
    OR o.sid LIKE '%-521'
    OR o.sid LIKE '%-526'
    OR o.sid LIKE '%-527'
  )
  AND NOT EXISTS (
    SELECT 1 FROM fact_group_membership_closure g
    WHERE g.member_sid = o.sid
      AND (
        g.group_sid = 'S-1-5-32-544'
        OR g.group_sid LIKE '%-512'
        OR g.group_sid LIKE '%-516'
        OR g.group_sid LIKE '%-518'
        OR g.group_sid LIKE '%-519'
        OR g.group_sid LIKE '%-520'
        OR g.group_sid LIKE '%-521'
        OR g.group_sid LIKE '%-526'
        OR g.group_sid LIKE '%-527'
      )
  )
ORDER BY o.sid, o.object_guid
```

Notes:

- `LIKE '%-RID'` against SIDs is anchored by the literal leading `-`, so
  `S-1-5-21-…-512` matches and `S-1-5-21-…-4512` does not (last 4 chars
  are `4512`, not `-512`).
- `dim_delegation.delegation_type = 'AdminCount'` is the upstream
  signal that `adminCount` attribute equals 1; the `details` column
  carries the raw value `"1"`. The evaluator does not read `details`.
- The closure check uses `fact_group_membership_closure`, **not**
  `fact_group_membership_direct`. A direct-only membership row that was
  never expanded into the closure table would not suppress SEC-030.
  Captured under `[IMP-MEMB-SOURCE]` in §13.
- `o.sid IS NOT NULL` silently drops NULL-SID `dim_object` rows. This
  is the same family as the SEC-026 `[IMP-NULL-SID]` issue, but for
  SEC-030 it is **intentional**: an account without a SID cannot be
  compared against well-known SIDs, so silently skipping it is
  defensible. Documented in §12.

### 3.2 Post-SQL filters (in C#)

For every row returned by the SQL:

- Compute `isOperatorGroup = Sec030OperatorGroupSids.Contains(sid)`
  (matches `S-1-5-32-548..552`).
- If operator-group, compute
  `hasObservedMembers = GroupHasObservedMembers(connection, sid)` —
  which checks `fact_group_membership_direct OR
  fact_group_membership_closure` for any row with `group_sid = sid`.
- **Suppress** an empty operator group (`!hasObservedMembers`) **only when**
  `IsGroupMembershipCoverageComplete(connection)` is true — i.e. the group is
  confirmed empty, not empty merely because capture was partial. This matches
  the catalog contract ("only empty groups are filtered out"). `[IMP-CAT-WORDING]`
  resolved in §12.
- Otherwise pick the `Detail` string from one of three templates (non-operator,
  operator-with-members, operator-without-members-but-coverage-partial) and emit.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| `o.sid IS NULL` | SQL `o.sid IS NOT NULL` | An object without a SID cannot be compared against the well-known SID list. Documented in §12. |
| BUILTIN\Administrators (`S-1-5-32-544`) | SQL exact match | Expected built-in admin. |
| Administrator (RID 500) | SQL `LIKE '%-500'` | Built-in administrator account; protected by design. |
| krbtgt (RID 502) | SQL `LIKE '%-502'` | Service account; `adminCount=1` is expected. |
| Domain Admins (RID 512) | SQL `LIKE '%-512'` | Expected protected identity. |
| Domain Controllers (RID 516) | SQL `LIKE '%-516'` | Expected protected identity. |
| Schema Admins (RID 518) | SQL `LIKE '%-518'` | Expected protected identity. |
| Enterprise Admins (RID 519) | SQL `LIKE '%-519'` | Expected protected identity. |
| Group Policy Creator Owners (RID 520) | SQL `LIKE '%-520'` | Expected protected identity. |
| Read-only Domain Controllers (RID 521) | SQL `LIKE '%-521'` | Expected protected identity. |
| Key Admins (RID 526) | SQL `LIKE '%-526'` | Expected protected identity. |
| Enterprise Key Admins (RID 527) | SQL `LIKE '%-527'` | Expected protected identity. |
| Transitive member of any of the above (except RID 500, RID 502) via closure | SQL `NOT EXISTS … fact_group_membership_closure` | An account already covered by AdminSDHolder via group nesting is "protected" — the adminCount stamp is not stale. |

Not excluded (intentionally subject to review):

- **BUILTIN\Account/Server/Print/Backup Operators and Replicators**
  (`S-1-5-32-548..552`). These AdminSDHolder-protected groups carry
  `adminCount=1` by default. A **populated** operator group always fires. An
  **empty** one is suppressed when `GroupMembership` coverage is complete
  (confirmed empty) and still fires — as a "review whether truly empty or only
  partially captured" prompt — when coverage is partial. `[IMP-CAT-WORDING]`
  resolved in §12.
- **Members of operator groups (548–552)**. The closure check does not
  include those RIDs, so a user who is a member of Account Operators
  but is not in a 512/516/518/519/520/521/544/526/527 group will still
  fire if they personally carry `adminCount=1`. This appears
  intentional (operator membership is risky in its own right) but is
  not documented.
- **Tombstoned (`is_deleted = 1`) objects**. The SQL does not filter.
  Stale adminCount on tombstoned accounts is reported. `[IMP-DEL-OBJ]`
  in §13.

| # | Scenario | Resolution |
| --- | --- | --- |
| E1 | Deny ACE / `deny_cancelled = 1` | N/A — SEC-030 does not consult `fact_control_edge`. |
| E2 | Inherited ACE | N/A — SEC-030 does not consult ACEs. |
| E3 | Deleted target object (`is_deleted = 1`) | Not filtered. A tombstoned account with `adminCount=1` would fire. `[IMP-DEL-OBJ]` in §13. |
| E4 | Multiple `AdminCount` delegation rows for the same `(object_guid)` | `dim_delegation` PK is `(object_guid, delegation_type, target)`. The default `InsertDelegation` helper inserts with `target=""`, so duplicates collapse on the primary key. The SQL has no `DISTINCT` because the PK already enforces uniqueness for the same target. |
| E5 | Coverage incomplete for required module | `coverage_complete` is stamped per finding by `FindingsService.StampCoverageOnFindings` based on `RuleCoverageRequirements["SEC-030"] = {Objects, GroupMembership}`. Verified by the parity / coverage tests. |
| E6 | Cross-domain principal | Subject is identified by SID. The closure check operates on SID, so cross-domain membership (RID-based) suppresses correctly. P7 pins. |
| E7 | Broad SID (`Everyone`, `Authenticated Users`, `Anonymous`) | N/A — broad SIDs are never targets of `adminCount=1`. |
| E8 | Privileged-by-membership (transitive DA/EA) non-RID SID | The closure check is RID-based via `LIKE '%-512'` / `'%-519'` / etc. A privileged group with a custom (non-well-known) RID would not be matched. | E10 | Member of an operator group (548–552), not directly a target of `adminCount=1` | SQL does not include 548–552 in the closure check, so the member's own `adminCount=1` row is not suppressed by operator-group membership. Apparent design intent. Documented in §5. |
| E11 | `Detail` and `ContextJson` carry SID and DN but no `sAMAccountName` | `[IMP-DN-ENRICH]` in §13. |
| E12 | `FindingKey` collision risk | `FindingKey = "SEC-030|{subjectSid}|{objectGuid}"`. Each object produces exactly one SEC-030 row (PK on `dim_delegation`), so collisions are impossible within a run. |
| E13 | Operator group with NULL SID | SQL `o.sid IS NOT NULL` drops it before the post-SQL operator-group check — `isOperatorGroup` is never `true` for a NULL SID. No regression. |

## 9. Output assertions (`Detail` and `ContextJson`)

For a generic user with stale adminCount, the finding must include:

- `RuleId == "SEC-030"`
- `Severity == Medium`
- `TargetKind == "object_guid"`
- `TargetId == objectGuid` (D-formatted)
- `SubjectSid == sid` (or empty string if NULL — see E9, but SQL gates that out)
- `SourceEdgeId is null` (delegation finding)
- `SourcePathId is null`
- `Detail` contains `has adminCount=1 but no protected group membership`
- `ContextJson` keys (verified by the operator-group test fixture):
  - `evidence_type` = `"account_hygiene"`
  - `condition` = `"AdminCount"`
  - `admin_count` = `1`
  - `object_dn` = the DN
  - `object_sid` = the SID
  - `protected_membership_observed` = `false`
  - `operator_group` = `true` for 548–552, else `false`
  - `observed_members` = `true` when an operator group has members
    captured (direct OR closure), else `false`
  - `object_guid` = the GUID (D-formatted)

`ContextJson` does **not** carry a top-level `"rule_id"` field — same
`[IMP-CTX-RULEID]` shape as SEC-026 §13.

## 12. Defects / deferred items

1. `[IMP-CAT-WORDING]` — **RESOLVED.** The catalog contract ("only
   empty groups are filtered out") is now honoured: an operator group
   (`S-1-5-32-548..552`) with no observed members is suppressed **when
   `GroupMembership` coverage is complete** (`IsGroupMembershipCoverageComplete`).
   When coverage is partial/failed/missing the group still surfaces as a
   review prompt, so a group that only *looks* empty due to incomplete
   capture is not silently dropped. Pinned by
   `WhenAdminCountOperatorGroupIsEmptyAndCoverageComplete_ThenSEC030DoesNotFire`
   (`[Theory]` over all five operator RIDs),
   `WhenAdminCountObjectIsAccountOperatorsEmptyWithPartialCoverage_ThenSEC030Fires`,
   and `WhenAdminCountOperatorGroupHasMembersAndCoverageComplete_ThenSEC030StillFires`.

2. `[IMP-MEMB-SOURCE]` (**new tag**) — **Accepted-with-known-limitation.**
   The closure-based protection check uses
   `fact_group_membership_closure` exclusively. A run that captured
   direct group membership but failed to expand the closure (partial
   coverage) would not suppress SEC-030 even for a user who is a
   direct member of Domain Admins. Coverage stamping flags this via
   `RuleCoverageRequirements["SEC-030"] = [Objects, GroupMembership]`
   but does not branch the SQL. Documented in §13.

3. `[IMP-DEL-OBJ]` — **Accepted-with-known-limitation.** SQL does not
   filter `is_deleted = 1`. Tombstoned accounts with stale adminCount
   still fire. Deferred to the cross-cutting `[IMP-DEL-OBJ]`
   workstream.

4. `[IMP-DN-ENRICH]` — **Accepted-with-known-limitation.** `Detail`
   and `ContextJson` carry DNs and SIDs but no `sAMAccountName` /
   `display_name`. Operators identifying which account to remediate
   typically search by `sAMAccountName`. Deferred to the cross-cutting
   `[IMP-DN-ENRICH]` workstream.

5. `[IMP-CTX-RULEID]` — **Accepted-with-known-limitation.**
   `ContextJson` produced by `CreateDelegationFinding` does not embed
   a top-level `"rule_id"` field. Same shape issue as documented in
   the SEC-026 card.

6. `[IMP-PRIV-MEMB-SRC]` — **Accepted-with-known-limitation.** The
   closure check is RID-based (`LIKE '%-512'`, `'%-519'`, …) and does
   not consult `RuleEvaluationContext.PrivilegedSids`. A custom
   privileged group whose SID has a non-well-known RID would not
   suppress SEC-030 for its members. Deferred to the cross-cutting
   `[IMP-PRIV-MEMB-SRC]` workstream.

7. `[IMP-PARITY-TEST]` — **Accepted-with-known-limitation.** No
   per-rule severity / category / tag parity assertion exists for
   SEC-030 in `RuleCatalogParityTests`. Deferred to the cross-cutting
   `[IMP-PARITY-TEST]` workstream.

## 13. Improvement suggestions (not blocking)

1. `[IMP-MEMB-SOURCE]` (**new tag**) — Some rules (SEC-030) rely on
   the closure table only; others (e.g. SEC-021, SEC-023) rely on
   both direct and closure. The asymmetry is not documented. A
   cross-cutting sweep could either standardize on closure (and
   require runtime guarantees that the closure expansion ran) or
   add explicit `direct OR closure` fallback to all rules.

2. `[IMP-NULL-SID]` (cross-cutting sweep) — SEC-030 uses
   `o.sid IS NOT NULL` explicitly, which is the correct guard. The
   audit candidate noted in the SEC-026 card (other evaluators that
   compare `dim_object.sid` via `LIKE`) is still open. SEC-030 itself
   is **not** affected because the `IS NOT NULL` filter is explicit.

3. `[IMP-CAT-WORDING]` — Reconcile the "only empty groups are
   filtered out" catalog text with the actual behavior. See §12.1.

4. `[IMP-CTX-RULEID]` — Same recommendation as SEC-026 §13.

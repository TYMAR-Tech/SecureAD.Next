## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-002
  name: "Unexpected Principal can DCSync"
  description: >-
    A principal has Replicating Directory Changes + Replicating Directory Changes All
    (or In Filtered Set) rights outside the expected Domain Controller replication path.
  severity: Critical
  category: CredentialTheft
  remediation: >-
    Remove DCSync rights from principals that do not require credential replication.
  mitre: T1003.006
  tags: ["dcsync", "credential-theft", "tier-zero"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` (the entry immediately after SEC-001).

## 2. Intended detection (plain English)

A finding must be raised for every principal that holds **both** `DCSyncGetChanges` **and** at least one of `DCSyncGetChangesAll` / `DCSyncGetChangesInFilteredSet` on the **same target object**, when the principal is not a well-known admin/system identity.

The rule fires per `(source_sid, target_object_guid)` pair, regardless of whether the target is the domain root — DCSync rights are dangerous on any naming-context root, so the evaluator does not restrict by `object_class`.

### 3.1 Effective SQL (from `EvaluateDCSync`)

```sql
SELECT e1.source_sid,
       e1.target_object_guid,
       MIN(o.distinguished_name) AS dn,
       MIN(e1.edge_id) AS edge_id,
       MAX(CASE WHEN e2.control_type = 'DCSyncGetChangesAll' THEN 1 ELSE 0 END) AS has_all,
       MAX(CASE WHEN e2.control_type = 'DCSyncGetChangesInFilteredSet' THEN 1 ELSE 0 END) AS has_filtered
FROM fact_control_edge e1
INNER JOIN fact_control_edge e2
    ON e1.source_sid = e2.source_sid
   AND e1.target_object_guid = e2.target_object_guid
INNER JOIN dim_object o ON e1.target_object_guid = o.object_guid
WHERE e1.control_type = 'DCSyncGetChanges'
  AND e2.control_type IN ('DCSyncGetChangesAll', 'DCSyncGetChangesInFilteredSet')
  AND e1.deny_cancelled = 0
  AND e2.deny_cancelled = 0
GROUP BY e1.source_sid, e1.target_object_guid
ORDER BY e1.source_sid, e1.target_object_guid
```

The `GROUP BY` guarantees one row per `(source_sid, target_object_guid)`. The `MAX(CASE ...)` columns expose which companion rights are held, and `MIN(edge_id)` provides a stable `SourceEdgeId`. This removes the prior non-determinism where two-row output collided in `INSERT OR IGNORE`.

### 3.2 Post-SQL filters (in C#)

- `if (RuleEvaluatorHelpers.IsAdminSid(sid)) continue;` — skips rows whose source is a well-known admin/system principal.
- `rightDesc` is composed deterministically from the `has_all` / `has_filtered` flags by enumerating every right held, joined with `" + "`. Examples:
  - only `GetChangesAll` companion → `"GetChanges + GetChangesAll"`
  - only `InFilteredSet` companion → `"GetChanges + GetChangesInFilteredSet"`
  - both companions → `"GetChanges + GetChangesAll + GetChangesInFilteredSet"`

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Deny-cancelled `GetChanges` edge | SQL `e1.deny_cancelled = 0` | Right not effective |
| Deny-cancelled `GetChangesAll`/`InFilteredSet` edge | SQL `e2.deny_cancelled = 0` | Right not effective |
| `GetChanges` only (no companion right) | SQL `INNER JOIN ... e2` requires a second edge | DCSync requires the pair; bare `GetChanges` is insufficient to replicate secrets |
| `GetChangesAll` only (no `GetChanges`) | SQL `e1.control_type = 'DCSyncGetChanges'` is required | Same — without `GetChanges` the principal cannot pull replication |
| Well-known admin RIDs / system SIDs | `IsAdminSid` post-SQL filter | DCs and DA/EA/BA are expected DCSync principals |

Not excluded (intentionally subject to review):

- **Broad SIDs** (`Everyone`, `Authenticated Users`, `Anonymous`) — `IsAdminSid` returns `false` for these. If captured holding both DCSync rights they will fire SEC-002.
- **Privileged-by-membership** non-RID SIDs (transitive DA) — `EvaluateDCSync` calls `IsAdminSid` only, not `IsPrivilegedPrincipal`. A transitive DA member still fires; documented and accepted (see SEC-001 §12 alignment).
- **Target `object_class`** — SQL does not restrict to `domainDNS`. DCSync on naming-context heads (`configuration`, `schema`, `dnsZone` etc.) still fires. This is intentional: DCSync rights on **any** NC head are credential-replication risks.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-002"`
- `Severity == Severity.Critical`
- `SubjectSid` = source SID from `e1.source_sid`
- `TargetKind == "object_guid"`
- `TargetId` = target object GUID (`D` format)
- `SourceEdgeId` = `fact_control_edge.edge_id` of the `GetChanges` edge (`e1.edge_id`)
- `FindingKey == "SEC-002|{SubjectSid}|{TargetId}"`
- `Detail` contains:
  - the SID
  - exactly one of: `"GetChanges + GetChangesAll"`, `"GetChanges + GetChangesInFilteredSet"`, or `"GetChanges + GetChangesAll + GetChangesInFilteredSet"` (deterministic based on the rights actually held)
  - the target DN (or GUID fallback)
  - `"can allow credential replication from the domain"`
- `ContextJson` non-null, includes:
  - `"rule_id": "SEC-002"`
  - `"control_type"` = the deterministic right enumeration string (e.g. `"GetChanges + GetChangesAll + GetChangesInFilteredSet"`)
  - `"evidence_type": "control_edge"`
  - `"target_dn"` matches the target DN
  - `"has_get_changes_all": true|false` — whether `DCSyncGetChangesAll` was held alongside `GetChanges`
  - `"has_get_changes_in_filtered_set": true|false` — whether `DCSyncGetChangesInFilteredSet` was held alongside `GetChanges`

## 12. Defects / deferred items

> Improvement tags follow the taxonomy in `docs/rules/IMPROVEMENTS.md`. Resolved items are kept for historical context (no tag needed).

1. **Non-deterministic `Detail` when a source holds both `GetChangesAll` and `InFilteredSet` on the same target.** **Resolved.** `EvaluateDCSync` was rewritten to `GROUP BY (source_sid, target_object_guid)` with `MAX(CASE ...)` companion-right flags and `MIN(edge_id)`. The `Detail` now enumerates every right actually held (e.g. `"GetChanges + GetChangesAll + GetChangesInFilteredSet"`) deterministically, and exactly one finding is produced per (source, target). Test `WhenAllThreeDCSyncRights_ThenSEC002PersistsSingleFindingWithAllRights` locks this behaviour.
2. `[IMP-CAT-WORDING]` **Catalog description vs SQL behavior.** Catalog text says "outside the expected Domain Controller replication path", implying the rule restricts to the domain root. The SQL has **no** `object_class` filter — DCSync rights on any NC head (e.g. `configurationNamingContext`, `schemaNamingContext`) also fire. **Status: accepted as a documentation-only mismatch.** Behavior is correct (DCSync on any NC head is dangerous); consider tightening the catalog wording in a future docs pass.
3. `[IMP-DEL-OBJ]` **`is_deleted` not filtered** on target. Aligned with SEC-001 §12.1 — accepted.
4. `[IMP-PRIV-MEMB-SRC]` **Privileged-by-membership not excluded** — aligned with SEC-001 §12.3 — accepted.

## 13. Suggested improvements (non-blocking)

> Improvement tags follow the taxonomy in `docs/rules/IMPROVEMENTS.md`. Items marked **Implemented** are historical and untagged.

- **Expose companion-right flags in `ContextJson`.** **Implemented.** `CreateEdgeFinding` now accepts an `extraContext` dictionary (snake_case keys, JSON-serialisable values) that merges into the emitted context. SEC-002 uses it to surface `has_get_changes_all` and `has_get_changes_in_filtered_set` booleans, so downstream consumers no longer have to parse the `Detail` string. The merge respects the reserved base schema — callers cannot overwrite `rule_id`, `source_sid`, etc. This extension point is now available to every control-edge rule.
- **Switch `ContextJson` encoder to `UnsafeRelaxedJsonEscaping`.** **Implemented.** Discovered while locking the `ContextJson` assertions for SEC-002: the default HTML-safe encoder was escaping `+` as `\u002B` in every rule's `ContextJson`. The blobs live in SQLite and are rendered in the UI/reports (never embedded in HTML), so the safer encoder was just clutter. Now all evaluators emit human-readable JSON. No call-site changes required.
- `[IMP-CAT-WORDING]` **Tighten catalog wording.** Change `description` to "A principal has Replicating Directory Changes plus GetChangesAll or GetChangesInFilteredSet on a naming-context head (domain, configuration, or schema) outside the expected DC replication path." — _pending your call._
- `[IMP-COV-REASON]` **Surface explicit Deny suppression in `coverage_reason`.** **Resolved by decision \u2014 will not implement as per-principal findings.** When a principal would hold DCSync rights but the only reason they do not fire SEC-002 is `deny_cancelled = 1` on an edge (a deny ACE neutralised the allow via DACL ordering), the suppression is not surfaced as evidence today. **Decision:** a deny that cancels a DCSync grant is *working* security control, not a defect \u2014 emitting a finding for every deny-suppressed (principal, target) pair would convert correct defensive configuration into noise (deny-cancelled edges are common on real domains via inheritance + explicit denies). The suppressed edges are **retained and directly queryable** in `fact_control_edge` (`deny_cancelled = 1`), so the data is not lost. SEC-002 itself behaves correctly. If a future need arises, the cheapest useful form is a **run-level aggregate** (e.g. "N principals had DCSync deny-suppressed") in the coverage summary / `dim_run.notes` \u2014 not per-principal findings. No code change.

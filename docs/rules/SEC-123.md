## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-123
  name: "Write SIDHistory Permission"
  description: >-
    A principal has WriteProperty on sIDHistory, enabling SID injection attacks for privilege escalation across trust boundaries.
  severity: Critical
  category: PrivilegeEscalation
  remediation: >-
    Remove unnecessary WriteProperty permissions on sIDHistory.
  mitre: T1134.005
  tags: ["sid-history", "sid-injection", "tier-zero"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 522–531.

## 2. Intended detection (plain English)

Fire one Critical finding per `(non-privileged trustee, target object)` pair when an explicit allow ACE on the target grants `WriteProperty` (`access_mask & 32`) against the `sIDHistory` attribute — conferred **either** by a sIDHistory-scoped object ACE (`object_type_guid = sIDHistory`) **or** by a non-object "write all properties" / `GenericAll` grant (`object_type_guid IS NULL`, whose generic-expanded mask carries the WriteProperty bit). On modern DCs `sIDHistory` is `System-Only = False` (since Server 2003) and is **not** a confidential attribute, so an all-properties write genuinely confers the SID-injection capability — unlike SEC-090's confidential LAPS attribute, there is no CONTROL_ACCESS overlay that would block a plain property write. Writing `sIDHistory` lets an attacker stamp a privileged SID into a non-privileged identity, giving the trustee a Tier-0 token at the next logon. The finding's `write_scope` context field records which path conferred the capability (`specific` vs `all_properties`). Well-known admin trustees and trustees that are already privileged-by-membership in tier-0 groups must not fire (they're expected to manage SIDs by design — the finding would be noise). Inherited ACEs are out of scope (the rule reports explicit grants, the source of action). Tombstoned (`is_deleted = 1`) targets must not fire even if a stale `fact_ace` row joins. Deny ACEs (`ace_type` 1 / 6) must not fire. The target class filter (`user` / `computer` / `inetOrgPerson` / gMSA) applies to both paths so an all-properties write on a non-principal (e.g. a group) does not fire.

### 3.1 Effective SQL (copied from code)

```sql
SELECT a.trustee_sid, a.object_guid, o.distinguished_name,
       MAX(CASE WHEN a.object_type_guid = $guid THEN 1 ELSE 0 END) AS has_specific,
       MAX(CASE WHEN a.object_type_guid IS NULL THEN 1 ELSE 0 END) AS has_broad
FROM fact_ace a
INNER JOIN dim_object o ON a.object_guid = o.object_guid
LEFT JOIN fact_control_edge e ON ... AND e.deny_cancelled = 0
WHERE (a.object_type_guid = $guid          -- sIDHistory schemaIDGUID (specific write)
       OR a.object_type_guid IS NULL)       -- write-all-properties / GenericAll (broad write)
  AND (a.access_mask & 32) != 0            -- ADS_RIGHT_DS_WRITE_PROP
  AND a.ace_type IN (0, 5)                 -- AccessAllowed / AccessAllowedObject
  AND a.is_inherited = 0
  AND o.is_deleted = 0
  AND o.object_class IN ('user','computer','inetOrgPerson','msDS-GroupManagedServiceAccount')
  AND NOT EXISTS (... deny_cancelled = 1 ...)
GROUP BY a.trustee_sid, a.object_guid, o.distinguished_name
ORDER BY a.trustee_sid, a.object_guid
```

Bound parameter `$guid` = `17eb4278-d167-11d0-b002-0000f80367c1` (sIDHistory schemaIDGUID per Microsoft adschema `a-sidhistory`). `has_specific` selects `write_scope` (`specific` when the sIDHistory-scoped ACE is present, else `all_properties`). [IMP-CTRL-SCOPE] widening — see §13.

### 3.2 Post-SQL filters (in C#)

- `IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — drops well-known admin RIDs (RID 500, 502, 512, 516, 518, 519, 521, …) **and** trustees whose SID appears in the precomputed transitive privileged set (DA / EA / Schema Admins / Builtin Administrators members).

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Non-sIDHistory attributes | SQL `a.object_type_guid = $guid` | Rule scope is the sIDHistory attribute; WriteProperty on other attributes is covered by SEC-024 / SEC-090 / dedicated rules. |
| Read access only | SQL `(a.access_mask & 32) != 0` | sIDHistory is readable via the global catalog by design; only WriteProperty enables SID injection. |
| Deny / audit ACEs | SQL `a.ace_type IN (0, 5)` | Deny ACEs (1/6) and audit (2/7) cannot grant WriteProperty. |
| Inherited ACEs | SQL `a.is_inherited = 0` | Rule reports explicit, source-of-action grants; inheritance is the propagation of an upstream finding and would produce derivative noise. |
| Deleted targets | SQL `o.is_deleted = 0` | Tombstoned targets cannot host an attack; lingering ACE rows would be noise. |
| Well-known admin trustees | C# `IsAdminSid(sid)` (inside `IsPrivilegedPrincipal`) | DA / EA / SA / BA already control sIDHistory by design; not actionable. |
| Privileged-by-membership trustees | C# `context.PrivilegedSids.Contains(sid)` (inside `IsPrivilegedPrincipal`) | Transitive DA / EA members inherit the same trust; surfacing SID writes from these principals is noise. |

Not excluded (intentionally subject to review):

- Cross-domain trustees (foreign-domain SIDs in DACL). Considered in scope: cross-trust SID injection is the canonical attack here.
- Generic-class targets. The SQL constrains `object_class IN ('user', 'computer', 'inetOrgPerson', 'msDS-GroupManagedServiceAccount')` (`[IMP-TGT-CLASS]` resolved).
- `deny_cancelled` semantics are not applied because the rule reads `fact_ace` directly. A deny ACE that neutralises an upstream allow via DACL ordering is currently surfaced. See §13 `[IMP-ACE-VS-EDGE]`.

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Wrong sIDHistory schemaIDGUID hardcoded (resolved on rule).** `EvaluateWriteSidHistory` previously hardcoded `bf967a6d-0de6-11d0-a285-00aa003049e2` as the sIDHistory GUID. Per Microsoft Learn (`adschema/a-userparameters` and `adschema/a-sidhistory`) that GUID is `userParameters`; the correct sIDHistory schemaIDGUID is `17eb4278-d167-11d0-b002-0000f80367c1`. The bug produced a complete miss on the intended attack (no real sIDHistory writes ever fired) plus noisy positives on benign WriteProperty grants over `userParameters`. Fixed inline this session; pinned by `WhenWritePropertySidHistory_ThenSEC123Fires` (uses the correct GUID and now fires) and `WhenWritePropertySidHistoryWithLegacyUserParametersGuid_ThenSEC123DoesNotFire` (regression for the historic value). Note: `src/SecureAD.Core/Schema/WellKnownGuids.cs:78` separately maps `sIDHistory` to a third value (`9a9a0220-4a5b-11d1-a9c3-0000f80367c1`, which per adschema is `userSharedFolderOther`) — that table feeds `dim_guid_map` enrichment, not findings, so it's out of scope for SEC-123 but tracked as a cross-cutting `[IMP-WK-GUID]` candidate (see §13).
2. **Tombstone gap (resolved on rule).** SQL did not filter `o.is_deleted = 0`, so lingering `fact_ace` rows against tombstoned targets would surface as Critical findings. Same defect class fixed for SEC-122 in the previous session. Fixed inline; pinned by `WhenSidHistoryAceOnDeletedTarget_ThenSEC123DoesNotFire`. Cross-cutting sweep against the other sibling rules in `AdvancedRuleEvaluator` (SEC-124, SEC-201, SEC-204) is still open — tracked under `[IMP-DEL-OBJ]`.
3. **Privileged-by-membership trustees previously surfaced (resolved on rule).** Evaluator filter was `IsAdminSid(sid)` only, ignoring `context.PrivilegedSids`. Sibling rules SEC-120 / SEC-121 in the same evaluator already use `IsPrivilegedPrincipal(sid, context.PrivilegedSids)`. Brought into parity inline this session; pinned by `WhenPrivilegedByMembershipTrusteeWritesSidHistory_ThenSEC123DoesNotFire`. Cross-cutting sweep tracked under `[IMP-PRIV-MEMB-SRC]`.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-DEL-OBJ]` — Cross-cutting sweep: extend `o.is_deleted = 0` consistently across SEC-124, SEC-201, SEC-204 (other rules in `AdvancedRuleEvaluator`). Resolved on SEC-123, but the sibling sweep is still open.
2. `[IMP-PRIV-MEMB-SRC]` — Resolved on SEC-123 (now uses `IsPrivilegedPrincipal`). Cross-cutting sweep against the other audited rules listed under this tag remains open.
3. `[IMP-DN-ENRICH]` — `Detail` interpolates `dn ?? objectGuid.ToString()`. When `dn` is null, the operator sees only a GUID, which is unactionable for sIDHistory remediation. The trustee SID is also surfaced raw with no `sam_account_name` join. Parity with SEC-100/101/102/120/121/122.
4. `[IMP-PARITY-TEST]` — No per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-123. Same gap is open across the audited backlog.
5. `[IMP-CTX-RULEID]` — `CreateEdgeFinding` already stamps `rule_id` into `ContextJson`, so this rule is fine on its own — but the sibling delegation-style rules in `AdvancedRuleEvaluator` (SEC-122) do not, and the cross-cutting tag still applies until `CreateDelegationFinding` is brought into parity.
6. `[IMP-MITRE-FIT]` — Catalog maps SEC-123 to `T1134.005` (Access Token Manipulation: SID-History Injection). This is a closer fit than the SEC-120/121/122 mappings, but the technique is about *exploiting* an injected SID, not about *granting WriteProperty on sIDHistory*. Arguably the precondition step is `T1098` (Account Manipulation) followed by `T1134.005` at exploit time. Same cross-cutting tag.
7. `[IMP-CTRL-SCOPE]` — **RESOLVED by widening (decision reversed on evidence).** SEC-123 originally keyed only on `fact_ace` where `object_type_guid = sIDHistory`, and this item previously argued for a documented partition (do not widen; assume broad grants are caught elsewhere). **Lab validation disproved that assumption:** a real audit DB (root + 2 children) had 3 non-admin principals — including `Everyone` (`S-1-1-0`) on two computers — holding a non-object `WriteAllProperties` ACE on security principals, none of which surfaced under any rule. Because `sIDHistory` is `System-Only = False` on modern DCs (Server 2003+) and is not confidential (no CONTROL_ACCESS overlay, unlike SEC-090 LAPS), a generic all-properties / `GenericAll` write genuinely confers the SID-injection capability (verified against Microsoft adschema `a-sidhistory` plus the property-ACE inheritance semantics). The query now also matches `object_type_guid IS NULL AND access_mask & 0x20` (which `GenericAll` generic-expanded mask satisfies), keeps the same class filter and admin exclusion, and records `write_scope` (`specific` | `all_properties`). Pinned by `WhenWriteAllPropertiesOnUser_ThenSEC123FiresWithAllPropertiesScope`, `WhenGenericAllOnUser_ThenSEC123Fires`, `WhenBroadPrincipalWritesAllPropertiesOnUser_ThenSEC123Fires` (the `Everyone` lab regression), `WhenReadAllPropertiesOnlyOnUser_ThenSEC123DoesNotFire`, `WhenAllPropertiesWriteTargetsGroup_ThenSEC123DoesNotFire`, and `WhenBothSpecificAndBroadSidHistoryWrite_ThenSEC123FiresOnceAsSpecific`. Lab: fixed predicate yields exactly the 3 expected findings (was 0).
8. `[IMP-TGT-CLASS]` — **RESOLVED.** The SQL now constrains `o.object_class IN ('user', 'computer', 'inetOrgPerson', 'msDS-GroupManagedServiceAccount')` so a malformed `dim_object` row with `object_class = 'group'` no longer surfaces a finding (`sIDHistory` does not apply to groups). Pinned by `WhenSidHistoryWriteTargetsGroup_ThenSEC123DoesNotFire`.
9. `[IMP-COV-MEMB]` — `RuleCoverageRequirements["SEC-123"]` does not include `CoverageModules.GroupMembership`, but `IsPrivilegedPrincipal` consumes `context.PrivilegedSids` (built from `fact_group_membership_closure`). When `GroupMembership` capture is incomplete, the privileged set silently degrades and N7-style positives could become false negatives without a `coverage_reason`. Same defect class as SEC-024 / SEC-025 / SEC-080 / SEC-081 / SEC-090.
10. `[IMP-ACE-VS-EDGE]` — Rule reads `fact_ace` directly instead of `fact_control_edge`, so it does not apply `deny_cancelled` semantics (a deny ACE that neutralises an earlier allow via DACL ordering still surfaces), the finding carries `SourceEdgeId == null` (no control-edge provenance), and the rule does not benefit from any future normalization at the edge layer. Resolution per the tag's standard sketch.
11. `[IMP-WK-GUID]` — *(new tag candidate — add to `IMPROVEMENTS.md` if it gains a second referent)* — `src/SecureAD.Core/Schema/WellKnownGuids.cs` declares well-known schema/control-access GUIDs by hand. Three of those entries were independently introduced for sIDHistory across the codebase: `bf967a6d-…` (userParameters, in the SEC-123 evaluator), `9a9a0220-…` (userSharedFolderOther, in `WellKnownGuids.cs:78`), and the correct `17eb4278-…`. Either centralize all schemaIDGUID literals into one strongly-typed catalog (and reference by name from evaluators) or backfill a per-attribute test that asserts the recorded GUID matches the Microsoft adschema authoritative value. The latter is the cheaper guard.

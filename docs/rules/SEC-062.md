## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-062
  name: "Domain Users in Local Admins Equivalent"
  description: >-
    Domain Users or similar broad group has administrative access.
  severity: High
  category: ConfigurationHygiene
  remediation: >-
    Remove broad groups from administrative access.
  tags: ["domain-users", "excessive-admins"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 303–311. No
`mitre` attribute on the catalog entry.

## 2. Intended detection (plain English)

Fire one finding per `(member_sid, group_sid)` direct-membership pair where:

- the **group** is an admin-equivalent privileged group — Domain Admins
  (RID 512), Schema Admins (RID 518), Enterprise Admins (RID 519), or
  `BUILTIN\Administrators` (`S-1-5-32-544`); and
- the **member** is a broad / anonymous principal — Domain Users
  (RID 513), `Everyone` (`S-1-1-0`), `Anonymous` (`S-1-5-7`),
  `Authenticated Users` (`S-1-5-11`), or `BUILTIN\Users`
  (`S-1-5-32-545`).

The catalog name says "Local Admins Equivalent" but the rule operates
purely against domain-side privileged groups; "local" is a misnomer
inherited from generic AD parlance (see §12.1 / `[IMP-CAT-WORDING]`).
Severity is fixed at `High`.

### 3.1 Effective SQL (copied from code)

```sql
SELECT g.member_sid, g.group_sid, o.object_guid, o.distinguished_name
FROM fact_group_membership_direct g
INNER JOIN dim_object o ON g.group_sid = o.sid
WHERE (g.group_sid LIKE '%-512' OR g.group_sid LIKE '%-519'
    OR g.group_sid LIKE '%-518' OR g.group_sid = 'S-1-5-32-544')
  AND (g.member_sid LIKE '%-513'
    OR g.member_sid = 'S-1-1-0'
    OR g.member_sid = 'S-1-5-7'
    OR g.member_sid = 'S-1-5-11'
    OR g.member_sid = 'S-1-5-32-545')
  AND o.is_deleted = 0
ORDER BY g.group_sid, g.member_sid
```

### 3.2 Post-SQL filters (in C#)

- _None._ Every row returned by the SQL is emitted as a finding; no
  in-code exclusions, no severity tiering, no fallback to
  closure-based membership.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Memberships in groups other than DA / SA / EA / BUILTIN\Administrators | SQL `g.group_sid LIKE '%-512' OR '%-519' OR '%-518' OR = 'S-1-5-32-544'` | These four are the canonical "admin-equivalent" set per AD threat-model docs. Operator groups (Account / Server / Backup / Print / Replicators) are intentionally out of scope; the catalog wording targets _admin_ membership, and operator groups are reviewed by SEC-030 instead. |
| Non-broad members (regular users, service accounts, individual SIDs) | SQL `g.member_sid LIKE '%-513' OR IN ('S-1-1-0','S-1-5-7','S-1-5-11','S-1-5-32-545')` | A regular user directly in Domain Admins is normal Tier-0 RBAC, not a SEC-062 hit. SEC-062 specifically targets _broad / anonymous_ principals being granted admin equivalence. |
| Target group marked deleted (`is_deleted = 1`) | SQL `o.is_deleted = 0` (added in this audit) | A tombstoned admin group cannot grant live access; emitting it is noise. Mirrors the SEC-061 audit fix. |
| Target group with no `dim_object` row | `INNER JOIN dim_object` on `group_sid = o.sid` | Without a captured group object the finding has no remediable identity (no GUID, no DN). Treated as a capture coverage gap (`Objects` module). |
| Transitive (closure-only) memberships | Only `fact_group_membership_direct` is read | Per-row remediation is "remove this direct edge". Closure expansion would conflate "Domain Users is nested via a benign group" with "Domain Users is directly granted". See §8 E9 and the `WhenBroadPrincipalIsMemberOfDomainAdminsViaClosureOnly_ThenSEC062DoesNotFire` pin test. |

Not excluded (intentionally subject to review):

- The broad SIDs themselves — they are the canonical positive subjects.
- Disabled / locked-out states on the group target — `is_deleted` is the
  only viability gate; a disabled admin group is still a policy
  violation. (Disabled admin _groups_ are not a normal AD state.)
- Cross-domain trust principals — if `fact_group_membership_direct`
  contains an FSP-resolved foreign-domain member matching a broad-SID
  pattern (very unusual; FSPs typically resolve to per-domain accounts),
  the finding still surfaces. Accepted: such a configuration is
  unambiguously a misconfiguration regardless of which forest the
  broad principal originated in.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-062"`
- `Severity == High`
- `SubjectSid` = the broad member's SID (never empty for emitted findings — see E11)
- `TargetKind == "object_guid"`
- `TargetId` = the admin-equivalent group's GUID in `D` format
- `SourceEdgeId` = `null` (delegation-style finding)
- `SourcePathId` = `null`
- `FindingKey == "SEC-062|{member_sid}|{group_guid}"`
- `Detail` contains: `"Broad principal {member_sid} is direct member of admin group "` followed by `group_dn ?? group_sid`
- `ContextJson` non-null and contains:
  - `"evidence_type": "group_membership"`
  - `"condition": "BroadPrincipalInAdminEquivalentGroup"`
  - `"member_sid"`: broad member SID
  - `"group_sid"`: admin-equivalent group SID
  - `"group_dn"`: DN string or null
  - `"object_guid"`: group GUID in `D` format
  - **No `"rule_id"` key** — `CreateDelegationFinding` does not inject it (cross-cutting `[IMP-CTX-RULEID]`).

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Catalog name vs. behaviour** `[IMP-CAT-WORDING]` — the catalog name
   says "Domain Users in **Local** Admins Equivalent" but the rule
   operates against **domain** privileged groups (Domain Admins,
   Schema Admins, Enterprise Admins, `BUILTIN\Administrators`). "Local"
   is a misleading carry-over from generic AD parlance.
   `Accepted-with-known-limitation`: rename to "Broad principal in
   admin-equivalent group" and rewrite the description to enumerate
   both the broad-principal set and the admin-equivalent group set.

2. **Broad-member set expanded** — the original SQL covered only
   `%-513`, `S-1-1-0`, `S-1-5-11`. This audit added `S-1-5-7`
   (Anonymous) and `S-1-5-32-545` (`BUILTIN\Users`) to match the
   classifier in `RuleEvaluatorHelpers.IsBroadPrincipalSid`. New
   pin tests in `WhenBroadPrincipalIsDirectMemberOfDomainAdmins_ThenSEC062Fires`
   protect the wider set. Resolved — no tag.

3. **Tombstoned target groups surfaced** — the original SQL did not
   filter `o.is_deleted`. Fixed in this audit; SQL now includes
   `AND o.is_deleted = 0`. Pin test
   `WhenAdminEquivalentGroupIsTombstoned_ThenSEC062DoesNotFire` protects
   the new behaviour. Resolved — no tag.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-DN-ENRICH]` — `Detail` and `ContextJson` carry SIDs and the
   target group DN but no `sam_account_name` for the broad member.
   Broad principals are well-known, so this is the lowest-value
   enrichment of the family; still worth doing for consistency.

2. `[IMP-CTX-RULEID]` — `CreateDelegationFinding` does not inject a
   top-level `"rule_id"` field into `ContextJson`. Cross-cutting;
   tracked against every delegation-style rule.

3. `[IMP-PARITY-TEST]` — `RuleCatalogParityTests` does not assert
   per-rule that SEC-062's emitted severity matches the catalog default
   (`High`), that the category is `ConfigurationHygiene`, that the tags
   are `["domain-users", "excessive-admins"]`, or that `mitre` is
   unset. Generic across most rules.

4. `[IMP-DEL-OBJ]` — SEC-062 now filters `is_deleted` on the **target**
   group, but the broader sweep across all evaluators that also need
   to filter on the **member** side (when a SID-only direct edge
   survives a tombstoned member) is still open.

5. `[IMP-MEMB-SOURCE]` — SEC-062 is explicitly direct-only (the rule's
   "membership shape" intent matches this), but the asymmetry with
   SEC-030 (closure-only) is worth documenting as part of the
   cross-cutting standardization. Belongs to the same sweep that
   pinned SEC-030's closure choice.

6. `[IMP-BROAD-DRIFT]` — the SEC-062 inline SQL list of broad-principal
   patterns (`%-513`, `S-1-1-0`, `S-1-5-7`, `S-1-5-11`, `S-1-5-32-545`)
   and the C# classifier `RuleEvaluatorHelpers.IsBroadPrincipalSid`
   (which derives the same set from `BroadSids` + RID-513 + `S-1-5-32-545`)
   are now in agreement but still maintained separately. SEC-060
   suffers from the same shape; consolidating both rules onto a single
   `BroadPrincipalCatalog` is one cross-cutting fix.

7. `[IMP-KEY-COLLAPSE]` — `FindingKey = "SEC-062|{member_sid}|{group_guid}"`
   is the correct grain (one per direct membership edge), so no
   collapse risk today. Listed here only because the family-wide
   discussion of key shape should still consider SEC-062 for
   consistency.

8. **`mitre` attribute absent** — most ConfigurationHygiene rules in the
   catalog also lack a MITRE id, so this is not a SEC-062-specific
   issue. Consider an ATT&CK mapping pass after the rule audit
   completes (could become `[IMP-MITRE]` if it gains scope).

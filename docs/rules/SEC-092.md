## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-092
  name: "LAPS Password Rotation Stale"
  description: >-
    A computer has LAPS enabled but the password expiration timestamp is in the past relative to
    the audit capture time. This indicates the LAPS agent is not rotating the password as expected,
    possibly due to GPO misconfiguration, agent failure, or network connectivity issues.
  severity: High
  category: ConfigurationHygiene
  remediation: >-
    Verify the LAPS GPO is applied to the computer, the LAPS agent is running, and the computer
    can reach a domain controller to update the password. Check Event Log on the computer for LAPS errors.
  mitre: T1078.002
  tags: ["laps", "rotation", "stale", "hygiene"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 445–454.

## 2. Intended detection (plain English)

For every non-deleted, non-DC computer with a `LapsEnabled` delegation row whose `target` is `Windows` or `Legacy`, decode the stored FILETIME from `details` and fire when the resulting UTC instant is `<= captured_utc`. The semantic is "the LAPS agent should have rotated by now but the captured snapshot still shows the same (past) expiration", indicating an agent / GPO / connectivity failure. Severity is `High` because a stale password means the local administrator credential is no longer cycled — a likely-stale shared secret across machines undercuts the whole point of LAPS.

## 4. Effective SQL executed (after defect fixes)

```sql
SELECT o.object_guid, o.distinguished_name, laps.target, laps.details, o.captured_utc
FROM dim_object o
INNER JOIN dim_delegation laps ON o.object_guid = laps.object_guid
                              AND laps.delegation_type = 'LapsEnabled'
                              AND laps.target IN ('Windows', 'Legacy')
WHERE o.object_class = 'computer' AND o.is_deleted = 0
  AND o.distinguished_name NOT LIKE '%,OU=Domain Controllers,%'
  AND laps.details IS NOT NULL
  AND CAST(laps.details AS INTEGER) > 0
  AND DATETIME((CAST(laps.details AS INTEGER) / 10000000) - 11644473600, 'unixepoch') <= DATETIME(o.captured_utc)
ORDER BY o.distinguished_name, laps.target
```

FILETIME conversion: SQLite has no native FILETIME arithmetic, so the SQL converts the 100-ns-tick FILETIME to Unix epoch seconds via `(filetime / 10000000) - 11644473600` (11,644,473,600 seconds between 1601-01-01 and 1970-01-01), then `DATETIME(..., 'unixepoch')` produces a `'YYYY-MM-DD HH:MM:SS'` string. The C# layer re-decodes the raw FILETIME via `DateTimeOffset.FromFileTime` for the human-readable `password_expiration_utc` field.

## 5. Defects discovered and fixed this session

| # | Description | Defect risk | Fix |
| --- | --- | --- | --- |
| 1 | Main path DC exclusion used `o.sam_account_name NOT IN (SELECT sam FROM DCs WHERE sam IS NOT NULL)` — identical to the SEC-091 defect fixed last session. A DC whose own `sam_account_name` is `NULL` bypassed the subquery and surfaced a false-positive "rotation stale" finding. | False positive on DCs. | Replaced the sam-account-name subquery with `o.distinguished_name NOT LIKE '%,OU=Domain Controllers,%'`. |
| 2 | The comparison `DATETIME(...,'unixepoch') <= o.captured_utc` was a **lexicographic string comparison**, not a datetime comparison. `DATETIME(...,'unixepoch')` produces `'YYYY-MM-DD HH:MM:SS'` (space separator) while `o.captured_utc` is stored as ISO-8601 `'YYYY-MM-DDTHH:MM:SSZ'` (`T` separator + `Z` suffix). At position 10 the space (`0x20`) sorts before `T` (`0x54`), so for the **same instant** the converted FILETIME string compares as less-than `captured_utc` — ambiguous boundary behaviour, and equal-instant comparisons could miss firing under different SQLite text collations. | Boundary-instant inconsistency; potential silent misses. | Wrapped the right-hand side in `DATETIME(o.captured_utc)` so SQLite normalizes both operands and performs an actual datetime comparison. |

Both fixes are pinned by dedicated regression tests in §7.

| Exclusion | Where applied | How |

| Computers whose LAPS expiration is in the future | SQL `DATETIME(...) <= DATETIME(captured_utc)` | Healthy LAPS rotations do not fire. |

## 10. Severity rationale

`High` matches `rules.yaml` and is loaded via `BuiltInRules.ById["SEC-092"].DefaultSeverity`. A failing rotation means the captured snapshot's local administrator credential is no longer being cycled, so any prior credential exposure (e.g. an old GPO leak, a now-departed admin) persists indefinitely. That justifies `High` even though it remains a hygiene finding rather than an active credential disclosure.

## 13. New cross-cutting items captured this session

- `[IMP-DATETIME-COMPARE]` — Evaluator SQL compares the output of `DATETIME(..., 'unixepoch')` (format `'YYYY-MM-DD HH:MM:SS'`) to a raw TEXT column storing ISO-8601 with a `T` separator and `Z` suffix. Without wrapping the column in `DATETIME(...)`, SQLite performs a **lexicographic** comparison that produces inconsistent boundary results. Affects SEC-092 today; audit every evaluator that compares a computed `DATETIME()` value to a stored ISO-8601 TEXT column.
- `[IMP-FILETIME-SQL]` — FILETIME-to-Unix conversion is hard-coded as `(value / 10000000) - 11644473600` in multiple evaluators. Move to a SQLite scalar function or a normalized capture-time column (`dim_delegation.expiration_utc`) so the conversion lives in one place and survives schema migrations.
- `[IMP-DETAIL-UNICODE]` — `Detail` strings contain Unicode punctuation (em-dash `—`) that breaks ASCII-only downstream consumers and complicates substring assertions in tests. Standardize on ASCII (`-` or `--`) for machine-readable detail text and keep Unicode formatting in the UI layer only.

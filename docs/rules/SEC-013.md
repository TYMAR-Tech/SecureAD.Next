## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-013
  name: "RBCD Configured on Privileged Resource"
  description: >-
    Resource-based constrained delegation is configured on a privileged resource, allowing delegated principals to impersonate users to it.
  severity: Critical
  category: Delegation
  remediation: >-
    Review and restrict accounts in msDS-AllowedToActOnBehalfOfOtherIdentity on privileged resources.
  mitre: T1558.001
  tags: ["kerberos", "rbcd", "delegation"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 102–111.

## 2. Intended detection (plain English)

A finding must be raised for every captured object that:

1. Has resource-based constrained delegation configured — i.e. its
   `msDS-AllowedToActOnBehalfOfOtherIdentity` attribute is populated (modelled as a
   row in `dim_delegation` with `delegation_type = 'RBCD'`); **and**
2. Is itself a **privileged resource** — i.e. its object SID identifies a
   well-known privileged principal (RID 500/502/512/516/518/519/520/521/526/527,
   a BUILTIN admin SID, SYSTEM, etc.) or is a transitive member of one of the
   well-known privileged groups built by `FindingsService.BuildPrivilegedSidSet`.

Catalog severity is `Critical`. The catalog wording also promises insight into
"delegated principals"; the evaluator now parses the security descriptor and
surfaces the trustee SIDs as `delegated_trustee_sids` in `ContextJson`
(`[IMP-RBCD-TRUSTEE]` resolved — see §12.2).

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid, d.details
FROM dim_delegation d
INNER JOIN dim_object o ON d.object_guid = o.object_guid
WHERE d.delegation_type = 'RBCD'
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

```csharp
if (sid is null || !RuleEvaluatorHelpers.IsPrivilegedPrincipal(sid, context.PrivilegedSids))
    continue;
```

- **Null-SID skip.** Rows where `dim_object.sid` is null are dropped (no actionable
  subject can be emitted).
- **Privileged-resource gate.** `IsPrivilegedPrincipal` returns true when:
  - The SID is in `PrivilegedSystemSids` (SYSTEM, Enterprise DCs, BUILTIN admin
    groups, Creator Owner, Self), **or**
  - The trailing RID is in `AdminRids` = `{500, 502, 512, 516, 518, 519, 520, 521, 526, 527}`, **or**
  - The SID was added to `context.PrivilegedSids` by `BuildPrivilegedSidSet`
    via transitive `fact_group_membership_closure` membership in a group whose
    `group_sid` ends in one of `{512, 516, 518, 519, 526, 527}` or equals one of
    `{S-1-5-32-544, -548, -549, -550, -551}`.

### 3.3 Finding shape

- `RuleId == "SEC-013"`, `Severity == Severity.Critical` (resolved via
  `SeverityOf` → `BuiltInRules`).
- `SubjectSid` = the resource's `dim_object.sid` (never empty thanks to the
  null-SID skip).
- `TargetKind == "object_guid"`, `TargetId` = the resource's `object_guid` in
  `D` format. The evaluator treats the **resource itself** as the target; the
  delegated trustee principals are surfaced in `ContextJson.delegated_trustee_sids`
  rather than as separate targets (`[IMP-RBCD-TRUSTEE]` resolved — see §12.2).
- `FindingKey == "SEC-013|{SubjectSid}|{TargetId}"`.
- `Detail = $"RBCD configured on privileged resource {dn ?? guid}"`.
- `ContextJson`: `evidence_type = "delegation"`, `delegation_type = "RBCD"`,
  `object_dn`, `object_guid`, `details` (the raw base64-encoded
  `msDS-AllowedToActOnBehalfOfOtherIdentity` value from `dim_delegation.details`).

### 3.4 Privileged-resource scope

| Resource SID | Privileged? | Why |
| --- | --- | --- |
| RID 500/512/518/519 etc. (well-known admin RIDs) | Yes | `IsAdminSid` RID match. |
| RID 502 (krbtgt) | Yes | `IsAdminSid` RID match. |
| RID 516 (Domain Controllers group / DC computer transitive member) | Yes | Either direct RID 516 SID or closure membership in RID-516 group. |
| `S-1-5-32-544` (BUILTIN\Administrators) | Yes | `PrivilegedSystemSids`. |
| `S-1-5-18` (SYSTEM) | Yes | `PrivilegedSystemSids`. |
| Non-RID account that is a transitive member of Domain Admins, Enterprise Admins, Schema Admins, BUILTIN\Administrators, etc. | Yes | `BuildPrivilegedSidSet` closure lookup. |
| Any other principal SID with no privileged membership | No | Skipped by `IsPrivilegedPrincipal`. |
| `dim_object.sid IS NULL` | n/a | Skipped by null-SID check. |

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Non-RBCD delegation rows (`Constrained`, `Unconstrained`, `SPN`, `AdminCount`, etc.) | SQL `delegation_type = 'RBCD'` | Out of scope — covered by SEC-010/011/012/020/…. |
| Resources whose SID is null | C# `if (sid is null ... continue)` | Cannot classify a null SID; emitting a finding with empty `SubjectSid` would produce a degenerate finding key. |
| Resources whose SID does not match any privileged criterion | C# `!IsPrivilegedPrincipal(sid, ...)` | The catalog scope is "on a privileged resource". Non-privileged resources are out of scope for SEC-013 (and are partially picked up by SEC-122 when the resource happens to be a DC). |

Not excluded (intentionally subject to review):

- **Deleted objects** — `is_deleted` not filtered. `[IMP-DEL-OBJ]`.
- **Disabled accounts** — `userAccountControl & ACCOUNTDISABLE` not consulted.
- **Domain Controllers (RID 516 / Domain Controllers group)** — fire on SEC-013
  *and* on SEC-122 (RBCD on DC). Both Critical; produces duplicate findings on
  the same DC + RBCD row. `[IMP-DUP-RULE]` documents the overlap.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-013"`
- `Severity == Severity.Critical`
- `SubjectSid` = the resource's SID (never empty — null-SID rows are skipped)
- `TargetKind == "object_guid"`
- `TargetId` = the resource `object_guid` (`D` format)
- `SourceEdgeId == null` (no edge provenance — pure delegation row)
- `FindingKey == "SEC-013|{SubjectSid}|{TargetId}"`
- `Detail = $"RBCD configured on privileged resource {dn ?? guid}"`
- `ContextJson` is non-null and contains:
  - `"evidence_type": "delegation"`
  - `"delegation_type": "RBCD"`
  - `"object_dn"` matches the resource DN (or null)
  - `"object_guid"` matches the GUID in `D` format
  - `"details"` matches the raw `dim_delegation.details` value (the
    base64-encoded `msDS-AllowedToActOnBehalfOfOtherIdentity` SD, or null when
    the writer recorded none)

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`).
> Resolved items are kept for historical context and are intentionally untagged.

1. **(Resolved this pass)** Method name `EvaluateRbcdFromNonAdmin` was inverted
   relative to its behaviour and to the catalog wording. The method requires the
   **resource (subject) SID** to be privileged; the trustees (which would be the
   "non-admin" source) are not even parsed. Renamed in code to
   `EvaluateRbcdOnPrivilegedResource` and a doc comment was added pointing at
   `[IMP-RBCD-TRUSTEE]`. No catalog change needed.
2. `[IMP-RBCD-TRUSTEE]` **RBCD trustees enumerated.** **Status: RESOLVED.**
   `msDS-AllowedToActOnBehalfOfOtherIdentity` is a security descriptor whose
   DACL lists the trustees that may impersonate to the resource. The capture
   pipeline stores the raw base64 SD in `dim_delegation.details`; the new
   `RuleEvaluatorHelpers.ExtractRbcdTrusteeSids` helper decodes it (via the
   existing `SecurityDescriptorParser`) and returns the distinct DACL trustee
   SIDs, which SEC-013 surfaces as `delegated_trustee_sids` in `ContextJson`
   (sorted ordinally for stable output). Malformed / empty / non-base64 SDs
   degrade to an empty array without throwing. Resolved evaluator-side only —
   no schema or capture-pipeline change. Pinned by
   `WhenRbcdSdHasTrustees_ThenSEC013EnumeratesDelegatedTrusteeSids` and
   `WhenRbcdDetailsIsMalformed_ThenSEC013EmitsEmptyTrusteeList`. Applied
   symmetrically to SEC-122. (A future per-trustee control-edge model —
   option (b) — remains possible but was not needed for the actionable-subject
   gap.)
3. `[IMP-DUP-RULE]` **SEC-013 and SEC-122 overlap on DC RBCD.** Domain
   Controllers are members of the Domain Controllers group (RID 516), which is
   in the privileged set, so any DC computer with a non-empty
   `msDS-AllowedToActOnBehalfOfOtherIdentity` produces **two** Critical findings
   (SEC-013 and SEC-122) on the same row. P6 pins the present behaviour.
   **Status: deferred improvement.** Resolution requires a product-level
   decision — either narrow SEC-013 to non-DC privileged resources (and let
   SEC-122 own the DC case) or collapse the two rules with tiered severity.
4. `[IMP-DEL-OBJ]` **`is_deleted` not filtered.** Tombstoned objects with a
   `dim_delegation` RBCD row would still fire. **Status:
   accepted-with-known-limitation.** Shared resolution with the SEC-001…SEC-012
   cluster.
5. `[IMP-DN-ENRICH]` **`Detail` / `ContextJson` do not include `sam_account_name`
   or `display_name`.** Operators see `CN=Domain Admins,…` but not the human
   name when the DN is null. **Status: accepted-with-known-limitation.** Shared.

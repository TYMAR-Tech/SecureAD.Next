## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-071
  name: "Path to Tier 0 Target"
  description: >-
    A non-administrative principal has a privilege escalation path (3+ hops) to a Tier 0 target.
  severity: High
  category: PrivilegeEscalation
  remediation: >-
    Review and break the escalation path by removing control edges.
  mitre: T1078
  tags: ["escalation-path", "tier-zero"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 324–333.

## 2. Intended detection (plain English)

Fire one finding per row in `fact_escalation_path` where:

- the **target** is classified `Tier0` (Domain Admins, Enterprise Admins,
  Schema Admins, krbtgt, Domain Controllers, etc.); and
- the **path length** is long — 3 or more hops (`path_length >= 3`); and
- the **source** is not itself a well-known admin principal
  (`IsAdminSid` exclusion).

Tier-0 classification is intended to come from `dim_asset_tier`. When
that table is absent, the evaluator falls back to a RID-based classifier
that recognises a narrower Tier 0 set (RID 512 only); see §12.1 and
`[IMP-FALLBACK-TIER]`.

Severity is fixed at `High`; SEC-070 (short path to Tier 0, ≤2 hops) is
the Critical-severity sibling and shares the same evaluator code path
with the inverse `maxPathLength` bound.

### 3.1 Effective SQL (copied from code)

Primary path (when `dim_asset_tier` exists):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name,
       att.reason AS tier_reason
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
LEFT JOIN dim_asset_tier att ON p.target_sid = att.sid
WHERE COALESCE(att.tier, 'Tier2') = $tier
   AND p.path_length >= $minLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $tier = 'Tier0', $minLen = 3
```

Fallback path (when `dim_asset_tier` does not exist):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
WHERE 1 = 1
   AND p.path_length >= $minLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $minLen = 3; tier classification then applied per row via ClassifyFallbackTier
```

### 3.2 Post-SQL filters (in C#)

- `IsAdminSid(sourceSid) → skip` — exclude rows whose source SID is a
  well-known admin (RID 500, 502, 512, 516, 518, 519, 520, 521, 526,
  527 — `AdminRids` in `RuleEvaluatorHelpers.cs:27`) or a well-known
  privileged system SID. `BroadSids` are explicitly **not** treated as
  admins.
- Fallback path only: `ClassifyFallbackTier(targetSid) != "Tier0" → skip`
  — drops rows whose target RID is not 512 (Domain Admins). RID 519
  routes to SEC-072 via `Tier0Shadow`, RID 516 routes to SEC-074 via
  `Tier1`, every other RID lands in SEC-075 (Custom). Same
  `[IMP-FALLBACK-TIER]` gap as SEC-070.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Paths to non-Tier-0 targets | `WHERE COALESCE(att.tier, 'Tier2') = 'Tier0'` (primary) / `ClassifyFallbackTier(target) == "Tier0"` (fallback) | SEC-071 is the long Tier-0 path rule by definition. Tier-1 and "Custom" / unclassified targets are SEC-074 / SEC-075 territory. |
| Short paths (≤2 hops) | `WHERE p.path_length >= 3` | The catalog says "(3+ hops)". SEC-070 (short path to Tier 0) handles `path_length <= 2` with `Critical` severity. |
| Admin sources | Post-SQL `IsAdminSid(sourceSid) → continue` | A path starting from `Domain Admins → ... → Enterprise Admins` is normal Tier-0 RBAC, not an escalation. Uses RID + well-known SID matching, never group-membership expansion (see E7). |
| Broad SIDs not excluded | `IsAdminSid` explicitly returns `false` for `BroadSids` (line 80) | A long path from `Authenticated Users` to Tier 0 is still a High escalation and must surface. |

Not excluded (intentionally subject to review):

- `coverage_complete = 0` rows — the rule still fires; the per-row flag
  flows through `CreatePathFinding` to `FindingV2.CoverageComplete`.
  A long path with incomplete coverage is still actionable evidence.
- Deleted (`is_deleted = 1`) source / target — `dim_object` is **not**
  joined; the path service is expected to drop tombstoned principals
  at capture time. Cross-cutting `[IMP-DEL-OBJ]`.
- Cross-domain paths — surface as-is. Tier 0 of any domain in the forest
  is in scope.
- No upper path-length bound — paths of length 10, 50, 500 still surface.
  Accepted: the path service already enforces a graph-wide budget and
  per-pair retention rules at capture time.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-071"`
- `Severity == High`
- `SubjectSid` = source principal SID
- `TargetKind == "sid"`
- `TargetId` = target principal SID
- `SourcePathId` populated (from `fact_escalation_path.path_id`)
- `SourceEdgeId == null`
- `CoverageComplete` = the path's per-row `coverage_complete`
- `FindingKey == "SEC-071|{source_sid}|{target_sid}|{path_id}"`
- `Detail` matches one of:
  - tier-table path: `"{source_name} has {path_length}-hop escalation path to Tier0 target {target_name}{[ (tier_reason)]}: {truncated path_detail}"`
  - fallback path: `"{source_name} has {path_length}-hop escalation path to {fallbackTier} target {target_name}: {truncated path_detail}"`
- `ContextJson` non-null (typed `PathFindingContext`) and contains:
  - `"rule_id": "SEC-071"`
  - `"source_sid"`, `"source_name"`, `"target_sid"`, `"target_name"`
  - `"path_id"`, `"path_length"`, `"coverage_complete"`
  - `"target_tier"` (`"Tier0"` on the primary code path; the fallback
    classifier value on the fallback code path)
  - `"tier_reason"` when supplied by `dim_asset_tier.reason`
  - `"path_detail"`, `"first_actionable_edge_id"`,
    `"first_actionable_edge_summary"`, `"steps"`

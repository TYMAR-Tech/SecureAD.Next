## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-067
  name: "Tier 0 Account Exposed to Delegation Impersonation"
  description: >-
    A Tier 0 user account (a transitive member of Domain Admins, Enterprise Admins, or Schema Admins)
    is delegatable — it has neither the "Account is sensitive and cannot be delegated" flag nor
    membership in the Protected Users group — while a Kerberos delegation impersonation vector exists in
    the environment ... This finding is risk-gated ... Domain controllers' inherent unconstrained-
    delegation trust is excluded.
  severity: Medium
  category: Delegation
  remediation: >-
    Set "Account is sensitive and cannot be delegated" on the account (low risk ...). For stronger
    protection, add the account to the Protected Users group, but test first ...
  mitre: T1558.003
  tags: ["delegation", "tier-zero", "impersonation", "kerberos", "review"]
```

## 2. Intended detection (plain English)

A **Tier 0 user** (transitive member of Domain/Enterprise/Schema Admins, RID 512/518/519, via
`fact_group_membership_closure`) that is **delegatable** — has **neither** the `NOT_DELEGATED`
userAccountControl flag (`0x100000`) **nor** Protected Users (RID 525) membership — **while a
delegation impersonation vector exists** that the protection would defeat: a **non-DC** host configured
for **protocol transition (S4U2Self)**, **RBCD**, or **unconstrained** delegation.

**Risk-gated, not a config checker:** with zero delegation vectors present, the rule produces nothing.
DC unconstrained delegation is inherent/required and excluded. Each finding is **Medium** /
`review_required`.

### 3.1 Logic (in C#)

1. `LoadDelegationVectors`: non-DC `dim_delegation` rows of type ProtocolTransition / RBCD /
   Unconstrained. **If empty → return no findings (risk gate).**
2. `LoadProtectedUsersMembers`: SIDs transitively in RID 525.
3. Tier-0 user query: `object_class='user'`, transitive member of `%-512/518/519`,
   `user_account_control & 0x100000 = 0` (no NOT_DELEGATED).
4. Skip any whose SID is in Protected Users.
5. Emit Medium / `review_required`; ContextJson `enabling_vectors` names the vector host(s).

## 4. Doc grounding (first-party, verified this session)

| Claim | Source |
| --- | --- |
| "By default, all accounts in Active Directory can be delegated" (admin membership does NOT auto-protect) | *Implementing Least-Privilege Administrative Models* |
| NOT_DELEGATED flag = "Deny delegation with unconstrained or constrained delegation" | *How to Configure Protected Accounts* |
| "accounts that have 'Account is sensitive and can't be delegated' set can't be delegated" | *Making the second hop in PowerShell Remoting* |
| Protected Users members "cannot delegate with unconstrained or constrained delegation"; protection is live/reversible (ends on leaving group); empty by default | *Protected Users security group* |
| The three delegation risks to remediate: Unconstrained, Constrained, RBCD | *Defender for Identity — Unsecure Kerberos delegation* |

**Key conceptual clarification (the design hinge):** privileged-group membership gives *power*, not
delegation protection — those are independent. The "sticky after removal" behavior the user recalled is
**AdminSDHolder/adminCount** (protects ACLs, SEC-030's domain), **not** Protected Users (live/reversible)
or the NOT_DELEGATED flag (persistent attribute). Verified, not assumed.

## 5. Operator explanation (first-class — the user's explicit requirement)

The finding **leads with the low-risk fix** and frames the aggressive one honestly, because Protected
Users is genuinely risky to apply to admins (AES-only, no NTLM, 4-hour tickets — can lock out accounts):
- Detail + `recommended_fix`: "Set 'Account is sensitive and cannot be delegated' (NOT_DELEGATED) — low
  risk, blocks delegation without affecting authentication. Stronger (test first): Protected Users …"
- UI guidance (`SpecificGuidanceByRule["SEC-067"]`) + `GetDefaultCaution` reinforce: pilot Protected
  Users before broad rollout.

## 9. Disposition model

Two-axis (severity = impact, disposition = certainty), like SEC-063/064/065/066. **Medium** (not High)
deliberately: it fires on multiple admins by design (Protected Users is empty by default in most orgs),
so it must not drown the actionable High queue. Risk-gating + the named vector keep it from being noise.

## 10. Live lab validation

Root + 2-child lab, after the user staged two non-DC vectors: **ProtocolTransition** on `BAMS1`
(`OU=Servers,OU=BA Lab`) and **RBCD** on `BAWK1` (`OU=Workstations,OU=BA Lab`). 6 delegatable Tier-0
user accounts (ba.admin, jimmy.strand.da, jimmystrand ×3, ph.admin) — all lacking NOT_DELEGATED, none in
Protected Users. **Predicted: 6 Medium findings**, each naming the 2 enabling vectors. The 3 DC
unconstrained-delegation hosts (ADDC/BADC/PHDC) are correctly excluded. Probe:
`LabDbProbe.ValidateSec067_AgainstLab`. **Bonus:** staging RBCD also proved the
`msDS-AllowedToActOnBehalfOfOtherIdentity` → `dim_delegation` RBCD derivation end-to-end, retroactively
confirming SEC-013/SEC-122 are not silently blind (the earlier 0-RBCD was simply no config, not a bug).

## 11. Defects / deferred items

1. **Computer-account victims** — v1 is user accounts only (DCs are delegatable by design; computer
   delegation semantics are messier). Deferred.
2. **Non-Tier-0 sensitive accounts** (operators, server admins) — v1 scopes to DA/EA/SA for clarity.
   Deferred.
3. **Cross-domain S4U precision** — EA is forest-wide Tier-0, so a child-domain vector exposes it; v1
   correlates at the environment level (a vector anywhere → all delegatable Tier-0 exposed) and does
   not model KDC trust-path reachability. Documented simplification.
4. **Per-account path precision** — for protocol transition specifically the attacker chooses the
   victim (S4U2Self), so there is no stored per-account link to key on; environment-level correlation is
   the technically-correct model. Not a defect.

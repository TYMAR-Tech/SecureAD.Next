## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-014
  name: "Unexpected Principal can Configure RBCD"
  description: >-
    A principal can write msDS-AllowedToActOnBehalfOfOtherIdentity.
  severity: Critical
  category: Delegation
  remediation: >-
    Remove write access to RBCD attribute unless the delegation is explicitly required and documented.
  mitre: T1558.001
  tags: ["kerberos", "rbcd", "write-access"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 113–122.

## 2. Intended detection (plain English)

A finding must be raised for every captured object that has an inbound control
edge from a **non-admin** principal whose `control_type` confers the ability to
write `msDS-AllowedToActOnBehalfOfOtherIdentity` on the target. The capability
arises from any of:

- **Direct attribute write.** A `WriteProperty` ACE scoped to the RBCD attribute
  GUID `3f78c3e5-f79a-46bd-a0b8-9d18116ddc79` — surfaced by
  `ControlEdgeService.DeriveControlTypes` as `ControlType.WriteRBCD`.
- **Broader write rights.** `GenericAll`, `GenericWrite`, and `WriteAllProperties`
  all subsume `WriteProperty` on every attribute including RBCD.
- **DACL / ownership pivot.** `WriteDacl` lets the principal rewrite the DACL
  to grant themselves any right; `WriteOwner` lets them take ownership;
  `Owns` is the implicit `WriteDacl` of the actual owner. All three pivot to
  the same capability.

The rule must exclude well-known admin/system principals via
`RuleEvaluatorHelpers.IsAdminSid` (`excludeAdmins: true`).

### 3.1 Effective SQL (copied from code)

```sql
SELECT e.source_sid, e.target_object_guid, o.distinguished_name, e.edge_id, e.control_type
FROM fact_control_edge e
INNER JOIN dim_object o ON e.target_object_guid = o.object_guid
WHERE e.control_type IN ($type0, $type1, $type2, $type3, $type4, $type5, $type6) AND e.deny_cancelled = 0
ORDER BY e.source_sid, e.target_object_guid, e.control_type
```

With `$type0..$type6` bound to the seven values of `WriteRbcdEquivalents`:
`WriteRBCD, GenericAll, GenericWrite, WriteAllProperties, WriteDacl, WriteOwner, Owns`.

### 3.2 Post-SQL filters (in C#)

- `excludeAdmins: true` — `RuleEvaluatorHelpers.IsAdminSid(sid)` skips rows
  whose source SID matches a well-known admin RID (500/502/512/516/518/519/520/521/526/527),
  a BUILTIN admin SID (S-1-5-32-544/548/549/550/551/552/554), or a privileged
  system SID (S-1-5-18 SYSTEM, S-1-5-19 LOCAL SERVICE, S-1-5-20 NETWORK SERVICE,
  S-1-5-9 Enterprise DCs, S-1-5-17 IUSR, S-1-5-83-0 NT VIRTUAL MACHINE).
  Broad SIDs (`Everyone`, `Authenticated Users`, `Anonymous`, `Users` group)
  are explicitly **not** treated as admin, so they continue to fire.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Well-known admin RIDs (500/512/516/518/519/…) and BUILTIN admin SIDs | `IsAdminSid` via `excludeAdmins: true` | Direct admin holders of the right are not "unexpected"; the rule semantics target principals outside the admin tier. |
| Privileged system SIDs (`S-1-5-18` SYSTEM, `S-1-5-9` Enterprise DCs, …) | `PrivilegedSystemSids` set in `IsAdminSid` | These SIDs hold every right inherently and are not actionable as findings. |
| `deny_cancelled = 1` edges | SQL `WHERE e.deny_cancelled = 0` | Edges already cancelled by an explicit deny ACE no longer confer the right. |

Not excluded (intentionally subject to review):

- **Broad SIDs** (`S-1-1-0` Everyone, `S-1-5-11` Authenticated Users, `S-1-5-7`
  Anonymous, `S-1-5-32-545` Users) — these are the high-impact cases the rule
  must catch, so `IsAdminSid` explicitly bails out for them via `BroadSids.Contains`.
- **Privileged-by-membership sources** — a member of Domain Admins via group
  closure (rather than via well-known RID) still produces a SEC-014 finding,
  because `IsAdminSid` is RID-/SID-based, not membership-based.
  See `[IMP-PRIV-MEMB-SRC]`.
- **Tier-0 targets** — SEC-014 does not down-tier findings against AdminSDHolder,
  Domain Controllers OU, or DC objects. They appear as ordinary Critical findings
  rather than as a separate Tier-0 RBCD signal.
- **`is_deleted = 1` targets** — the SQL does not filter deleted objects. See
  `[IMP-DEL-OBJ]`.

## 12. Defects / deferred items

1. **Resolved — scope too narrow.** Before the fix, SEC-014 dispatched
   `EvaluateControlEdgeRule(..., ControlType.WriteRBCD, ...)` with an
   exact-match `control_type = 'WriteRBCD'` SQL. The catalog says any principal
   who can *write* `msDS-AllowedToActOnBehalfOfOtherIdentity`, but
   `ControlEdgeService.DeriveControlTypes` only stamps `WriteRBCD` for object-type
   ACEs whose object_type GUID equals the RBCD attribute GUID. Six other
   capability-equivalent control types (`GenericAll`, `GenericWrite`,
   `WriteAllProperties`, `WriteDacl`, `WriteOwner`, `Owns`) were ignored, so the
   detection missed every case where the principal held broad rights or
   ownership instead of an explicit attribute-scoped ACE. **Fixed** by adding
   an `IReadOnlyCollection<ControlType>` overload to `EvaluateControlEdgeRule`
   and dispatching SEC-014 against `WriteRbcdEquivalents`. Mirrors the
   pattern SEC-060 already uses for the broad-SID `IN (...)` set.

2. `[IMP-CTRL-SCOPE]` / `[IMP-TGT-CLASS]` — **RESOLVED for the widening
   group.** SEC-014 was already widened to `WriteRbcdEquivalents` but
   **lacked a target-class filter**, so a class-agnostic broad grant
   (`GenericAll` on a group, OU, ...) fired "can configure RBCD" even
   though only `computer` / `user` / gMSA carry
   `msDS-AllowedToActOnBehalfOfOtherIdentity`. Retrofitted with
   `targetFilter: o.object_class IN ('computer', 'user',
   'msDS-GroupManagedServiceAccount')`, pinned by
   `WhenGenericAllOnGroupTarget_ThenSEC014DoesNotFire`. The shared
   `RuleEvaluatorHelpers.PropertyWriteEquivalents` helper now backs SEC-006
   / SEC-024 / SEC-025 / SEC-081; SEC-014 keeps its own
   `WriteRbcdEquivalents` (which additionally includes the DACL-pivot
   rights `WriteDacl` / `WriteOwner` / `Owns`, an intentional per-rule
   choice).

3. `[IMP-DEL-OBJ]` — the SQL does not filter `is_deleted = 1` on the target
   object. A finding on a tombstoned object is not remediatable.

4. `[IMP-DN-ENRICH]` — `Detail` and `ContextJson` carry raw SIDs only for the
   source principal; sam-account-name and display-name resolution would
   greatly improve operator triage.

5. `[IMP-PRIV-MEMB-SRC]` — a source principal that is a transitive member of
   Domain Admins (rather than holding a well-known admin RID directly) still
   produces a SEC-014 finding. Either filter via `IsPrivilegedPrincipal`
   (consistent with SEC-013) or tier the severity via `ClassifyPrincipal`.
   This is a UX trade-off, not a SQL bug.

6. `[IMP-CAT-WORDING]` — the catalog `description`
   ("A principal can write msDS-AllowedToActOnBehalfOfOtherIdentity") does
   not mention that admin/system principals are intentionally excluded, that
   broad SIDs are the high-impact case, or that the equivalence set covers
   six rights besides the direct attribute write. Tightening the wording
   prevents future drift between catalog and evaluator.

7. `[IMP-PARITY-TEST]` — no per-rule severity/MITRE/tag parity assertion
   exists for SEC-014 in `RuleCatalogParityTests`. Asserting
   `Severity == Critical`, `mitre == "T1558.001"`, and the exact tag set
   ("kerberos", "rbcd", "write-access") would prevent silent catalog edits.

8. `[IMP-KEY-COLLAPSE]` — `FindingKey = "{ruleId}|{subjectSid}|{targetGuid}"`
   intentionally collapses multiple equivalent control_types into one
   finding (validated by P9). The trade-off: the surviving finding's
   `control_type` is whichever sort order wins, so a principal who holds
   both `Owns` and `WriteRBCD` will surface only one of them in `Detail`.
   Acceptable today but worth revisiting if remediation guidance needs to
   enumerate every contributing right.

## 13. Improvement suggestions (not blocking)

1. `[IMP-CTRL-SCOPE]` — The widening group (SEC-006 / SEC-014 / SEC-024 /
   SEC-025 / SEC-081) is resolved via the shared
   `RuleEvaluatorHelpers.PropertyWriteEquivalents` + a mandatory target
   `object_class` filter. SEC-040 (`CertificateEnroll`) is an
   **extended right**, not a property write, so it is conferred by
   `GenericAll` only (not `GenericWrite` / `WriteAllProperties`) — a
   separate equivalence class; left as a distinct follow-up.

2. `[IMP-PRIV-PROV]` — Carry the source principal's privileged-group provenance
   into `ContextJson` (`SourceIsPrivilegedByMembership` is already there, but
   the matching group SID(s) are not), so a SEC-014 finding on a transitive
   DA member is operationally distinguishable from one on a standard user.

3. `[IMP-DC-DETECT]` — SEC-014 inherits the `'%OU=Domain Controllers%'`
   heuristic only indirectly (none of its filters use it), but if the rule
   ever grows a "down-tier on DC target" branch it should adopt the
   `userAccountControl & 0x2000` check.

## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-020
  name: "Kerberoastable Account"
  description: >-
    A user account has a servicePrincipalName set (vulnerable to Kerberoasting). Excludes gMSA and managed service accounts.
  severity: Medium
  category: CredentialTheft
  remediation: >-
    Remove unnecessary SPNs from user accounts or use strong passwords.
  mitre: T1558.003
  tags: ["kerberos", "kerberoasting", "spn"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 124–133.

## 2. Intended detection (plain English)

A finding must be raised for every captured **user** account that has any
`servicePrincipalName` value set, because such accounts can have a TGS ticket
requested by any authenticated principal and the resulting ticket can be
offline-cracked to recover the account's NT hash (Kerberoasting). Group
Managed Service Accounts (gMSA) and Managed Service Accounts (MSA) must be
excluded because their passwords are managed by AD with high-entropy random
values, making the attack non-economical. `krbtgt` should be excluded because
it is the KDC's own service account.

### 3.1 Effective SQL (copied from code)

```sql
SELECT o.object_guid, o.distinguished_name, o.sid, d.target
FROM dim_delegation d
INNER JOIN dim_object o ON d.object_guid = o.object_guid
WHERE d.delegation_type = 'SPN'
  AND o.object_class = 'user'
  AND o.is_deleted = 0
ORDER BY o.sid, o.object_guid
```

### 3.2 Post-SQL filters (in C#)

- `IsKrbtgtSid(sid)` — excludes the row when the source SID ends in `-502`
  (any RID-502 account, not literally the string "krbtgt"). Strictly RID-based.
- (No other post-SQL filter.) gMSA / MSA exclusion is **implicit** via the SQL
  `object_class = 'user'` filter, relying on
  `LdapAttributeHelper.ExtractMostSpecificClass` returning the structural class
  (`msDS-GroupManagedServiceAccount` / `msDS-ManagedServiceAccount`) for those
  objects rather than the inherited `user` class. See Â§12 and `[IMP-TGT-CLASS]`.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| RID-502 (`krbtgt`) | `IsKrbtgtSid` post-SQL filter | KDC's own ticket-granting service; not an attacker-targetable account. The filter is RID-based, not name-based — any account ending in `-502` is excluded (uncommon collision in real domains). |
| Computer accounts | SQL `o.object_class = 'user'` | Computer-account passwords are 120-char random by default and rotated every 30 days; Kerberoasting is not economical. SEC-024 covers the related `WriteSPN` vector. |
| Group / OU / built-in objects | SQL `o.object_class = 'user'` | Cannot have a usable Kerberos password to crack. |
| gMSA (`msDS-GroupManagedServiceAccount`) | SQL `o.object_class = 'user'` (indirect) | gMSA passwords are 240-byte random values rotated by AD. The structural class returned by `ExtractMostSpecificClass` is `msDS-GroupManagedServiceAccount`, not `user`. |
| MSA (`msDS-ManagedServiceAccount`) | SQL `o.object_class = 'user'` (indirect) | Same reasoning as gMSA. |

Not excluded (intentionally subject to review):

- **Disabled user accounts** — filtered by `NotDisabledSql("o")` in the SQL.
  The KDC refuses to issue a TGS for a disabled account, so a Kerberoasting
  attack cannot complete; excluded. `[IMP-DISABLED-FILTER]` resolved on this
  rule. Verified by `WhenKerberoastableUserIsDisabled_ThenSEC020DoesNotFire`.
- **`is_deleted = 1` tombstoned users** — filtered by SQL (`AND o.is_deleted = 0`).
  `[IMP-DEL-OBJ]` resolved on this rule. Verified by `WhenKerberoastableUserIsDeleted_ThenSEC020DoesNotFire`.
- **Trust accounts (`InterdomainTrustAccount`)** — captured as `object_class = 'user'`
  in older schemas. Their passwords are also AD-managed but with shorter cycles;
  not currently filtered.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-020"`
- `Severity == Medium`
- `SubjectSid` = the user's SID (or `""` when null)
- `TargetKind == "object_guid"`
- `TargetId` = user object GUID (`D` format)
- `SourceEdgeId == null` (delegation findings carry no edge id)
- `FindingKey == "SEC-020|{SubjectSid}|{TargetId}"`
- `Detail` matches `Kerberoastable user {dn ?? guid} has SPN: {spn}`
- `ContextJson` non-null and contains:
  - `"rule_id": "SEC-020"`
  - `"evidence_type": "delegation"`
  - `"delegation_type": "SPN"`
  - `"spn": "<the SPN value of the surviving row>"`
  - `"object_dn": "<DN or null>"`
  - `"object_guid": "<GUID in D format>"`

## 12. Defects / deferred items

1. `[IMP-TGT-CLASS]` — gMSA/MSA exclusion is **indirect** via
   `object_class = 'user'`. The exclusion only holds because
   `LdapAttributeHelper.ExtractMostSpecificClass` returns the structural class
   from the `objectClass` multi-valued attribute. If the capture side is ever
   refactored to surface the inherited `user` class (or to canonicalise on
   `samAccountType`), every gMSA/MSA will start firing. Suggested resolution:
   either (a) make the filter explicit (`AND o.object_class NOT IN
   ('msDS-GroupManagedServiceAccount', 'msDS-ManagedServiceAccount')`) in
   addition to the positive `= 'user'` filter, or (b) add a SQL-level
   predicate based on `sam_account_type` once that column is captured.

2. `[IMP-DISABLED-FILTER]` — **RESOLVED.** Disabled user accounts (UAC bit
   0x2 = `ACCOUNTDISABLE`) are now excluded via `NotDisabledSql("o")` in the
   SQL, since the KDC will not issue a TGS for them. The former
   `*_StillFiresKnownLimitation` pin was flipped to
   `WhenKerberoastableUserIsDisabled_ThenSEC020DoesNotFire`.

3. `[IMP-DEL-OBJ]` — Resolved. SQL now filters `o.is_deleted = 0`; a
   tombstoned user with a stale SPN row no longer fires.

4. `[IMP-KEY-COLLAPSE]` — `FindingKey = "{ruleId}|{subjectSid}|{targetGuid}"`
   collapses N SPN rows on the same user into one finding. The surviving
   `Detail`/`ContextJson` carries whichever SPN row sorted first, hiding the
   other SPNs from operator triage. SEC-021 already handles this via
   `GROUP_CONCAT(spn.target, '|')` and an `all_spns` ContextJson field; the
   same pattern could be applied to SEC-020.

5. `[IMP-DUP-RULE]` — SEC-020 (Medium) and SEC-021 (High) fire on the same
   row when the user is both privileged AND has a service-prefix SPN. Two
   findings per principal complicates remediation triage. Resolution
   requires a product-level decision (collapse-with-severity-tiering vs
   explicit non-overlap).

6. `[IMP-DN-ENRICH]` — `Detail`/`ContextJson` carry the user's `object_dn`
   but no `sam_account_name` or human-readable display name. Operator
   triage benefits from both.

7. `[IMP-PARITY-TEST]` — No per-rule severity / MITRE / tag parity
   assertion exists for SEC-020 in `RuleCatalogParityTests`. Adding one
   (`Severity == Medium`, `mitre == "T1558.003"`, tags
   `{ "kerberos", "kerberoasting", "spn" }`) would prevent silent catalog
   edits.

8. `[IMP-CAT-WORDING]` — The catalog says "Excludes gMSA and managed
   service accounts" but does not mention the krbtgt exclusion, the
   computer / group / OU implicit exclusion, or that the exclusion is
   class-based rather than attribute-based. Tightening the wording prevents
   future drift.

## 13. Improvement suggestions (not blocking)

1. `[IMP-DISABLED-FILTER]` - **Resolved** (see section 12). Disabled accounts are now
   filtered via `NotDisabledSql("o")`, applied consistently across SEC-020 /
   SEC-021 / SEC-022 / SEC-023.



2. `[IMP-KEY-COLLAPSE]` — Apply SEC-021's `GROUP_CONCAT` pattern to
   SEC-020 so the finding's `Detail`/`ContextJson` enumerate every SPN.

3. `[IMP-TGT-CLASS]` — Centralise the structural-class set
   ("`user`-but-not-machine-managed") into a shared helper used by SEC-020,
   SEC-021, SEC-022 (AS-REP), SEC-040 (Cert Enroll), and any future
   "user-account-only" rule, so the implicit gMSA/MSA exclusion becomes
   a single point of maintenance.

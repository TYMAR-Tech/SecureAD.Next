## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-074
  name: "Path to Tier 1 Target"
  description: >-
    A non-administrative principal has a privilege escalation path (3+ hops) to a Tier 1 target.
  severity: Medium
  category: PrivilegeEscalation
  remediation: >-
    Review and break the escalation path by removing control edges.
  mitre: T1078
  tags: ["escalation-path", "tier-one"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 357–366.

## 2. Intended detection (plain English)

Fire one finding per row in `fact_escalation_path` where:

- the **target** is classified `Tier1` (Account Operators, Server
  Operators, Print Operators, Backup Operators, Cert Publishers,
  RAS and IAS Servers, Remote Desktop Users, Incoming Forest Trust
  Builders); and
- the **path length** is long — 3 or more hops (`path_length >= 3`); and
- the **source** is not itself a well-known admin principal
  (`IsAdminSid` exclusion).

Tier-1 classification is intended to come from `dim_asset_tier`. When
that table is absent, the evaluator falls back to a RID-based classifier
that recognises a narrower Tier 1 set (RID 516 only); see §12.1 and
`[IMP-FALLBACK-TIER]`.

Severity is the catalog default `Medium` on **both** code paths. Earlier
revisions boosted the fallback path to `High` via a `GetFallbackSeverity`
helper; `[IMP-FALLBACK-TIER]` **removed** that helper and aligned the
fallback classifier with `StaticAssetTierClassifier`, so fallback now
classifies the real well-known Tier 1 groups (Backup / Server / Account
Operators, etc.) and reports them at the catalog `Medium` — identical to
the tier-table path. See §3.2 and §12.1.

SEC-073 (short path to Tier 1, 1–2 hops) is the High-severity sibling
and shares the same evaluator code path with the inverse
`maxPathLength` bound.

### 3.1 Effective SQL (copied from code)

Primary path (when `dim_asset_tier` exists):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name,
       att.reason AS tier_reason
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
LEFT JOIN dim_asset_tier att ON p.target_sid = att.sid
WHERE COALESCE(att.tier, 'Tier2') = $tier
   AND p.path_length >= $minLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $tier = 'Tier1', $minLen = 3
```

Fallback path (when `dim_asset_tier` does not exist):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
WHERE 1 = 1
   AND p.path_length >= $minLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $minLen = 3; tier classification then applied per row via ClassifyFallbackTier
```

### 3.2 Post-SQL filters (in C#)

- `IsAdminSid(sourceSid) → skip` — exclude rows whose source SID is a
  well-known admin (RID 500, 502, 512, 516, 518, 519, 520, 521, 526,
  527 — `AdminRids` in `RuleEvaluatorHelpers.cs:27`) or a well-known
  privileged system SID. `BroadSids` are explicitly **not** treated as
  admins. Note RID 516 (Domain Controllers) is in `AdminRids`, so any
  DC-sourced path is excluded — `IsAdminSid` is symmetric with the
  fallback classifier's choice of RID 516 as the **target** Tier-1
  identifier.
- Fallback path only: `ClassifyFallbackTier(targetSid) != "Tier1" → skip`
  — drops rows whose target RID is not 516 (Domain Controllers). RIDs
  512 / 519 are routed to SEC-071/072 via `Tier0`/`Tier0Shadow`, every
  other RID lands in SEC-075 (Custom). Same `[IMP-FALLBACK-TIER]` gap
  as SEC-070..073.
- Fallback path: severity is the catalog `Medium`, identical to the
  tier-table path. The former unconditional `GetFallbackSeverity` boost to
  `High` was removed by `[IMP-FALLBACK-TIER]` when the fallback classifier
  was aligned with `StaticAssetTierClassifier`, so fallback now classifies
  the real well-known Tier 1 groups (Backup / Server / Account Operators)
  and emits them at `Medium`. Pinned by `WhenThreeHopFallbackPathToBackupOperators_ThenSEC074FiresWithFullShape`
  (this fixture) and contrasted with the tier-table positives in
  `EscalationPathTierFindingsTests` which assert `Medium`.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Paths to non-Tier-1 targets | `WHERE COALESCE(att.tier, 'Tier2') = 'Tier1'` (primary) / `ClassifyFallbackTier(target) == "Tier1"` (fallback) | SEC-074 is the Tier-1 long-path rule by definition. Tier-0 and "Custom" / unclassified targets belong to SEC-070..072 / SEC-075. |
| Short paths (≤ 2 hops) | `WHERE p.path_length >= 3` | The catalog says "(3+ hops)". SEC-073 (short path to Tier 1) handles `path_length <= 2` with `High` severity. |
| Admin sources | Post-SQL `IsAdminSid(sourceSid) → continue` | A long path from `Domain Admins → ... → Backup Operators` is normal admin lateral movement, not an escalation. Uses RID + well-known SID matching, never group-membership expansion (see E7). |
| Broad SIDs not excluded | `IsAdminSid` explicitly returns `false` for `BroadSids` (line 80) | A long path from `Authenticated Users` to a Tier 1 group is still a Medium escalation and must surface. |

Not excluded (intentionally subject to review):

- `coverage_complete = 0` rows — the rule still fires; the per-row flag
  flows through `CreatePathFinding` to `FindingV2.CoverageComplete`.
- Deleted (`is_deleted = 1`) source / target — `dim_object` is **not**
  joined; the path service is expected to drop tombstoned principals
  at capture time. Cross-cutting `[IMP-DEL-OBJ]`.
- Cross-domain paths — surface as-is. A Tier 1 target in any domain of
  the forest is in scope.
- Very long paths (e.g., `path_length >= 10`) — no upper bound; capture
  pipeline is expected to cap practical path length.

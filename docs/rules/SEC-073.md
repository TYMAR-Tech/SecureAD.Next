## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-073
  name: "Short Path to Tier 1 Target"
  description: >-
    A non-administrative principal has a short (1-2 hop) privilege escalation path to a Tier 1 target (Server Operators, Backup Operators, Account Operators, etc.).
  severity: High
  category: PrivilegeEscalation
  remediation: >-
    Break the escalation path by removing control edges.
  mitre: T1078
  tags: ["escalation-path", "tier-one", "short-path"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 346–355.

## 2. Intended detection (plain English)

Fire one finding per row in `fact_escalation_path` where:

- the **target** is classified `Tier1` (Account Operators, Server
  Operators, Print Operators, Backup Operators, Cert Publishers,
  RAS and IAS Servers, Remote Desktop Users, Incoming Forest Trust
  Builders); and
- the **path length** is short — 1 or 2 hops (`path_length <= 2`); and
- the **source** is not itself a well-known admin principal
  (`IsAdminSid` exclusion).

Tier-1 classification is intended to come from `dim_asset_tier`. When
that table is absent, the evaluator falls back to a RID-based classifier
that recognises a narrower Tier 1 set (RID 516 only); see §12.1 and
`[IMP-FALLBACK-TIER]`.

Severity is fixed at `High`; SEC-074 (long path to Tier 1, ≥3 hops) is
the Medium-severity sibling and shares the same evaluator code path
with the inverse `minPathLength` bound.

### 3.1 Effective SQL (copied from code)

Primary path (when `dim_asset_tier` exists):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name,
       att.reason AS tier_reason
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
LEFT JOIN dim_asset_tier att ON p.target_sid = att.sid
WHERE COALESCE(att.tier, 'Tier2') = $tier
   AND p.path_length <= $maxLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $tier = 'Tier1', $maxLen = 2
```

Fallback path (when `dim_asset_tier` does not exist):

```sql
SELECT p.path_id, p.source_sid, p.target_sid, p.path_length, p.path_detail, p.coverage_complete,
       sp.display_name AS source_name, tp.display_name AS target_name
FROM fact_escalation_path p
LEFT JOIN dim_principal sp ON p.source_sid = sp.sid
LEFT JOIN dim_principal tp ON p.target_sid = tp.sid
WHERE 1 = 1
   AND p.path_length <= $maxLen
ORDER BY p.source_sid, p.target_sid, p.path_id
-- $maxLen = 2; tier classification then applied per row via ClassifyFallbackTier
```

### 3.2 Post-SQL filters (in C#)

- `IsAdminSid(sourceSid) → skip` — exclude rows whose source SID is a
  well-known admin (RID 500, 502, 512, 516, 518, 519, 520, 521, 526,
  527 — `AdminRids` in `RuleEvaluatorHelpers.cs:27`) or a well-known
  privileged system SID. `BroadSids` are explicitly **not** treated as
  admins. Note RID 516 (Domain Controllers) is in `AdminRids`, so any
  DC-sourced path is excluded — `IsAdminSid` is symmetric with the
  fallback classifier's choice of RID 516 as the **target** Tier-1
  identifier.
- Fallback path only: `ClassifyFallbackTier(targetSid) != "Tier1" → skip`
  — drops rows whose target RID is not 516 (Domain Controllers). RIDs
  512 / 519 are routed to SEC-070/071/072 via `Tier0`/`Tier0Shadow`,
  every other RID lands in SEC-075 (Custom). Same `[IMP-FALLBACK-TIER]`
  gap as SEC-070/071/072.

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Paths to non-Tier-1 targets | `WHERE COALESCE(att.tier, 'Tier2') = 'Tier1'` (primary) / `ClassifyFallbackTier(target) == "Tier1"` (fallback) | SEC-073 is the Tier-1 short-path rule by definition. Tier-0 and "Custom" / unclassified targets belong to SEC-070..072 / SEC-075. |
| Long paths (≥3 hops) | `WHERE p.path_length <= 2` | The catalog says "short (1-2 hop)". SEC-074 (long path to Tier 1) handles `path_length >= 3` with `Medium` severity. |
| Admin sources | Post-SQL `IsAdminSid(sourceSid) → continue` | A short path from `Domain Admins → ... → Backup Operators` is normal admin lateral movement, not an escalation. Uses RID + well-known SID matching, never group-membership expansion (see E7). |
| Broad SIDs not excluded | `IsAdminSid` explicitly returns `false` for `BroadSids` (line 80) | A short path from `Authenticated Users` to a Tier 1 group is still a High escalation and must surface. |

Not excluded (intentionally subject to review):

- `coverage_complete = 0` rows — the rule still fires; the per-row flag
  flows through `CreatePathFinding` to `FindingV2.CoverageComplete`.
- Deleted (`is_deleted = 1`) source / target — `dim_object` is **not**
  joined; the path service is expected to drop tombstoned principals
  at capture time. Cross-cutting `[IMP-DEL-OBJ]`.
- Cross-domain paths — surface as-is. A Tier 1 target in any domain of
  the forest is in scope.
- `path_length = 0` (self-loop / identity path) — possible in theory
  but the path service never emits such rows; not tested explicitly.

## 9. Output assertions (`Detail` and `ContextJson`)

The finding produced must include:

- `RuleId == "SEC-073"`
- `Severity == High`
- `SubjectSid` = source principal SID
- `TargetKind == "sid"`
- `TargetId` = target principal SID
- `SourcePathId` populated (from `fact_escalation_path.path_id`)
- `SourceEdgeId == null`
- `CoverageComplete` = the path's per-row `coverage_complete`
- `FindingKey == "SEC-073|{source_sid}|{target_sid}|{path_id}"`
- `Detail` matches one of:
  - tier-table path: `"{source_name} has {path_length}-hop escalation path to Tier1 target {target_name}{[ (tier_reason)]}: {truncated path_detail}"`
  - fallback path: `"{source_name} has {path_length}-hop escalation path to {fallbackTier} target {target_name}: {truncated path_detail}"` where `{fallbackTier}` is `"Tier1"` for RID 516.
- `ContextJson` non-null (typed `PathFindingContext`) and contains:
  - `"rule_id": "SEC-073"`
  - `"source_sid"`, `"source_name"`, `"target_sid"`, `"target_name"`
  - `"path_id"`, `"path_length"`, `"coverage_complete"`
  - `"target_tier"` (`"Tier1"` on the primary code path; the fallback
    classifier value on the fallback code path)
  - `"tier_reason"` when supplied by `dim_asset_tier.reason`
  - `"path_detail"`, `"first_actionable_edge_id"`,
    `"first_actionable_edge_summary"`, `"steps"`

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Fallback classifier narrower than the tier table** `[IMP-FALLBACK-TIER]` —
   **RESOLVED** (see SEC-070 §12.1). `ClassifyFallbackTier` now delegates to
   `StaticAssetTierClassifier`, so the real Tier1 operator RIDs (548 / 549 / 550 /
   551 / 517 / 553 / 555 / 557) classify as `Tier1` and short paths to them fire
   SEC-073; RID 516 (Domain Controllers), formerly the only fallback Tier1 target,
   now correctly classifies as `Tier0` and fires SEC-070 / SEC-071. The operator
   `*_KnownLimitation` pins were flipped to
   `WhenFallbackShortPathTo{BackupOperators,ServerOperators,AccountOperators}_ThenSEC073Fires`.
   Historical description follows:
   same gap as SEC-070/071/072 §12.1, narrowed to the Tier 1 dimension.
   `ClassifyFallbackTier` maps only RID 516 to `Tier1`, so when
   `dim_asset_tier` is absent, paths to Account Operators (RID 548),
   Server Operators (RID 549), Print Operators (RID 550), Backup
   Operators (RID 551), Cert Publishers (RID 517), RAS and IAS Servers
   (RID 553), Remote Desktop Users (RID 555), and Incoming Forest Trust
   Builders (RID 557) silently miss SEC-073 and surface only as SEC-075
   (Medium severity). The tier-table-backed code path
   (`EvaluateByTier`) handles all those RIDs correctly when
   `dim_asset_tier` is populated. Additionally, RID 516 (Domain
   Controllers) is `Tier0` in `StaticAssetTierClassifier.Tier0GroupRids`
   but `Tier1` in `ClassifyFallbackTier` — so in fallback mode a DC
   path inflates to SEC-073 (`High`) instead of SEC-070 (`Critical`),
   the inverse problem from the SEC-070 fallback gap.
   `Accepted-with-known-limitation`: pinned by three `*_KnownLimitation`
   tests in `FindingsServiceTests.cs` (Account / Server / Backup
   Operators) and contrasted with the tier-table-backed positives in
   `EscalationPathTierFindingsTests.cs`. Resolution will land as part
   of the cross-cutting `[IMP-FALLBACK-TIER]` sweep covering
   SEC-070..077.

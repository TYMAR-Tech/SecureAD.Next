## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-120
  name: "AdminSDHolder ACL Backdoor"
  description: >-
    A principal has dangerous rights (GenericAll, GenericWrite, WriteDACL, WriteOwner, or ownership control) on AdminSDHolder. This is a persistence mechanism that propagates permissions to all protected objects.
  severity: Critical
  category: Persistence
  remediation: >-
    Remove unnecessary delegated permissions from the AdminSDHolder object and audit for unauthorized ACL changes.
  mitre: T1222.001
  tags: ["adminsdholder", "persistence", "acl-backdoor", "tier-zero"]
```

Source: `src/SecureAD.Core/Findings/Rules/rules.yaml` lines 489–498.

## 2. Intended detection (plain English)

Fire one Critical finding per `(non-privileged principal, AdminSDHolder)` pair when that principal holds `GenericAll`, `GenericWrite`, `WriteDacl`, `WriteOwner`, or ownership (`Owns`) on `CN=AdminSDHolder,CN=System,DC=…`. AdminSDHolder is the SDProp template — any non-admin who can rewrite its DACL or take ownership of it can persistently re-grant themselves rights on every protected (admin-tagged) account in the domain. Well-known admins and principals that are already privileged-by-membership in tier-0 groups should not fire (their access is by definition expected). Deleted (tombstoned) AdminSDHolder rows must not fire even if lingering control-edge rows still join.

### 3.1 Effective SQL (copied from code)

```sql
SELECT e.source_sid, e.target_object_guid, e.control_type, o.distinguished_name, e.edge_id
FROM fact_control_edge e
INNER JOIN dim_object o ON e.target_object_guid = o.object_guid
WHERE e.deny_cancelled = 0
  AND e.control_type IN ('GenericAll', 'GenericWrite', 'WriteDacl', 'WriteOwner', 'Owns')
  AND o.is_deleted = 0
  AND o.distinguished_name LIKE '%CN=AdminSDHolder,CN=System,%'
ORDER BY e.source_sid, e.target_object_guid, e.control_type
```

### 3.2 Post-SQL filters (in C#)

- `RuleEvaluatorHelpers.IsPrivilegedPrincipal(sid, context.PrivilegedSids)` — skips well-known admins (built-in SIDs + admin RIDs from `AdminRids`) **and** principals that are transitive members of the precomputed privileged closure (Domain Admins / Enterprise Admins / etc.). Broad SIDs (Everyone, Authenticated Users, Anonymous) are *not* skipped — they are the worst-case offenders here.

## 4. Data dependencies

| Table | Columns read | Required coverage module |
| --- | --- | --- |
| `fact_control_edge` | `source_sid`, `target_object_guid`, `control_type`, `deny_cancelled`, `edge_id` | `ControlEdges` |
| `dim_object` | `object_guid`, `distinguished_name`, `is_deleted` | `Objects` |

`ControlEdges` is derived from `SecurityDescriptors`, so `RuleCoverageRequirements["SEC-120"]` correctly maps to `[Objects, SecurityDescriptors, ControlEdges]`. The transitive `SecurityDescriptors` dependency is required because incomplete DACL capture upstream would mean an incomplete edge set and therefore false negatives. `context.PrivilegedSids` is built once per run from `fact_group_membership_closure`; it does not require its own coverage module since absence of closure data just degrades the exclusion (causing false positives, which are noisy but not silent misses).

## 5. Exclusions (and the reason each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| `deny_cancelled = 1` edges | SQL `WHERE e.deny_cancelled = 0` | The allow ACE was negated by a stronger deny ACE during edge derivation, so the trustee cannot actually exercise the right. |
| Out-of-scope control types | SQL `IN (...)` filter | Only ownership / full-write / DACL-rewrite primitives can re-publish AdminSDHolder permissions via SDProp. Reads, ResetPassword, etc. don't propagate. |
| Non-AdminSDHolder targets | SQL `LIKE '%CN=AdminSDHolder,CN=System,%'` | The rule is scoped to the SDProp template object specifically. Other ACL backdoors are covered by SEC-060/SEC-061/SEC-090 etc. |
| Deleted target objects | SQL `o.is_deleted = 0` | Tombstoned AdminSDHolder rows can't drive SDProp. |
| Well-known admins | C# `IsPrivilegedPrincipal` (admin RIDs + built-ins) | These principals already control AdminSDHolder by design (RID 500, RID 512, BUILTIN\Administrators, …). |
| Privileged-by-membership | C# `IsPrivilegedPrincipal` (closure-derived) | Custom accounts that are transitive members of tier-0 groups are equivalent to admins; surfacing them as SEC-120 would be a tautology and noise. |

Not excluded (intentionally subject to review):

- Broad SIDs (`Everyone`, `Authenticated Users`, `Anonymous`). These are the canonical worst-case offenders for an AdminSDHolder backdoor and must fire.
- Inherited vs. explicit edges — `fact_control_edge` does not distinguish; if the right reaches the SDProp object, it can rewrite the template.
- Object class — the rule asserts `o.object_class = 'container'` (`[IMP-TGT-CLASS]` resolved).
- DN anchoring — the DN filter is anchored to the head (`LIKE 'CN=AdminSDHolder,CN=System,%'`), so children of AdminSDHolder no longer match (`[IMP-TGT-CLASS]` resolved).

## 12. Defects / deferred items

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). Resolved items are kept for historical context and are intentionally untagged.

1. **Tombstone gap (resolved on rule).** The SQL did not filter `o.is_deleted = 0`, so lingering control-edge rows against tombstoned AdminSDHolder objects would surface as Critical findings. Fixed inline this session by adding `AND o.is_deleted = 0` to the `WHERE` clause; regression pinned by `WhenDeletedAdminSdHolderHasWriteDacl_ThenSEC120DoesNotFire`. Cross-cutting sweep against the other sibling rules in `AdvancedRuleEvaluator` (SEC-121, SEC-123, SEC-124, SEC-201) is still open — tracked under `[IMP-DEL-OBJ]`.
2. **Privileged-by-membership exclusion gap (resolved on rule).** The post-SQL filter used `IsAdminSid(sid)`, which only matches well-known admin RIDs and built-in SIDs. A custom account that was a transitive member of Domain Admins via `fact_group_membership_closure` would still fire — a tautological false positive. Fixed inline this session by swapping to `IsPrivilegedPrincipal(sid, context.PrivilegedSids)`; regression pinned by `WhenPrivilegedByMembershipHoldsGenericAllOnAdminSdHolder_ThenSEC120DoesNotFire`. Cross-cutting sweep against `AdvancedRuleEvaluator` siblings still open — tracked under `[IMP-PRIV-MEMB-SRC]`.

## 13. Improvement suggestions (not blocking)

> Tag each entry with an `[IMP-xxx]` code (see `docs/rules/IMPROVEMENTS.md`). If a needed tag does not exist, add it to the taxonomy first, then use it here.

1. `[IMP-TGT-CLASS]` — **RESOLVED** (re-tagged from `[IMP-CTRL-SCOPE]` — a target-identification issue; SEC-120 already fires on the full takeover set). The DN filter previously used a leading `%` (`LIKE '%CN=AdminSDHolder,CN=System,%'`), so it matched *children* of AdminSDHolder. The filter is now anchored to the DN head (`LIKE 'CN=AdminSDHolder,CN=System,%'`) so child objects no longer leak in. Pinned by `WhenChildOfAdminSdHolderViaDnLeakage_ThenSEC120DoesNotFire`.
2. `[IMP-TGT-CLASS]` — **RESOLVED.** The rule now asserts `o.object_class = 'container'`, so a synthetic / corrupt row carrying the AdminSDHolder DN but a different class no longer matches. Pinned by `WhenAdminSdHolderDnButNonContainerClass_ThenSEC120DoesNotFire`.
3. `[IMP-DN-ENRICH]` — `Detail` interpolates `targetDn ?? targetGuid.ToString()`. When `dn` is `NULL`, the operator sees only a GUID, which is unactionable. SEC-100/SEC-101/SEC-102 carry the same `[IMP-DN-ENRICH]` tag; the underlying fix (dim_object enrichment or a derived `dim_object_label` table) would resolve them all together.
4. `[IMP-PARITY-TEST]` — There is no per-rule parity assertion that the catalog row (`name`, `severity`, `category`, `mitre`, `tags`) wired into `BuiltInRules` matches `rules.yaml` for SEC-120. Same gap is open across the audited backlog.
5. `[IMP-CTX-RULEID]` — `EdgeFindingContext.RuleId` is duplicated as both the embedded `rule_id` JSON key and as a separate column (`FindingV2.RuleId`). Cheap consistency win across all evaluators emitting `CreateEdgeFinding` — tracked centrally.
6. `[IMP-MITRE-FIT]` — Catalog maps SEC-120 to `T1222.001` (Windows File and Directory Permissions Modification). The closer ATT&CK technique is `T1098.001` (Account Manipulation: Additional Cloud Credentials) or — more accurately — `T1098` Account Manipulation + `T1078.002` Domain Accounts. For AdminSDHolder specifically, BloodHound / MITRE describe this as the `GenericAll`/`WriteDACL` AdminSDHolder persistence pattern, which is most often classified as `T1098` with a `T1484.001` (Domain Policy Modification) overlay. Worth a catalog-wide re-review of MITRE mappings; same tag as SEC-091/SEC-092/SEC-100/SEC-101/SEC-102.

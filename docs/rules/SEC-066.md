## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-066
  name: "Weak Directory or SMB Signing Posture"
  description: >-
    A Group Policy security template (the [Registry Values] section of GptTmpl.inf) explicitly sets an
    Active Directory or SMB signing / channel-binding control to a known-weak value ... A weak value
    means the domain controller or member accepts unsigned or unbound authentication traffic, which is
    the on-ramp for NTLM and Kerberos relay and man-in-the-middle attacks ...
  severity: High
  category: ConfigurationHygiene
  remediation: >-
    Set the named control to its secure value ... Stage clients first ...
  mitre: T1557
  tags: ["gpo", "signing", "ldap", "smb", "relay", "hardening", "sysvol"]
```

## 2. Intended detection (plain English)

A GPO security template (`GptTmpl.inf [Registry Values]`, captured into `dim_gpo_setting`) explicitly
sets one of the tracked AD/SMB **signing or channel-binding** controls (`SigningHardeningCatalog`) to a
**known-weak value**. A weak value means the DC or member accepts **unsigned / unbound authentication
traffic** — the on-ramp for NTLM/Kerberos **relay** and MITM (MITRE **T1557**). This undermines the
directory-write (SEC-013/025/123/204) and certificate (SEC-040) findings, which assume an attacker must
already hold a permission: weak signing lets them **relay coerced authentication** into the directory
instead.

Each grant is a **review/hardening** finding (`disposition = review_required`), **High** severity.

### 3.1 Effective SQL

```sql
SELECT s.gpo_guid, s.setting_key, s.setting_value, gpo.distinguished_name
FROM dim_gpo_setting s
INNER JOIN dim_object gpo ON s.gpo_guid = gpo.object_guid
WHERE s.source_file = 'GptTmpl.inf' AND s.section = 'Registry Values'
  AND s.setting_value IS NOT NULL AND TRIM(s.setting_value) != ''
ORDER BY s.gpo_guid, s.setting_key
```

### 3.2 Per-row logic (in C#)

`setting_key` is the full `MACHINE\...` registry path; `setting_value` is `<regtype>,<value>`
(e.g. `"4,1"` = REG_DWORD 1). For each row:
1. Skip unless `SigningHardeningCatalog.Find(registryPath)` is non-null (a tracked signing setting).
2. Parse the dword via `ParseRegistryDwordValue` (token after the comma); skip if not an integer.
3. Skip if `!setting.IsWeak(value)` (secure value — not a finding).
4. Otherwise emit **High** / `review_required`. FindingKey discriminator = registry path (one finding
   per setting per GPO).

## 4. The setting catalog (every encoding grounded in a first-party Microsoft source)

| Control (GPO name) | Registry value | Weak condition | Secure | Source |
| --- | --- | --- | --- | --- |
| SMB server signing — "Microsoft network server: Digitally sign communications (always)" | `LanManServer\…\RequireSecuritySignature` | `= 0` | 1 | overview-server-message-block-signing |
| SMB client signing — "Microsoft network client: Digitally sign communications (always)" | `LanmanWorkstation\…\RequireSecuritySignature` | `= 0` | 1 | overview-server-message-block-signing |
| Netlogon secure channel — "Domain member: Digitally encrypt or sign secure channel data (always)" | `Netlogon\…\RequireSignOrSeal` | `= 0` | 1 | Windows security baseline (CCE-36142-8) |
| **LDAP server signing** — "Domain controller: LDAP server signing requirements" | `NTDS\…\LDAPServerIntegrity` | `≠ 2` (None=1) | 2 | **KB4520412** mapping table |
| **LDAP channel binding** — "Domain controller: LDAP server channel binding token requirements" | `NTDS\…\LdapEnforceChannelBinding` | `≠ 2` (Never=0 / WhenSupported=1) | 2 | **KB4520412** mapping table |

**Headline correctness point:** the **same captured value `1`** is **secure** for SMB signing
(1 = required) but **weak** for LDAP server signing (1 = None; secure = 2). Each catalog entry therefore
carries its own secure value + `SecureComparison` (`EqualsSecure` vs `AtLeastSecure`); a flat
"1 = secure" check would invert the LDAP verdict. **KB4520412** gives the verbatim GPO→registry map
(`None=1, Require Signing=2`; channel binding `Never=0, When Supported=1, Always=2`), which is what
turned the lab's `LDAPServerIntegrity=1` from inference into a verified true positive.

## 5. Operator explanation (the finding is self-describing — a design requirement)

Each catalog entry carries `PolicyName`, `WeakMeaning`, `AttackImpact`, `Fix`, and `Source`. The
evaluator composes the **Detail** string from `PolicyName + WeakMeaning + AttackImpact + Fix`, and the
**ContextJson** carries each field separately (`policy_name`, `weak_meaning`, `attack_impact`,
`recommended_fix`, `reference`, `configured_value`, `secure_value`). The UI investigation card
(`FindingInvestigationProvider.SpecificGuidanceByRule["SEC-066"]`) adds per-control concept text. So a
finding reads as: *what is weak* → *why it matters* → *exact value to set* — never an opaque
"registry value X = Y".

## 6. Exclusions (and why each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Untracked registry values | `SigningHardeningCatalog.Find` returns null | Only the 5 signing/channel-binding settings are in scope; the many other `[Registry Values]` rows (NoLMHash, password policy) are not flagged. |
| Secure values | `IsWeak` returns false | The whole point — a correctly-hardened value must be silent (lab's SMB `=1` and Netlogon `=1`). |
| Malformed values | `ParseRegistryDwordValue` returns null | A non-integer value is skipped rather than mis-flagged. |
| **Unset policy (absence)** | SQL only sees captured rows | **Deliberate:** an unset policy writes no row, and the effective OS default cannot be read from GptTmpl alone, so flagging absence would be a false-positive minefield (see §11). |
| Non-Registry-Values rows | SQL `section = 'Registry Values'` | Privilege Rights / Group Membership / other sections are out of scope. |

## 11. Defects / deferred items

1. **GPO precedence / RSoP** — the rule assesses each GPO's `[Registry Values]` in isolation, not the
   *effective* value after link-order/OU precedence. If GPO-A sets Require and GPO-B sets None, both are
   assessed independently; the effective DC state may differ. Documented limitation (same spirit as
   SEC-064 "we assess what is captured"). A future enhancement could correlate with gPLink scope.
2. **Windows Server 2025 enforcement key** — WS2025 adds `LDAPServerEnforceIntegrity` (a *separate*
   policy) which **overrides** `LDAPServerIntegrity`. On a 2025 DC where enforcement is enabled by
   default, a legacy `LDAPServerIntegrity=1` may be moot. The lab's `{6AC1786C}` GUID + the presence of
   the legacy key indicate pre-2025 tooling. Deferred: add `LDAPServerEnforceIntegrity` awareness when a
   2025 lab is available.
3. **Kerberos policy (ticket lifetimes, PKINIT)** — the `[Kerberos Policy]` section
   (`MaxTicketAge`/`MaxServiceAge`/etc.) is a distinct hardening concern, deferred to a future **SEC-067**
   (lower impact than signing/relay; not in this rule's scope).
4. **Absence-of-policy** — intentionally not flagged (see §6); revisit only if combined with per-DC OS
   version + effective-default modeling.

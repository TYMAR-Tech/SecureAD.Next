## 1. Catalog claim (verbatim from `rules.yaml`)

```yaml
- id: SEC-063
  name: "Unexpected Broad Control Over Container"
  description: >-
    A non-administrative principal holds a broad control right (GenericAll, GenericWrite,
    WriteAllProperties, WriteDacl, WriteOwner, or Owns) over an organizational unit. Broad OU
    control confers authority over every object in the OU subtree, including the ability to write
    gPLink, reset passwords, and rewrite ACLs on descendants. AD delegation legitimately grants OU
    owners and data administrators broad control, so this is a delegation to review and confirm
    intended rather than proof of compromise — but where the OU subtree contains a Tier 0 object it
    is a direct privilege-escalation path that must be fixed if unintended.
  severity: Medium
  category: ConfigurationHygiene
  remediation: >-
    Confirm the principal is an intended OU owner or data administrator. If the delegation is not
    intended, remove the broad control and re-delegate the specific task required ... Prioritize any
    OU whose subtree contains Tier 0 objects.
  mitre: T1222.001
  tags: ["delegation", "ou-control", "review", "least-privilege"]
```

## 2. Intended detection (plain English)

Fire one finding per `(non-admin, non-broad principal, organizationalUnit)` pair where the principal
holds a broad control right (`GenericAll` / `GenericWrite` / `WriteAllProperties` / `WriteDacl` /
`WriteOwner` / `Owns`) over the OU. Broad OU control confers authority over the whole subtree, so it
is a genuine capability — but Microsoft's delegation model (Delegation of Control Wizard, OU-owner /
data-administrator roles) makes broad OU delegation an **intended, first-class pattern**. The rule
therefore surfaces each as a **review** finding (`disposition = review_required`): confirm the
delegation is intended, and if it is not, it is a fix.

Impact is tiered by **subtree Tier-0 reach**:
- **Critical** when the OU subtree contains a Tier-0 object — including an account that is a Tier-0
  member purely by group membership (transitive Domain/Enterprise/Schema Admins) **at any nesting
  depth**. This is the genuine escalation path: control the OU → control the deeply-nested DA.
- **Medium** otherwise (delegation debt to confirm and tighten).

### 3.1 Effective SQL (broad-control edges on OUs)

```sql
SELECT e.source_sid, e.target_object_guid, MIN(o.distinguished_name) AS dn,
       MIN(e.edge_id) AS edge_id, MIN(e.control_type) AS control_type
FROM fact_control_edge e
INNER JOIN dim_object o ON e.target_object_guid = o.object_guid
WHERE e.control_type IN ('GenericAll','GenericWrite','WriteAllProperties','WriteDacl','WriteOwner','Owns')
  AND e.deny_cancelled = 0
  AND o.object_class = 'organizationalUnit'
  AND o.is_deleted = 0
GROUP BY e.source_sid, e.target_object_guid
ORDER BY e.source_sid, e.target_object_guid
```

### 3.2 Tier-0 reach (in C#, depth-agnostic)

`LoadTier0Sids` = transitive members of DA/EA/SA (`fact_group_membership_closure` group_sid LIKE
`%-512` / `%-518` / `%-519`) **+** every captured `dim_object.sid` that `IsAdminSid` recognizes
(well-known RIDs and the DA/EA/SA group objects). `LoadTier0AncestorOus` resolves each Tier-0 SID to
its object DN and walks `DnHelper.GetParentDn` up the chain, adding every ancestor `OU=` DN. A finding
is Critical when its OU DN is in that set — i.e. a Tier-0 object lives somewhere in the OU subtree,
**regardless of nesting depth**. This deliberately avoids fragile DN suffix-matching.

### 3.3 Post-SQL filters

- `ShouldExcludePrivilegedTrustee(sid, PrivilegedSids)` — admins and privileged-by-membership
  trustees are expected OU owners; excluded.
- `BroadPrincipalCatalog.IsBroad(sid)` — broad principals (Everyone / Authenticated Users / Domain
  Users) are SEC-060's domain; excluded here to partition cleanly (no double-count).

## 5. Exclusions (and why each is correct)

| Exclusion | Mechanism | Justification |
| --- | --- | --- |
| Well-known admin / privileged-by-membership sources | `ShouldExcludePrivilegedTrustee` | Expected OU owners; a DA managing an OU is normal operation. |
| Broad principals | `BroadPrincipalCatalog.IsBroad` | Owned by SEC-060 (broad-principal write); partition avoids double-counting. |
| Non-OU targets | SQL `object_class = 'organizationalUnit'` | Broad control on users/computers/GPOs is SEC-001/024/025/080/204 territory. Sites/domain root are SEC-001/201's domain. |
| Deny-cancelled edges | SQL `deny_cancelled = 0` | The principal does not effectively hold the right. |
| Deleted OUs | SQL `is_deleted = 0` | A tombstoned OU applies to nothing. |
| Read-only edges | control-type set is write/control only | Read access is not control. |

## 8. Output assertions

`ContextJson` carries `disposition = "review_required"` and `tier0_in_subtree` (bool). `Detail` leads
with **"Review delegation:"** and, when `tier0_in_subtree`, states the subtree contains a Tier 0
object. Severity is `Critical` iff `tier0_in_subtree`, else `Medium`. Pinned by P1/P2.

## 9. Disposition model (Severity vs Review)

Severity expresses **impact if unintended** (Critical when a Tier-0 object is reachable; Medium
otherwise). `disposition = review_required` expresses **certainty** — broad OU delegation is a
supported AD pattern, so the finding asks the operator to confirm intent. Reads as "Critical · Review
Delegation" / "Medium · Review Delegation" without adding a new `Severity` enum value. (If a
first-class grid "Review" badge/filter is wanted later, promote `disposition` to a typed `FindingV2`
field; the context is already present.)

## 10. Live lab validation

Root + 2-child lab (2,787 objects): **2 Critical** (broad control over `OU=Users,OU=BA Lab` whose
subtree holds `ba.admin`, a DA **by membership**, depth ~5) + **1037 Medium** review findings = 1039.
6 Tier-0 ancestor OUs identified via the closure + `DnHelper.GetParentDn` walk. Confirms the
deep-nesting Tier-0 detection works on real data (the earlier ad-hoc DN suffix-match was replaced by
the robust `GetParentDn` walk). Probe: `LabDbProbe.ValidateSec063_AgainstLab` (read-only, lab-only).

## 11. Defects / deferred items

1. `[IMP-DN-ENRICH]` — `Detail` / `ContextJson` carry the source SID but no display name; join
   `dim_principal` for `source_name`. Family-wide.
2. `[IMP-COV-MEMB]` — declared coverage includes `GroupMembership` (needed for both the privileged
   exclusion and the Tier-0 closure), so SEC-063 is **not** subject to the silent-degradation gap that
   affects the other privileged-SID consumers — but a `coverage_reason` is still only stamped when the
   module is recorded missing.
3. **Partition with SEC-081** — broad `WriteAllProperties`/`GenericAll` on an OU now fires **both**
   SEC-081 (`link_capability = via_broad_write`, gPLink-specific framing) and SEC-063 (whole-OU
   control framing). Intentional: the two findings answer different questions (can-link-GPO vs.
   controls-the-OU-subtree). Revisit if the overlap proves noisy in practice.

# Prompt for the P-280 reviewer

Paste everything below the line. Frozen 2026-09-24 alongside
[`P280-PROPOSAL.md`](P280-PROPOSAL.md).

---

You have full access to this repository. I want an adversarial review of a storage
change, not a summary and not approval.

**Read first:** `docs/specs/P280-PROPOSAL.md`. Then
`docs/specs/P280-JUDGEMENT-OCCURRENCE-ROWS.md` for the living specification, and
`.github/copilot-instructions.md` for how this repository judges its own work.

**Context in one paragraph.** SecureAD captures an Active Directory forest into sealed
evidence and judges it against security rules. A judging run of the owner's production
forest — 940,067 objects, nine domains — would write a 138 GB result describing 18.67 GB
of evidence, and a real run was abandoned after eight hours at 27 GB still growing. The
proposal restructures one table, `permission_classification_entry`, so that the same run
writes roughly 3.5 GB. No permission stops being reported; the change is storage shape
only.

**The standard this has to meet.** This is an audit tool. A customer makes a security
decision on what it reports. The failure that matters is not a crash — it is the product
saying something false: a permission attributed to the wrong object, a "found nothing"
that was really "could not compute", an object reported safe that is not. Please weight
your review accordingly.

## Argue with me on these, in this order

**1. The claim the whole proposal rests on: that classifying a permission entry depends
only on the entry, never on the object it sits on.**

I traced `PermissionClassification.CreateObjectResult` and everything it calls and
concluded the target object's class, name, attributes and Tier 0 status never reach the
classification. `DangerousPermissionClassifier` appears to state the principle
deliberately.

**Try to break this.** Find any path — now or plausibly in future rule work — where a
property of the target object influences `Rights`, `Summary`, `Scope`,
`RightsAreComplete`, `right_count`, `reading_id`, `object_schema` or
`inherited_schema`. **If you find one, shapes C and D in the proposal are wrong and
would cause the product to report a permission it does not have.** That is the single
most valuable thing you could find here, so please spend disproportionate effort on it.

**2. The fingerprint — §8 of the proposal.**

`SharedPermissionStorage` says the fingerprint *is the binding*: it is what made removing
`target` from `permission_entry` safe in `P-279`. My proposal removes the per-occurrence
row, so there is nowhere to put a per-occurrence fingerprint. I propose fingerprinting
`(descriptor_id, generation, ordinal, entry)` and letting the **evidence seal** carry the
object-to-descriptor half, and I argue that is stronger than today because half the chain
is then protected by a hash over sealed evidence rather than by one the judgement writes
about itself.

**Construct a scenario where an occurrence becomes misattributed or unverifiable under
that scheme** — a copied judgement, a re-judged bundle, a generation mismatch, two
objects swapping descriptors between runs, a tampered judgement paired with intact
evidence. If you cannot construct one, say what you tried; that is more useful to me than
agreement.

**3. Dropping `position`.**

I claim `position` is never independent information — it is only ever the rank within the
list ordered by `ordinal`, derivable at read time even when ordinals have gaps (which
happens when `ParseAcl` skips a malformed ACE, exactly when `DaclCompleteness` is
`Incomplete`). **Construct a DACL where rank-at-read differs from the stored position**,
or confirm it cannot exist.

**4. What the measurement is anchored to.**

This repository has a recorded finding, `F-S44-2`, where three sound test suites agreed
with each other in both directions with negative controls, and the whole circle was
anchored to the wrong reference — so fifteen attributes nobody had written a rule for
were silently missing. The lesson recorded was: *ask what a set of checks is anchored to,
not only whether each one is sound.*

So: **what is my forecast anchored to?** It is validated against
`next/artifacts/p279-after`, where it forecast 17,164,866 occurrences against that
judgement's actual 17,164,866 rows. But that bundle is **synthetic**, generated by this
same codebase, and it carries **zero object-type GUIDs** — while on the real forest those
GUID columns are the largest single item at 14.9 GB. Is the anchor adequate? What is
still unanchored that I have not noticed?

**5. What the byte model gets wrong.**

`JudgementForecast.RowModel` prices rows from SQLite's record format. It reports 365
bytes per row against 418.9 observed on the one bundle that can check it. Two independent
routes to the same production figure agree within 1.3%. Please check the model's
constants against SQLite's actual record and b-tree formats, and say whether
`WITHOUT ROWID` is genuinely a win at the proposed row size or whether I have talked
myself into it.

## Also check, because I cannot from here

- **Read paths.** Everything that reads a judgement would go through a join. This
  repository requires that bounded paging *"must not eagerly reconstruct whole objects,
  derive totals or risk from loaded pages, truncate oversized values, or conflate
  unloaded pages with incomplete captured evidence."* Does the proposed shape endanger
  any of that? Does Stage 7 saved-path presentation break?
- **Saved results.** The standing requirement is to *"preserve per-right permission
  classifications, reasons, inheritance/applicability and captured-schema support as
  saved generation-bound results."* Moving those onto a per-entry table — does the
  generation binding still hold, given `permission_entry` already carries a generation?
- **`PermissionClassificationStorage.Complete`** counts occurrences per object and
  refuses a product whose counts disagree. Under the proposal it becomes a join. Can it
  still refuse every case it refuses today?
- **What I have not costed at all.** Control edges. The calibration bundle derived none —
  `control_ace`, `full_control_source_entry` and `shared_proof_value` were all empty — so
  every figure in the proposal is a floor. Is there a cheaper way to bound that than
  running a full derivation?

## What I want back

1. **Anything that would make the product report something false.** Severity first,
   everything else after.
2. **A verdict on §8**, the fingerprint: sound, unsound, or needs a different scheme —
   with the scenario that decides it.
3. **Anything I have assumed rather than measured** that should be measured before
   building rather than after.
4. **Anything scoped wrongly** — too much in one change, or something excluded that
   should be in. In particular: I excluded compressing `security_descriptor.raw_bytes`
   because it lives in sealed evidence and touching it would force a re-capture of nine
   domains before the change could be tested. Is that the right call?

**Please disagree where you disagree.** A review that confirms my reasoning back to me is
worth nothing; I have already convinced myself, which is the problem. If the proposal is
sound, the most useful thing you can tell me is which parts you tried hardest to break
and could not.
